NEW: Split `$text` into slot content vs source provenance — spec at `docs/superpowers/specs/2026-08-26-text-content-vs-source-provenance.md`. `$text` currently means two unrelated things: the VALUE of a text-modeled kind (an identifier's name — survives edits) and the SPAN a structural node was read from (provenance — destroyed by any edit, kept only to replay untouched subtrees byte-exactly). Because both share a name, `hasStructure` / `isUntouchedSubtree` / `_isReadTextLeaf` / `slot.rs` each re-derive which role is in play from node shape, the JS and native readers disagree (JS omits branch `$text` behind `SITTIR_DEBUG_TEXT`, native always captures it), and structural text is ~23% of a deep read's wire — 99.9% of all `$text` bytes on an 8KB file, re-sent once per nesting level.

    END STATE: `$text` means content only; provenance becomes the coordinate `(tree, $span)`, which handles already name now that they carry their tree id and the engine retains trees. ONE transport rule — unread and unedited are the same state, both coordinates-only, both short-circuit. Biggest win is CORRECTNESS not wire size: a deep read currently rebuilds every level and re-spells the source even with zero edits (`pub fn main() {\n\t// keep me\n...` → `pub fn main(){ // keep me\nlet x=1;...}`); under this rule deep and shallow render byte-identically.

    CARRIER: `SlotValue` stays a two-arm enum but `Node(T)` and `Verbatim(String)` both go — it becomes `Coord(NodeCoordinate) | Transport(T)`, orthogonal on one axis (is the content in the tree, or in this message). `Verbatim`'s three meanings separate: captured span -> `Coord`, text-as-content -> `VerbatimTransport` inside `Transport`, free text in a slot admitting no text kind -> error. NOT a field on each transport struct: storage fields are mostly REQUIRED (rust 242/429, ts 306/516, py 186/261 — only the `$`-prefixed metadata is optional), and a coord-only value has no storage, so a coord field would force every required field to become `Option` — downgrading that many grammar facts to "maybe" so one unrelated state could be expressed. The enum keeps them required because a `Coord` never constructs a transport at all, makes coord+storage unrepresentable, and stays one mechanism where a field would be two (enum-typed slots need an arm regardless). `#![recursion_limit = "256"]` is the price and it is a compile-time knob already paid. `RenderRoot` is already `SlotValue<AnyTransport>` so the root is covered by the same arm.

Same cause. NEW: **The wrap functions have no declared return type, and that is load-bearing debt.** Every `wrapX` is emitted as `export function wrapX(data, tree) { … }` with its return INFERRED, and `XTree` is then defined backwards from it — `export type SourceFileTree = _WrapReturnByKindId[TSKindId.SourceFile]`, where the map's entries are `ReturnType<typeof wrapX>`. Two consequences, one visible and one measured.

    VISIBLE: drilling into a parsed tree loses the wrapped surface IN TYPES. `drillIn<T>(entry: T): T` and `drillInAll<T>(entries): T[]` declare the DATA type they were handed, so `file.statements()?.[0]` types as `Statement | undefined` — no `$with`, no accessors — even though at runtime it is a fully wrapped node (`fn.$with.name('run')` renders `pub fn run(){ }` from a bare string). The loose `$with` landed in the emitter is therefore reachable in typed code only at the ROOT, whose type IS annotated; one level down a caller needs a cast, which the no-casts gate forbids.

    MEASURED: the obvious fix does not work while returns are inferred. Declaring `drillIn<T>(…): _TreeOf<T>` with `type _TreeOf<T> = T extends { $type: infer K } ? K extends keyof _WrapReturnByKindId ? _WrapReturnByKindId[K] : T : T` makes the whole-repo type-check TIME OUT past 10 minutes rather than fail — inferring `wrapSourceFile`'s return needs `_TreeOf<Statement>`, which needs `wrapExpressionStatement`'s return, which needs more `_TreeOf`, and nothing bounds it. `wrapNode` gets away with the same indexed access only because it is a declaration, never inferred through.

    FIX: emit an explicit `XTree` type per kind — storage keys, accessors returning the Tree types of what they hold, the `$with` record, the node methods — and annotate `wrapX` with it. The annotation is what breaks the cycle: the checker uses the declared type instead of inferring through the recursion. `_WrapReturnByKindId` then becomes a map of declared types rather than `ReturnType<…>`, and `drillIn` can name the wrapped return honestly. Size it deliberately: this is one declared type per kind on top of a generated `types.ts` that is already ~11k lines for rust, and it neighbours the `__slots__` stamped-interface design (item 26's cousin) — the two should be decided together rather than one bolted onto the other.

OPTIONAL ENHANCEMENT (deprioritized — read the spec's opening section before building any of it): **The node surface should be immutable; setters belong a layer up** — spec at `docs/superpowers/specs/2026-08-26-immutable-node-surface-and-layered-setters.md`. `$with` is authored TWICE by two emitters that cannot see the same things, and the two results are different public APIs for one operation: a factory-built node declares `name(value: T.Identifier | T.Metavariable)` while a parsed node declares `name: (v: LooseConfig['name'])`. A caller has to know which shape of node it holds to know what the setter takes, and nothing in the API says so. Not an oversight — a coercing setter needs the resolver AND the factory, `from.ts` has both so wrap's setters coerce, and `factories.ts` sits below the resolvers so its setters cannot. Scale: 419/429/289 `$with` mentions in factories, 209/213/144 in wrap. END STATE: factories/from/wrap emit the immutable node — `$type`, `_<slot>` storage, accessors, `$render`/`$toEdit`/`$replace`/`$trivia` — and `ir.ts` attaches setters in ONE construction shaped `callable & { strict }`, mirroring the `ir.*` bundle it already builds 140 times with `attachProps`. Convergence becomes structural rather than maintained. Shape settled: setters are one more stage in the pipeline `ir.ts` already runs, `addNamespace(makeMutable(FR.xxx, F.xxx, { <field>: FR.resolveXxx_field }), { strict, …variants })` — `addNamespace` is today's `attachProps` renamed for what it does, and `makeMutable` is the only new part, taking the coercing factory, the strict one and the kind's own resolvers and returning a factory whose nodes carry `$with`. Runtime is a LOOP and the types come from the call site — exactly how accessors are already attached: `withAccessors<T, A>(node, accessors): T & A` iterates `Object.keys` and every accessor's type is inferred through `A` from the record literal. `makeMutable` binds setters the same way, so NO projection over `NamespaceMap` is needed — the per-kind record literal IS the type. The earlier worry about a runtime table erasing per-field types applies to a GLOBAL table keyed by kind, not to a per-kind literal. Gate it on the type-check baseline: if the count moves, it is expanding something it should be indexing. TWO GENERATED STAGES: `namespaces.ts` holds the per-kind bundles (`attachProps(FR.coerceToX, { strict, …variants })`) with NO setters and no entry mentioning another; `mutable.ts` imports all of it and emits `makeMutable(NS.x, { <field>: NS.<slotKind> })` per kind. The split is what keeps the TYPES resolvable — stage one is complete before stage two names it, so nothing is inferred through something still being inferred, which is exactly the non-termination item 30 records. Chaining survives with NO self-reference: `makeMutable(ns, slots)` closes over both, and each setter rebuilds through that same `ns` and re-attaches from that same `slots`, so the module never reaches back into its own exports. BIND THE `ir` ENTRY, NOT A BARE RESOLVER: a slot admitting ONE kind binds that kind's `ir` entry and inherits its whole surface — coercing call, `.strict`, AND the named sub-factories, so `ir.lineComment.doc` becomes `$with.<field>.doc` without the setter emitter knowing that variant exists. Measured reach: 329/417 rust, 387/510 typescript, 196/243 python slots are single-kind (76–81%). The remaining fifth admits a union that no single entry describes and binds the field resolver instead. Verify before assuming the majority case is free — a single-kind slot's `LooseConfig[field]` and that kind's own `Loose` are close but not obviously identical (the field may carry `__looseHints__` the bare entry lacks). NB `buildWithNamespace` (item 28) is the vestige of exactly this design, written and never wired; it becomes the helper or it goes. NB also the `@ts-expect-error` in `packages/rust/tests/loose-with-on-tree-nodes.test.ts` pins the divergence as intent and must be deleted by this work. WHY THIS IS SUGAR, NOT A DEFECT FIX: `$with.x(y)` takes `y` at the field's own type, and a caller wanting coercion already has a direct route — `node.$with.name(ir.identifier('run'))` works today and always will. The loose setter saves one composition. Real but small. And the one piece of sugar that WOULD have been worth adding, variadic setters for array/separated-list slots, ALREADY EXISTS on both sides (`statements(...values: T.Statement[])` in factories, `statements: (...v: …[number][])` in wrap). What is left is a cosmetic inconsistency between built and parsed setter parameter types — worth fixing while these emitters are already open for another reason, not worth opening them for. Cheaper alternative recorded in the spec and NOT chosen: only `_wrapWithChildren` pins the resolvers above factories (0 of 275 resolvers touch `F.` directly), so late-binding that one dispatch would let factories coerce — but that fixes the layering without fixing the duplication.
