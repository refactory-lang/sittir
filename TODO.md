NEW: **The wrap functions have no declared return type, and that is load-bearing debt.** Every `wrapX` is emitted as `export function wrapX(data, tree) { … }` with its return INFERRED, and `XTree` is then defined backwards from it — `export type SourceFileTree = _WrapReturnByKindId[TSKindId.SourceFile]`, where the map's entries are `ReturnType<typeof wrapX>`. Two consequences, one visible and one measured.

    VISIBLE: drilling into a parsed tree loses the wrapped surface IN TYPES. `drillIn<T>(entry: T): T` and `drillInAll<T>(entries): T[]` declare the DATA type they were handed, so `file.statements()?.[0]` types as `Statement | undefined` — no `$with`, no accessors — even though at runtime it is a fully wrapped node (`fn.$with.name('run')` renders `pub fn run(){ }` from a bare string). The loose `$with` landed in the emitter is therefore reachable in typed code only at the ROOT, whose type IS annotated; one level down a caller needs a cast, which the no-casts gate forbids.

    MEASURED: the obvious fix does not work while returns are inferred. Declaring `drillIn<T>(…): _TreeOf<T>` with `type _TreeOf<T> = T extends { $type: infer K } ? K extends keyof _WrapReturnByKindId ? _WrapReturnByKindId[K] : T : T` makes the whole-repo type-check TIME OUT past 10 minutes rather than fail — inferring `wrapSourceFile`'s return needs `_TreeOf<Statement>`, which needs `wrapExpressionStatement`'s return, which needs more `_TreeOf`, and nothing bounds it. `wrapNode` gets away with the same indexed access only because it is a declaration, never inferred through.

    FIX: emit an explicit `XTree` type per kind — storage keys, accessors returning the Tree types of what they hold, the `$with` record, the node methods — and annotate `wrapX` with it. The annotation is what breaks the cycle: the checker uses the declared type instead of inferring through the recursion. `_WrapReturnByKindId` then becomes a map of declared types rather than `ReturnType<…>`, and `drillIn` can name the wrapped return honestly. Size it deliberately: this is one declared type per kind on top of a generated `types.ts` that is already ~11k lines for rust, and it neighbours the `__slots__` stamped-interface design (item 26's cousin) — the two should be decided together rather than one bolted onto the other.

NEW: **The structural builders stamp ref facts that flatten.ts should derive.** `packages/codegen/src/compiler/evaluate.ts`'s injected `optional()`, `repeat()`, `repeat1()` and `field()` each run `walkRefs(...)` at construction time to mutate a side-table of `SymbolRef { refType, from, to, fromRuleId?, fieldName?, optional?, repeated?, position? }` — `optional()` sets `ref.optional = true`, the repeats set `ref.repeated = true`, `field()` sets `ref.fieldName` on every ref beneath its content that does not already have one. All four are POSITION facts about where a ref sits in the finished rule tree, and the tree is walked again downstream; flatten.ts is the phase that already has the position and should own the derivation. Stamping them in the builders makes the fact's source "whoever happened to call the constructor", which is why the SECOND ref-fact stamping in evaluate — `field()`'s first-writer-wins `if (ref.fieldName === undefined)` — is order-dependent in a way nothing in the model records.

    CONSEQUENCE THAT MOTIVATED THIS: `reconstructWrapper` (`dsl/transform/transform-path.ts`) cannot rebuild a wrapper by spreading, because the constructor call IS the side effect — it must re-invoke `optional()`/`field()` to re-stamp the refs, and everything the constructor's parameters cannot express (`metadata`, a delimited repeat's `separator`/`leading`/`trailing`) then has to be carried back over by hand. Move the stamping to flatten and the reconstruction becomes a plain structural rebuild with nothing to restore.

    NB this does NOT remove the need for `carryOverProperties`: the tree-sitter side of the dual pipeline injects tree-sitter's own `field()`, which sittir does not control, so a rebuild routes through a foreign constructor there regardless. Byte identity of all three grammars' generated output is the gate.
