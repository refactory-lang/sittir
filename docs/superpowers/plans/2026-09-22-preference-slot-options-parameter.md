# Preference slots drop out of config, into a per-call options parameter

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** every slot an `options:` declaration registers as a preference site — not just a spelling site with no kind ids — leaves the factory's config object and becomes a trailing per-call `options` parameter, defaulting to the site's declared arm. `ir.returnStatement(expression)` instead of `ir.returnStatement({ expression, terminator: ';' })`; the terminator is still overridable, now as `ir.returnStatement(expression, { terminator: 'automatic_semicolon' })`.

**Architecture:** PR #315 (`feat/token-case-spelling`, stacked on #313 on #311) built this collapse for one narrow case: a registered slot whose arms are literal text with no kind ids (`prefix: '0x' | '0X'`, `marker: 'e' | 'E'`). Its `registeredOption` stamp, `configSlots`, `spellingTypeOf`/`registeredSlotSource` and the trailing-parameter factory surface are the mechanism to generalize — not rebuild. The gap this plan closes: a registered *choice* slot (`terminator`, `quotes/style`, the ~20 statement kinds and `string`) has arms that ARE kind ids, are read by the native render engine's option table, and currently stay in `config` because `classifyFactoryShape`/`resolveFactorySurface` never learned to treat them like spelling sites. This plan is grammar/codegen + factory-surface only; it does not touch `render(options)` or the native option table, which already read these sites correctly.

**Tech Stack:** TypeScript (ESM, `.ts` imports), sittir codegen pipeline (`packages/codegen/src`), the three grammar packages.

## Design questions to settle before coding (STOP for user rulings)

1. **Scope of "preference slot".** `registeredOption` today only ever gets set from the literal-arms branch in `withDeclaredArms` (`site-preferences.ts`). A `choice`-source site (`source: 'choice'`, arms with `kind`) resolves through a different branch and pushes a `SitePreference`, never touching the model slot. Does the collapse apply to every `source: 'choice'` site, or only ones the grammar explicitly opts a slot into (to avoid surprising every future `preference()` declaration with a signature change)? Recommend: every registered site, matching the "apply to every node" ruling from #315 — but flag that this is a wider blast radius (≈20+ kinds already use `terminator`/`quotes`).
2. **Multiple registered slots on one node.** `#315`'s `spellingTypeOf` already builds one object type over all registered slots on a node, so this generalizes for free. Confirm no node has a registered slot AND is itself a `spread`/`elements` shape (list kinds) — those don't go through `resolveConfigFactorySurface`'s config branch and would need a separate surface.
3. **Loose/from-side surface.** `#315` added the options parameter to `emitters/from.ts`'s branch resolver for the `direct`/`forwarded` path. The `config`-shape path (still most nodes with a registered choice slot, since they usually have >1 real slot too) needs the same trailing parameter threaded through `emitBranchFrom`'s multi-slot branch — not yet built for spelling sites because none of the nine spelling-site nodes had >1 real slot. This plan's first real node (`expression_statement`: `expression` + `terminator`) exercises that path for the first time.
4. **Native render still needs a value when the caller doesn't ask.** Today a `config`-shape node's `terminator` slot is `undefined` unless the caller sets it, and native render's per-tree/per-call/engine/grammar-default chain (site-preferences doc, "Render options design state" memory) fills it at render time. If the factory now *always* stamps `options?.terminator ?? declaredDefault`, that pre-empts the native chain — a node built once and rendered under two different engine option sets would render the same terminator both times, which breaks the whole point of engine-level defaults. **This is the central risk, not a detail.** Candidate resolutions:
   - (a) Registered choice slots with a *render-time* resolution chain (anything already reachable via `render(options)` / engine options / `inferOptions()`) do NOT get an eager default baked into the built node — the factory leaves the slot genuinely `undefined` when the caller omits it, and only the render path fills it. This means the options parameter here is sugar for "set the slot", not a resolution point; a bare `ir.returnStatement(expression)` renders with whatever the render-time chain picks, same as writing `{ expression, terminator: undefined }` today.
   - (b) Bake the site's own default (as spelling sites do) and accept that render-time engine defaults no longer affect these slots once the factory ran. This directly conflicts with the render-options design ("stamp-else-engine-option-table"; per-tree > stamp > per-call > tree table > engine > grammar default) and probably regresses it.
   - Recommend (a): the options parameter's arm becomes just another way to set the slot (like today's `{ terminator: ... }`), not a new defaulting layer — the "drop from config" is purely a config-shape / ergonomics change, and default resolution stays exactly where it lives now (native render). This is DIFFERENT from #315's spelling sites, where there was no render-time resolution chain to preserve (a lexed kind's prefix isn't a native option site at all). **This needs your ruling before Task 2, because it changes what "collapse" buys for choice sites vs. spelling sites.**

## Task 2 — factory surface: options parameter for choice-arm registered slots

Blocked on the ruling in design question 4.

- [ ] `emitters/factories.ts`: `registeredSlotSource` currently emits `options?.${configKey} ?? ${JSON.stringify(optionDefaultArm)}`. Under resolution (a), a choice-arm registered slot must NOT get the `?? default` fallback baked in — it should emit `options?.${configKey}` alone (`undefined` when absent), while a literal-arm (spelling) slot keeps the eager default. Distinguish the two by whether the site's arms carry `kind` (reuse the same test `withDeclaredArms` uses to decide the collapse) — thread that bit onto the model stamp (e.g. `registeredOption: 'spelling' | 'choice'` instead of `boolean`) rather than re-deriving it in the emitter.
- [ ] `spellingTypeOf`/`omitRegistered` generalize as-is (they already iterate all `registeredOption` slots regardless of kind).
- [ ] Rename the emitted type from `Spelling` to something that covers both (`Options`? — check for collision with the per-node `Options` used elsewhere in `types.ts`/`options.ts`; likely needs a different name, e.g. `T.<Kind>.Preferences`). **Ask before choosing** — `Options` is already the top-level per-grammar type name.

## Open risk not yet resolved by this plan

`terminator`'s current default resolution reads `slot value ?? option value` (per the labels-via-bindings handoff: "the config *supplies* the option's default"). If Task 2 goes with resolution (a) — slot stays genuinely `undefined` when the caller omits the parameter — then a *read* tree that never sets the slot (e.g. from `wrap`) and a *factory-built* tree that never sets it must resolve identically at render time. Confirm `wrap.ts`'s equivalent slots already leave `_terminator` `undefined` in the same case (they should, since wrap doesn't invent values tree-sitter didn't parse) before assuming parity — check `wrapExpressionStatement` alongside Task 3.
