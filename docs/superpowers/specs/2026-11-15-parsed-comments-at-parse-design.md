# A parse places comments and nothing else

**Status:** approved in direction by the maintainer, 2026-11-15. The output examples, the deletion list and the order below were proposed by the peer that owns the arena work, from the engine's code. Entries marked "to verify" are checked on a probe before they are built. This supersedes lazy whitespace placement and the tree-owned placed-sides design that followed from it.

## Decided by the maintainer

- **"Lazy placement means we're storing a side channel for extra data we don't need... We are giving too much up just to preserve whitespace.... I don't think it's worth it"** (2026-11-15). This returns to the 2026-11-05 rulings "comments (nontrivial trivia) is important, but whitespace really isn't" and "addition by subtraction — simply remove the logic that creates the gaps table".
- **A parsed node does not behave differently from a built node** (2026-11-15, said while reading the render numbers).
- **Comments are placed "during parse for sure"** (2026-11-15).
- **How a placed side is stored: "it would be whatever matches built nodes"** (2026-11-16). Where this design leaves a form open, the form a built node already uses decides it.
- **Blank lines: "Yes, on list items only"** (2026-11-15). One fact, kept only for items of a list slot.
- **A blank-line run is held as the layout kind that matches it** (2026-11-20, "Double_blankline is a layout kind", then "Both follow the run"). One blank line is `blankline`; two or more are `double_blankline`, the largest layout kind, so a run of three or more renders as two. This holds for every blank-line fact: a list item's, and the member a comment holds after it. It replaces the 2026-11-15 reading that a rebuilt list writes one blank line whatever the run's length.
- **The run before a comment on its own row is kept on every side** (2026-11-20, "Keep it"). A trailing or inner side's first entry on its own row holds the blank-line run before it as its layout kind, as a leading side's entry does. So a same-value rebuild of a list whose last item is followed by `⏎⏎# five` keeps the blank line, as it already did when the comment led another item (python's `x = 1⏎⏎# five⏎` renders unchanged; a run of three or more renders as two).
- **A list broken across lines: "Accept: options decide"** (2026-11-15).
- **Indentation: "We need a generic way to enforce this"**, with nothing specific to one grammar (2026-11-15).
- **"there should be no 'parse' side channel of data not captured within the materialized nodes"** (2026-11-12) stands, and this design applies it to placement.
- **Both storages take gaps from options** (2026-11-17), with object storage's own placement deferred ("I don't want to invest too much time in object storage"): in the lookup both storages share, a layout run keeps its source form only where it sits directly beside an extra, an `ERROR` or a member entry; every other gap takes the options.
- **Object storage follows arena's output now** (2026-11-19, "Object follows now"), replacing, in the bullet above, the source form a layout run kept beside an extra, an `ERROR` or a member entry. The premise of the deferral, that it leaves no difference in output, did not hold once arena's render read only the parse-placed sides: the two storages rendered the same edited or snapshot node differently in 580 corpus nodes. Object storage's placer writes the sides parse writes, each entry with its line-break members and nothing else, and the lookup both storages share keeps no source gap beside an entry. Object storage's parse-time placement stays deferred, and so its placer stays when arena's is deleted (the maintainer, 2026-11-20: "Keep object's"): it keeps placing lazily, calling the same edge-item rule arena's render calls. The two storages give one output, and the storage comparison holds them to it.
- **A source gap beside a comment is kept only while both its sides are the same** (2026-11-17). A layout run keeps its source form beside an entry only when that entry's side is seated between the gap's own two tokens, decided from the parse spans; once the comment is seated between different neighbours, the options decide the gap, as for a built node. The example this was first asked on, `for /* keep */ (;;) { x(); }`, turned out not to be a kept gap: a snapshot seats the comment on the leading side of the initializer, a unit, with no layout run beside it, and the space in `for (/* keep */ ;;) {` is the join every leading side writes between a same-line entry and its owner (`NodeTrivia::render_leading`; the trivia-ownership spec, "leading: each entry, then a line break (or a space when `$sameLine`), then the owner"). A built node renders the same space, whatever kind the owner is, so that output stands. One wording to reconcile when the placer's spec is retired: the trivia-table spec says a comment in a gap between two of the owner's own tokens goes to no side, while here it is seated on the nearest child.
- **Rust token trees take the options too** (2026-11-17, "Accept: token trees take the options too"). A token tree's members are slot content and the gaps between them are ordinary gaps; no fact keeps them as the source writes them. The options never merge two tokens. What can change in an edited or snapshot render is whether two adjacent punctuation tokens touch, which only a procedural macro can observe; an untouched macro call renders as its source bytes.
- **Comment work is gated on the language having trivia that isn't whitespace** (2026-11-20: "We should honestly gate stuff on existence of non-whitespace trivia"; "It shouldn't be hardcoded to regex - it should language level flag generated based on the existence/absence of non-whitespace trivia"). The grammar's model carries the fact, derived once from its extras: a named extra (one with a kind of its own, such as a comment or python's line continuation) is trivia that isn't whitespace. Codegen emits the fact into the grammar's generated code. Work that exists only for a placed entry (placing comments at parse, finding a list's edge item) runs only for a language that has such trivia, or for a tree that holds an `ERROR`, which the root's error fact from the parser already says. So regex, whose only extra is a line break, does none of it for a tree without an `ERROR`. Nothing keys on a grammar's name.
- **A render stops looking for entries once none is left** (2026-11-20: "render should never look up the placer if there are no comments, and it should keep a decrementing counter of the number of comment rendered, so when it reaches 0 it stops checking"). The parse counts the entries it places, comments and `ERROR`s, and the store holds that count with the read's sides; a write that gives a read's node a side adds to it. It is the store's count of what it holds, so it is node data, not a parse side channel. A render of a read that holds no entry never looks up a side or a list's edge item, and a render that has passed the last entry it can reach stops looking. A render never stops early: an entry read twice, or a render of a subtree that leaves entries outside it, must not cause a later entry to be dropped. Arena storage only; object storage, whose placement is deferred, keeps the language gate.
- **A regex pattern's line breaks are trivia** (2026-11-17): the regex grammar declares `extras: [/\r?\n/]`, so an edited pattern takes its gaps from the options like any other.
- **After a line-terminated extra a gap breaks the line,** whatever the options' arm for it, decided by the kind's line-terminated fact on the model and never by the comment's text (2026-11-17, brainstorm's call on a bug the stored whitespace had hidden: an entry added after `b # comment` rendered inside that comment).
- **An empty statement stays on its predecessor's line** (2026-11-19, "Keep it on the line"). A list item whose kind spells nothing but its terminator, an empty statement, takes no line break before it, whatever the options' arm for the list's gaps. So an edited rust `const { 1 + 3 };` and typescript `declare module Foo.Bar { … };` keep the `;` where master does. The model decides which kind that is, never the kind's name or text, and the same rule holds in every grammar.

## The end state

- An untouched parsed node is written as its source bytes, as today.
- A gap that a rebuilt parent writes comes from the render options. The source's whitespace there is not consulted.
- Comments and other extras are placed onto their owners during parse and kept. A parsed node's sides are read the same way a built node's are.
- No whitespace run, excess or baseline is computed for a parsed tree, in either storage. No per-tree placement state exists, and no render places anything.

## Comments at parse

- **The rule is unchanged.** An extra's owner is the smallest node holding both tokens round its gap. An entry that starts on the previous token's row trails the child before it; the rest lead the child after; with neither beside it, it is the owner's `inner`; a list passes it to the item.
- **Nothing under an ERROR or an extra is placed.** An ERROR is an entry written as its source text, so an ERROR or comment inside it is part of that text and lands in no side. `case *x,:` parses to an outer ERROR holding an inner ERROR for `:`; only the outer one is placed.
- **A source that is wholly an ERROR.** The root is the ERROR and nothing is above it, so the rule above does not apply: its text is one entry on the root's own `inner`, with no in-line run either side. Without it such a source would render empty once a render reads only the store.
- **When.** In the hydration walk. The walk meets each extra between its siblings in document order with their rows in hand, so it needs no rank, no token walk and no navigation. This assumes the parser attaches an extra as a child of its gap's owner (an extra never begins or ends a node). The parity test of step 1 proves it on every fixture; where one disagrees, the walk hands the extra up or down to the owner by the two tokens' spans, which it holds.
- **Where.** In the held-sides store, under the key a parsed node's written side already uses. A parse-placed side and a caller-written side of the same node are then one entry in one store, read by one path, and a write replaces the entry. The store's contract changes with it: written trivia was an overlay over what placement assigned, and with no placement there is nothing underneath.
- **The entry's form is the built one.** A placed comment or ERROR is stored as a pointer to its own record, the entry a built node's side holds when a parsed comment is written onto it, and the render writes that record's source text. No coordinate is stored in a side. This follows the arena design: "A parsed node uses the built node's address-keyed paths where one exists: written sides, the render entry, cell and side-record reads, counts." Two consequences, both making a parsed node match a built one:
  - An ERROR does not keep the in-line whitespace beside it; the options write that gap, as they do for a built node holding a parsed ERROR. That holds where the source touches too: typescript's `let x: +4`, whose `+` reads as an ERROR, rebuilds as `let x: + 4`, equally unparseable, in both storages, and the snapshot census lists it (the maintainer, 2026-11-20: "Accept the entry") until corpus loading skips that upstream entry for its local replacement, when the listing goes. Inside a string an ERROR's gaps are the options' as well.
  - A line continuation (python's `\`) is placed (the maintainer, 2026-11-16: "it should be placed"). In the grammar it is a named extra, `line_continuation_newline` and `line_continuation_nul`, declared beside `comment`, so it has a record of its own and is not the whitespace pattern this design stops keeping. Its entry is a record pointer, as a built node's side holds one. The space before the backslash is a gap, so the options write it: one space before a line continuation, for built and parsed nodes alike (the maintainer, 2026-11-16: "Record pointer, fix the gap"). `total = a + \` then renders with its space under a rebuilt parent. Master does not do this today. A built line continuation renders `a +\`; leading a statement it joins the two statements; on a file's first line it is dropped. A parsed one written onto a built side is a coordinate whose edges are the whitespace of the source it was taken from, so it renders the same way when that source was tight and with a space when it was not. That is the carried whitespace this design removes. The hydrate-at-parse branch moves parsed entries onto the built form and inherits the built form's defect. The fix is in the shared write, for built and parsed entries alike, on master first; the branch's read-record write then goes through the same leaf write.

  What the options write around a line continuation, whatever the entry came from:

  | where it sits | renders |
  |---|---|
  | leading a statement | `x = 1` ⏎ `\` ⏎ `y = 2`: the statement's line break is kept |
  | after an operator | `a + \` ⏎ `b` |
  | trailing the left operand | `a \` ⏎ `+ b` |
  | after an opening bracket | `f(\` ⏎ `a)`: the bracket's tight edge wins (the maintainer, 2026-11-16: "Bracket stays tight") |
  | a file's first line | `\` ⏎ `x = 1`: nothing is dropped | Its text holds its own line break, so a rebuilt parent neither joins nor splits the statement. It stays an extra: it may sit between any two tokens, so no rule can hold it in a slot.
- **Line breaks beside a comment.** Today a comment carries no line fact of its own: whether it sits on its own line is held by the whitespace runs beside it, which this design deletes. Parse therefore writes the side as a caller writes one on a built node: the comment's entry, with a line-break member before or after it where the source has a break there, and nothing where it doesn't. One representation serves parsed and built nodes and no field is added. Without it `// own line\nlet y` could render as `// own line let y`; this is not style.
  - **The gaps outside a side are its owner's parent's,** written from the options, except where the side's leading layout says otherwise, as the blank-line fact already does. A leading side whose first entry starts on the previous token's row holds a `space` layout value ahead of it, so `a: string, // c` ⏎ `b` keeps `// c` on `a`'s row when the list is rebuilt. A gap's line break that follows text which already ended its line (a line comment's own line end) is that same break, not a second one, so `fn f() {} // c` ⏎ `fn g() {}` gains no blank line. The writer applies this to built and parsed nodes alike. A node rendered on its own starts with its first entry, not with the layout before it (brainstorm's call, 2026-11-19, on what the step that reads only parse-placed sides showed). To verify on the probe: what the options write after a built node's line comment that has no member beside it. A line comment must never be followed on its line by code, whatever the side holds.
- **Release.** A parse-placed side is node data with the lifetime of its record. A read's records are freed with the engine's arena, and the store with them; neither is released earlier today. When read records become individually releasable, their entries are dropped in the same callback that drops a built record's sides. To measure on the probe: retained bytes per parse on a comment-heavy file, since they stay as long as the records do. The maintainer has since ruled that this is not the end state: "parsed node release vs. built node release really ought to be no different" (2026-11-16). One release behaviour for both is designed separately, proposal before code; this design only requires that a parsed node's store entries go in the same callback that releases its record.
- **Cost.** Extras are about 0.1% of record words on the paired corpora (46, 9 and 43 extras in the python, typescript and rust corpora). Parse time and retained bytes on a comment-heavy file are measured on the probe.

## The blank-line fact

A list item after the first that follows a blank line in the source carries that fact as the layout kind matching the run: `blankline` for one blank line, `double_blankline` for two or more. A rebuilt list writes before such an item the blank lines its kind spells, one or two, so `x = 1\n\n\ny = 2` keeps its two blank lines and `x = 1\n\n\n\ny = 2` renders with two. Where an options arm also rules that gap, the gap takes the larger of the two (maintainer, 2026-11-17: "The larger of the two"): python's `preference('double_blankline')` after a `def` or `class` keeps its two blank lines before the next statement whether or not the source had any, and `import a\n\n\nclass A:` keeps its two from the entry. A source with blank lines never renders fewer than the same source without. The fact holds only while the item keeps its source neighbour: the edit spec's rule for gaps after an edit governs a changed edge (an edge whose neighbour changed drops its edge runs, and `insert`, `removeAt` and `move` give the list's spacing around the item), so `a\nb\n\nc` rebuilt as a, c, b renders `a\nc\nb`, and an attribute inserted before a set-apart function gets no blank line between itself and the function.

**Where the fact is held (maintainer's direction, 2026-11-17).** A blank line "is just the enum value from the layout enum", and a side that holds only that should not pay a store row (measured: about 48 bytes of row for an 8-byte entry, for built and parsed nodes alike, and 2.6–5.9% of arena parse as first built). The direction: "maybe it's that layout up until the first non-layout trivia goes on the node, and then comments + any trivia after that go on the table". So a side's leading layout is held on the node's own record, and the store holds a side from its first comment, ERROR or text entry onward, with any layout after it. The order is kept without a merge, since what is on the node always comes first. Costed and approved ("Go: layout in the record's spare bits, row kept for comments"). Measured before: a side holding only a blank line costs about 100 bytes requested for a parsed node and 124 for a built one, and such sides are 15–32% of all stored sides. The form: a parsed or built record holds its sides' leading layout run in spare bits of its header word, three bits a layout value (none, then the six gap kinds in rank order), up to five values (leading 3, trailing 1, inner 1); a leaf item holds it in its holder's run entry; the store row holds what follows, in order. A write splits a side at its first entry that is not such a layout value; a read decodes the record's codes and appends the row. "The larger of the two" is the larger code. A row with one entry holds it inline and allocates no list. A blank line before a unit item is not held, since a unit owns no side. Moving a row's entries into the engine's chunks waits until built chunks can free a sub-range.

**Form (maintainer's direction, 2026-11-15: "layout entries can be added to $trivia maybe we ought to use the trivia table here as well").** The fact is a blank-line layout entry, the first entry of the item's leading side, in the same store as its comments: the entry a caller already writes through `$trivia` on a built node. A built item can then carry it too, and one read path serves both. A flag on a parsed record's run entry was the earlier form; it costs no storage but only a parsed node could hold it. The cost of the entry form (a store entry per blank-line gap between list items) is measured on the probe before step 2 is built: gaps per corpus, parse time, retained bytes. The points below on the flag's storage apply only if the measurement sends this back to the flag.

- It is set only between items of a list slot (statements, members, arguments). The gap after an opening token and the gap before a closing one belong to the tokens and come from the options, so a list's first item never carries the flag (maintainer, 2026-11-15: "Between items only").
- With leading comments, the flag is measured from the previous item's end to the start of the item's first leading entry, so `a();\n\n// c\nb();` keeps the blank line above the comment. A blank line between a leading comment and its own item (`// d\n\nc();`) is kept too: the comment holds a blank-line member after it where the source has one, as it holds a line break, of the layout kind matching the run as an item's fact is (`/** Outer */\n\n\n/*! Inner */` keeps its two blank lines), so a file's header comment stays apart from its first item (`// Copyright …` ⏎⏎ `use a::b;`) and so does `// d` from `c();` (the maintainer, 2026-11-20: "Keep it after a comment", replacing the 2026-11-15 "Above the comment only", once a rebuilt root was shown to join a file's header to its code).
- It adds no stored word: a record child's run entry has spare bits, and a slot-held row uses a spare bit of an existing count.
- Parse does one scan per gap between list items, of the bytes between them, from the spans the walk holds. (Corrected 2026-11-17: the walk does not hold row numbers; it reads positions only for extras and ERRORs, and reading two positions per child costs more than the scan. The same scan serves the lookup both storages share, whose items hold bytes, not rows.) Nothing reads the flag unless the list is rebuilt.

## Indentation

One rule, for every grammar:

- A line a rebuilt parent writes is indented with the source's inferred indentation unit. The unit is inferred once per source, for every grammar, and kept when it differs from the engine's. To verify on the probe: that every line a rebuilt parent writes uses the inferred unit, with no deviation in play.
- An untouched slice moved to another depth is re-indented from its first line: each later line that starts with the first line's source indentation has that prefix replaced by the unit times the new depth. A later line indented less than the first, a line that begins inside a token, and a blank line keep their bytes.
- In a grammar that has depth tokens, the slice's net depth move is applied to the writer. Whether a grammar has depth tokens is a fact of the grammar, never its name.

The second and third exist in the engine today and stay.

What goes is the writer's excess: extra indentation levels the source opened beyond the template's depth, restored per frame. It is a stored whitespace deviation. It matters only when the over-indented thing is itself a child the rebuilt parent places: that child is re-indented to unit times depth. An over-indented continuation inside an untouched statement (`x = g(\n            1,\n            2)`) is part of a slice and keeps its bytes. In a rebuilt one, a line a line comment breaks continues at the statement's own depth, since a continuation's hanging indent is excess and no layout fact holds it: `let // c⏎    x = 1;` rebuilt with `x = 2` writes `let // c⏎x = 2;` (brainstorm's call, 2026-11-20, from the rule above). To verify on the probe: a measured example of the first case, and that no depth-token grammar relies on excess for correctness.

## What the output looks like

Only gaps a rebuilt parent writes change.

| case | source | today | after |
|---|---|---|---|
| rebuilt root, blank lines between untouched statements | `const   x  =  1;\n\n\nfoo( a,b );   // trail\n// own line\nlet y = [1,2,\n   3];\n` | `const   x  =  1;\n\n\nfoo( a,b ); // trail\n// own line\nlet y = [1,2,\n   3];\n` | the same |
| rebuilt statement over untouched children | `const   x  =  1;` | `const x  =  1;` | the same |
| rebuilt block | `{\n\n    a();\n\n\n    b();  // why\n}` | `{\n\n    a();\n\n\n    b(); // why\n}` | `{\n    a();\n\n\n    b(); // why\n}` |
| rebuilt function over a body indented by eight spaces | `def f():\n        x = 1\n\n        return x  # done\n` | the function's bytes, unchanged (the file's final `\n` is the root's) | the same |
| a call rebuilt over an untouched broken argument list | `f(\n  a,\n  b,\n)` | `f(\n  a,\n  b,\n)` (the list is a slice) | the same |
| a broken argument list rebuilt (one argument edited) | `f(\n  a,\n  b,\n)` | `f(\n  a,\n  b,)` (the break before `)` is already lost) | as the options write that list; the trailing comma is kept if the separator preference keeps it (to verify) |
| comments between list items, parent rebuilt | `a();\n\n// c\nb();\n// d\n\nc();` | byte-identical | the same |
| trailing comment on the same row | `b();  // why` | `b(); // why` | the same |

## What is deleted

All of it is shared engine code, so both storages change together and no difference between them is introduced.

- The baseline measure, whole: the recorder and its tallies, the recorded render of a region, the gap and depth lookups behind it, and the recording render path of each storage. It exists only to say what the options would write at a gap, so that a deviation can be stored.
- Layout runs, run excess and the deviation lookup; whitespace a parse derives as a deviation from the options. A whitespace member a caller can write on a built node stays, and is the form parse uses for a line break beside a comment.
- The whitespace half of list slots (the per-side class). The separator half is a preference choice and stays, compared with the options directly.
- Per-tree placement state, its lock and its published tables in object storage, and the per-call placement table in arena storage.
- The placer.
- To trace before deleting: the depth anchors and level lookups, to separate what served whitespace deviations from what the indentation rule above still needs.

The JavaScript surface that carries layout (the snapshot and slot layouts of a read) shrinks or goes. Those are API rows, listed for the maintainer once the deletion is drafted.

## What the gates will show

- **Untouched trees.** Read then render is still the source bytes, so byte round-trip rows do not move.
- **Rebuilt trees.** Read-render-parse rows compare trees, not bytes, and hold if a comment keeps its side and its line fact.
- **Tests that pin preserved whitespace under a rebuilt parent** change by design. They are counted and listed with the deletion; each is shown to pin the superseded behaviour before its expectation changes.
- **Benchmarks.** Expected, not measured: a first render loses the placement share in both storages; arena storage stops re-placing on every render; a render of an edit result loses the baseline's recording render. Parse gains a comparison per list gap and work proportional to the number of extras.

## Order

1. The parse-time comment placement, with the lazy placer still present and still the only thing a render reads. A side the store holds masks the placer's side, whitespace runs included, so a parse-placed side is not read by a render until step 3; this step changes no output. A parity test compares, per fixture, node and side, the extras and ERRORs the placer assigns (kind and span, in order) with what parse stored, and each extra's line breaks in the source with the members written beside it.
2. The blank-line flag.
3. Switch a render to the parse-placed sides, delete the baseline, deviations and runs, and retake the expectations the ruling changes, in one change.
4. Delete the placer and per-tree placement.
5. A census of what still reads the plain token rows (6% to 17% of record words). Whether they can go is a separate decision.

Each step is measured on a paired run against master's arena on the pinned toolchain.

## What this does to work in flight

- The fix that stops an edit copying a parsed node's sides eagerly is unaffected.
- The hand-off of sides from a render gets smaller (comment sides only) and is re-measured.
- The cached-position navigation change was measured on placement, and is re-measured against the readers that remain before it lands.
- The walk-order stamp on records is dropped.
- The per-call scratch allocator spec still applies to per-call navigation tables. Its allocation count is taken after step 4, since the placer was the largest per-call allocator.
- A full per-call reformat and style inference from sources stay parked.
