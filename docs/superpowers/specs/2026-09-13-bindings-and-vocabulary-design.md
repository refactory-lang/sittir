# Bindings, the vocabulary and the portability API

**Status:** Design spec. Supersedes the earlier "Role Interfaces & `roles.scm`" design.

See §4.5.

## 1. Two APIs, and the map between them

sittir has two construction surfaces. The low-level surface is shaped by each grammar. The portable surface is shaped by the vocabulary, which is the same for every language. The bindings say how one grammar realizes the vocabulary, and the generator turns them into **the map**: the only artifact the bindings produce.

| layer | what it is | source of truth | made by |
| --- | --- | --- | --- |
| **low-level API** | one builder per grammar kind, with exact kinds and kind ids; a strict form that coerces nothing and a loose form that coerces each slot's input by the slot | `grammar.sittir.ts` and the tree-sitter grammar | generated |
| **vocabulary** | the portable API: semantic kinds shared across languages, their refinements and flags, the synonyms their names take (§4.2), members by role, the structures that satisfy them (§8) and the nodes a portable read returns (§9) | `packages/types/src/vocabulary/` | authored |
| **features** | which vocabulary kinds, members and flags a language has (§4) | `packages/types/src/vocabulary/features/`, a folder per feature, and one composition per language | authored |
| **bindings** | which grammar node is which vocabulary kind, which slot is which member, which token or node states which fact | `packages/<grammar>/bindings.scm` | authored |
| **the map** | the bindings resolved against the grammar's slot model and the vocabulary's declarations: for each vocabulary kind the factories that build it, for each member the slot it lands in, and for each flag the token or kind whose presence it is; for each grammar kind the vocabulary kind it is | generated with the grammar package (§5) | generated |
| **a language's portable interfaces** | one interface per vocabulary kind the language claims, generated as its low-level interfaces are, with each member spelled out as the language realizes it; each extends its vocabulary interface over the language's context, so one that does not match the vocabulary is a compile error in the grammar package. The portable builders, nodes and guards are typed against them, as the low-level ones are against the low-level interfaces | the vocabulary and the map | generated |

- **Each surface is an engine.** `createEngine(lang)` gives the low-level surface and `createEngine(lang, { api: 'portable' })` the portable one, through the reserved `ApiSurface` option. The portable engine's `build` builds structures (§8), its `parse` reads portable nodes (§9), and its `render` renders them directly, dispatching on `$type` (§9). A node moves to another engine only through the target engine's `attach` (§9).
- **The vocabulary is a designed API, not a derived one.** Its interfaces are written by hand, under the rules of §3. The bindings never generate them. The inventory checks the map against them (§10), so a binding that names a member the vocabulary lacks, or a vocabulary member no binding of a composed language reaches, is a diagnostic.
- **The portable surface builds through the low-level loose surface.** A structure's member is routed by the map to a slot, and the value is handed to that slot's loose coercer. Coercion therefore has one table: the loose contract (`docs/factory-surface-issues.md`, "The contract: loose = strict + six coercions"). The portable layer adds no coercion of its own beyond what §8 lists.
- **A fixed word is a kind at the low level, and looks like a slot only in the portable layer** (the user, 2026-11-08). The low-level model folds a field whose content is one fixed word (rust's `crate`, `self` and `mut`, python's `__init__`, typescript's `this` and `constructor`), so no low-level slot holds only fixed text. Where the word tells forms apart, the low-level API carries it as a variant or a kind (rust's `mut_pattern` beside its pattern), and the portable layer projects a slot-like member from that kind.
- **A binding is bidirectional.** A constructive pattern, one that fixes every node it would emit, serves reading (§9) and building (§8). Only a predicate outside the invertible subset (§7) is read-only, and the inventory names it.
- **Coverage of the portable surface** is measured by a validator lane that parses a corpus file with the portable engine, builds every node again from its members, renders and re-parses (§10).

## 2. `bindings.scm`

One file per grammar package, `packages/<grammar>/bindings.scm`, written in tree-sitter's query language. It states every role fact for its grammar; nothing else does.

### 2.1 Form

- **Sixteen sections in a fixed order,** identical in every file, an empty section left visible where a grammar has nothing: `file`, `declaration`, `statement`, `clause`, `argument`, `element`, `expression`, `pattern`, `type`, `literal`, `identifier`, `modifier`, `attribute`, `comment`, `keyword / punctuation`, `unclaimed`.
- **One claim per line,** the parent before its refinements, refinements in the order of the vocabulary.
- **Kind claims** are dotted captures on nodes: `(binary_expression) @expression.binary`. A single-segment capture alone on a pattern's top node claims the namespace's root kind: `(identifier) @identifier`.
- **A claim may name a kind the bindings mint** (an alias or a visible clone); it is checked as the kind it is minted from.
- **A text piece is a kind.** A node that carries only text is claimed as a kind of its own: a string's text between its escapes and interpolations is `literal.string.text` (`(string_fragment) @literal.string.text`), a comment's text after its marker is `comment.text`, and a regex's pattern and flags are `literal.regex.pattern` and `literal.regex.flags`. Like `literal.string.escape`, each extends the kind it sits in, so a text piece also reads as that kind, and the slot that holds it is a member of its parent typed by its kind.
- **Member captures are constructive and exhaustive.** A claim's members and the facts it routes are exactly its single-segment captures on nested nodes and on tokens. Every non-layout slot of a claimed kind is captured, as a member, as a fact or as `@dropped`, and the inventory fails on a slot that is none of them; a dropped slot is not a member and has no route in the map.
  - The capture's name is the converged member name (§6), whether or not the upstream field already spells it: `(class_definition superclasses: (_)? @bases)`.
  - A deep capture reaches through a wrapper to the node that matters, so nesting artefacts (`content`, body wrappers, hidden arms) exist only where a capture names them: `(class_declaration (class_heritage (extends_clause (_) @extends)))`.
  - A capture on a token names the fact its presence states: `"async" @async`. A second single-segment capture on a node names the fact that the node's kind states in the slot the first capture names: `name: (private_property_identifier) @name @privateName` states `privateName` where the name is a private name, and a build that states `privateName` builds a private name.
  - **A leaf has no slots.** No claim puts a member on a leaf: its text is the node's `$value` (§9), and a member that holds a leaf is a slot of its parent. An identifier is a leaf, so an identifier kind has no member either, not even `content`, the root's or a refinement's. A compound identifier is not a leaf, so its node-holding slots stay: rust's `scoped_identifier`, typescript's `nested_identifier` and python's `dotted_name` keep the nodes they hold. A bare identifier in a role slot stays an identifier; the slot names its role. Its kind does not change, so neither a claim nor the grammar bindings pretend it does: a python or lambda parameter list, a rust closure's parameters and a typescript arrow's parameter hold it as an item typed by a union, `Parameter | Identifier`. A grammar kind that only names a role claims `identifier` too: `type_identifier`, `field_identifier`, `property_identifier` and `private_property_identifier`, typescript's label (`statement_identifier`), and the shorthands, typescript's `shorthand_property_identifier` in an object and `shorthand_property_identifier_pattern` in a pattern, and rust's `shorthand_field_identifier`, the name of a `field_pattern` with no `pattern` in `let Foo { a } = x` (§6, rule 8). Nothing but the slot tells a type's name from a value's, the holder's `privateName` flag tells a private name (§3.3), and in a build a bare string fills the slot's own leaf kind (§8). An identifier refinement is a fact of its own, never a role.
  - A capture on a nested node is a member of the top claim, reached along the pattern, anchors (`.`) included: python's docstring is `(function_definition body: (… (block . (… . item: (expression_statement (string) @doc)))))`, the function's `doc`, the string that opens its body. The string stays a `literal.string`. A claim sits on a nested node only under an envelope, which sets the fact it names on the element it unwraps (§9).
  - A captured node finds its slot by its field, else by its kind, else by position: an unfielded wildcard names the first node slot after the slot of the node pattern before it, so `(index_expression (_) @object (_) @index)` names both slots in order and a token before a wildcard does not count.
  - The slot model types a captured member (kinds, multiplicity, requiredness) and confirms that the capture resolves to a slot; it never adds a member.
  A claim is unconditional, so an optional member named in a claim carries a quantifier (`?`, `*`, `+`) and the claim matches whether or not the member is present.
- **Refinements** are the parent's pattern with a literal fixed: `(binary_expression operator: "+") @expression.binary.arithmetic.add`.
- **A claim names a fact, never its form.** A fact with no data is a refinement or a flag, and which one is the vocabulary's declaration (§3.3), never the bindings'. A claim names the fact by its path, the owner's path and then the fact: `(method_definition accessor_kind: "get") @declaration.member.property.getter` names `getter`, and `(abstract_class_declaration) @declaration.type.class.abstract` names `abstract`. A single-segment capture names a member or a fact of its claim's kind, as `"async" @async` does. The generator resolves each name against the vocabulary's declarations: a path segment to a kind or to one of its flags, and a single-segment capture to a member or a flag (§5.2). The bindings never say which form a fact takes, so a fact the vocabulary reclassifies changes no line of `bindings.scm`. A name that resolves to nothing the vocabulary declares is a diagnostic. A segment of a path, and a flag, may be written as a synonym (§4.2), which the reader canonicalizes: `@declaration.parameter.this` claims `declaration.parameter.receiver`.
- **A fact a decorator spells has one claim per fact** (`@property`, `@x.setter`, `@override`), never one per order of combined decorators. The read takes the decorator out of `decorators` and records the fact under `$at`, keyed by the fact's name, with the decorator's index and its spelling. A rebuild restores both, so `@typing.override` rebuilds as `@typing.override`: the spellings depend on different imports, and normalizing one can raise a NameError. A fact set fresh takes the first spelling in bindings order, `@override` (the user, 2026-11-07: "Restore what was read (Recommended)"; on the name `$at`: "Should it matter?").
- **A value spelled by a node of its own is claimed on that node and on each owner.** The node claims the value's kind, by its path beneath its axis's root: `(accessibility_modifier "private") @modifier.visibility.private`. Each owner claims its refinement for the value with a pin on that node, after the owner's own claims: `(method_definition (accessibility_modifier "private")) @declaration.member.method.private`. The read tests the pinned node, which tells the owner's slot that holds it, so no capture routes that slot. A member the value adds is captured on every claim of the value, the value's own and each owner's (§3.3).
- **Content-derived kinds** are predicate claims: `((function_definition name: (identifier) @name) @declaration.member.constructor (#eq? @name "__init__"))`. A kind is claimed wherever content, position or finite text determines it, whether or not the grammar has a node for it; the grammar's kind list is the floor of coverage, never its ceiling.
- **Template regexes** name every hole: `(#match? @name "^__(?<stem>.*)__$")`. A bare hole is an error (§7).
- **A container that wraps one node** is never claimed. A pattern that captures the wrapped node as `@element` assigns its other captures to the kinds its element slot names directly, never to a kind behind a supertype or a further container: `(decorated_definition (decorator)* @decorators definition: (_) @element)` gives `declaration.type.class` and `declaration.function` their decorators, and `(attributed_field_declaration (attribute_item)* @attributes (_) @element)` gives `declaration.member.field` its attributes. A wrapper that carries information of its own is claimed as a kind, not declared a container: one whose element slot names no directly claimed kind (`declare global {}` is a `declaration.ambient`, not a declarable block, and a labeled statement is a `statement.labeled`), and one with a slot beside its element (`Iterator<Item: Copy>`'s argument is an `element.type_argument` that keeps its `constraint`). A container drops nothing silently: every slot besides its element is captured, or marked `@dropped` with its reason where a ruling keeps it out (`((attributed_argument (attribute_item)* @dropped (_) @element) (#set! reason "…"))`). The inventory reports a container capture with no direct target, and a container slot left uncaptured, and fails.
- **Token classes** are captures in the `keyword / punctuation` section: `["if" "else"] @keyword.conditional`, `["(" ")"] @punctuation.bracket`. They are classes for highlighting, not vocabulary kinds, and the map carries them in a table of their own (§5).
- **Unclaimed** kinds are stated in the file with a reason, never in a comment: `((line_continuation) @unclaimed (#set! reason "layout token"))`. The directive is for parser artefacts. Any other unclaimed kind is debt, and its count is a ratchet that only falls.

### 2.2 Seed and override

- **Two files per grammar.** `bindings.seed.scm` is generated (`sittir tool bindings-inventory --seed <grammar>`), committed, never hand-edited, and regenerated when the grammar package bumps. `bindings.scm` is authored and overrides it. The two compose by one rule: a kind claimed in the override drops every seed claim on that kind, so the override is either the whole story for a kind or silent about it.
- **The seed comes from the upstream queries and the slot model.** Each grammar package vendors tree-sitter's `queries/tags.scm` and `queries/highlights.scm`.
  - Tags decide claims and the `@name` capture, through one table shared by every grammar: `definition.class` → `declaration.type.class`, `definition.function` → `declaration.function`, `definition.method` → `declaration.member.method`, `definition.interface` → `declaration.type.interface`, `definition.module` → `declaration.module`, `definition.macro` → `declaration.macro`, `definition.constant` → `declaration.constant`, `reference.call` → `expression.call`.
  - Highlights decide the token classes (`@keyword`, `@operator`, `@punctuation`), and `@property`, `@type`, `@constructor`, `@comment`, `@string` and `@number` name the token or leaf under a claim.
  - The slot model expands every remaining slot of a claimed kind into a candidate capture, named under the name rules (§6). This is what makes exhaustive member captures cheap to write: the seed spells them, and an override restates only the kinds whose members it changes.
  - Every kind the tags never mention is listed in the seed's `unclaimed` section with the reason `unseeded`. That reason exists only in a seed: an authored file states a parser artefact or claims the kind.
- **The seed is coarse by construction.** Tags file rust's struct, enum, union and type alias all as `definition.class`; the override splits them. Tags cover a tenth of a grammar's claims and the model expansion is the bulk; the override is where the vocabulary's judgement lives. Locals and injections carry nothing the bindings need.
- **A seed is never the vocabulary's source.** It lowers the cost of a new grammar and of a grammar bump, nothing else.

### 2.3 What is never claimed

- **Grammar supertypes.** Namespaces are the vocabulary's supertypes (§3.2); a grammar union maps to its members' claims.
- **Containers.** A list holder with no members of its own (`argument_list`, `parameters`, a class body, a use list) is bound through its elements: by the elements' own claims where they have them. A bare identifier in a role slot stays an identifier, and the slot names its role (§2.1): a bare identifier in a python parameter list is an item of the parameters, typed `Parameter | Identifier`. A name alone in a typescript enum body is not bare: the grammar gives it a node, `enum_body_element_name`, the body's name arm lifted with a `name` slot, so it is claimed as a kind, `declaration.member.enum_member`, beside `enum_assignment`. The parser's kinds decide, here as for a bare identifier. A value in argument position supplies nothing but itself, so there is no `argument` role kind for it: a positional argument is the expression.
- **Layout.** Terminators, automatic semicolons, quote tokens, separators, indentation. These are render options and never members. The grammar's options block names the terminator and semicolon slots, every separated list's separator slot carries the compiler's separator name, and a delimiter token the options do not reach is unclaimed with its reason, so a slot holding only unclaimed kinds is layout too.

**Totality** is measured on the meaningful kinds: every visible kind that is not a container or a grammar supertype is claimed or explicitly unclaimed.

## 3. The vocabulary

### 3.1 Namespaces

Fourteen top-level namespaces. Eleven are semantic: `file`, `declaration`, `statement`, `expression`, `pattern`, `type`, `literal`, `identifier`, `modifier`, `attribute`, `comment`. Three are role namespaces, for pieces that belong to a construct without being one:

- `clause`: pieces of a statement or declaration: `else`, `catch`, `where`, a type annotation, a trait bound, a match arm, import and export specifiers;
- `argument`: pieces of a call that are not expressions, such as python's keyword argument;
- `element`: pieces of a composite expression that are not expressions: a pair, a spread, a struct field initializer, a JSX attribute, a token tree.

Keyword and punctuation classes are not namespaces (§2.1). The root of a file is `file`, the namespace's root kind, claimed by python's `module`, typescript's `program` and rust's `source_file`; a module declared inside a file (`mod`, `namespace`) is `declaration.module`. A file is the neutral term: a C or C++ file is no module.

Placement is **semantic namespace first, language qualifier as the refinement**: a macro invocation is `expression.call.macro`, a JSX element `expression.jsx.element`, a `where` clause `clause.where`. A language-specific leaf is assignable to its shared parent, so cross-language reading sees rust's macro invocations as calls; only cross-language building fails, at the leaf the target lacks.

### 3.2 Path and kind-set

Two relations, kept apart:

- **The path** is how a kind is addressed: `expression.binary.arithmetic.add`. A prefix is a kind-set, the union of every leaf beneath it, **strictly**: everything under `expression` is an expression. That rule is what put pairs, spreads and keyword arguments in the role namespaces, and enum members beside enums (`declaration.member.enum_member`) rather than beneath them.
- **Kind-set membership** is what a member admits. A namespace's kind-set is its `Any`, what lies beneath its path in a language (§3.4, §4.5): the kinds beneath the path, which every language with the path has alike, and the alias paths beneath it, which a language has by its composition.
  - **An alias path places a kind from elsewhere beneath a namespace** that admits it at every one of its slots in a language: `identifier` beneath `expression` and `pattern` in every language (`expression.identifier`, `pattern.identifier`), and rust's `if` beneath `expression` in rust only (`expression.if`). An alias path is the namespace and its target's last segment, `expression.if` → `statement.if`, and it covers its target and what lies beneath the target. A base alias a language lacks at a slot is narrowed there by its map (§4.5). A path that is already a kind or a namespace is no alias, and the generator reports it.
  - **An alias is declared like a kind,** in the base or in the feature that owns it, with one owner (§3.4, §4.5), and a language holds the aliases of what it composes. The guard and the type come from that one source: `is.expression` holds for rust's `if` and not for typescript's, and `V.Expression.Any<G>` holds `V.Statement.If<G>` over rust's map and not over typescript's.
  - **An alias names the narrowest target the namespace admits.** Rust's expression kind-set holds its block-like statements through an alias each, `expression.if`, `.loop`, `.match`, `.block`, `.break`, `.continue` and `.return`, never `statement`, which would admit a declaration as an operand.
  - **A slot that admits more than its namespace's `Any`** takes the union at the slot, named `AnyWith…` where two or more slots share it (§4.5).
  - **A language's map narrows each kind-set to its grammar's rule for it** (§4.5): a grammar union maps to the claims of its members, and one whose members are not all claimed admits its claimed members and records the rest as unmapped (§5). The inventory checks the rule against the aliases: it lists each kind from elsewhere the rule admits that no alias the language holds covers, and each alias the language holds that the rule does not admit, which the map narrows.
  - Inclusion is a DAG, through the aliases too, and the generator checks it for cycles.
  - **A kind-set that slots share is named, and slots are typed by its name** (§4.5).

The path relation is unchanged: what lies beneath a prefix as a kind is still strictly what the path says, and an alias is no kind. A node carries one claim. Rust's `if` is claimed as `statement.if`; that it lies beneath `expression` in rust is its alias, not a second claim.

### 3.3 Refinements, flags and members

A fact the vocabulary states about a kind takes one of three forms: a refinement, a flag or a member. Which one is the vocabulary's declaration: its authors decide it, informed by the grammars, and declare it on the fact (§3.4). The bindings name a fact the same way whatever its form (§2.1). The generator maps each claim onto the fact the vocabulary declares, and never infers a fact's form from a grammar's shape: a choice, a keyword or a slot's arity decides nothing (§5.2).

- **A refinement narrows, never widens.** It may add members and narrow a member's kind-set; it never makes a parent's required member optional, and it never admits a kind its parent does not.
- **A fact that picks one of several values is a refinement axis.** Its values are kinds in the namespace path, and a node's path names the value it has. A method's visibility is `declaration.member.method.public`, `.public.internal`, `.public.restricted`, `.protected` or `.private`; a property's accessor is `declaration.member.property.getter` or `.setter`; a rust receiver is `declaration.parameter.receiver.owned` (`self`, `mut self`), `.reference` (`&self`) or `.reference.exclusive` (`&mut self`); a binary's operator is `expression.binary.arithmetic.add` and its siblings. No member holds an axis's value, so the portable surface has no enumeration type. A node whose source states no value of an axis is its unrefined kind: a method that spells no level is `declaration.member.method` (§4.3), and a typed receiver (`self: Box<Self>`) is `declaration.parameter.receiver` with its `type`.
  - **An axis many owners share states its values once,** as kinds beneath the axis's root, nested where one value includes another: the access levels are `modifier.visibility.public`, `.public.internal`, `.public.restricted`, `.protected` and `.private`. A value's kind declares its `$path` and the members its value adds, and nothing else. The bindings claim a value on the node that spells it (§2.1).
  - **Every owner × value is a refinement kind.** `<owner>.<value>` extends its owner and is named by the value's path beneath the axis's root, one namespace per segment and never flattened: `declaration.function.public.internal` extends `declaration.function.public`, which extends `declaration.function`. It extends `RefinedBy<Owner, Value>`, a mapped type in `utils.ts` (`SubKindOf<Owner> & Omit<Value, '$path'>`), which gives it the owner's members under a `$path` beneath the owner's and the members the value's kind adds: `interface Public<G> extends RefinedBy<V.Declaration.Function<G>, V.Modifier.Visibility.Public<G>>`, and `declaration.function.public.internal` is `RefinedBy<V.Declaration.Function.Public<G>, V.Modifier.Visibility.Public.Internal<G>>`.
  - **A value may add members, each owned by a feature.** `public.restricted` adds `scope`, the ancestor module that `pub(super)` and `pub(in path)` name. `scope` is owned by `scoped-visibility`, which extends `visibility`. The feature writes the member on the value's kind, as it writes a member any kind gains (§4.1): `Modifier.Visibility.Public.Restricted<G> { readonly scope: G['identifier'] }`, in `scoped-visibility`'s folder. `RefinedBy` gives the member to each owner's `public.restricted` refinement, gated as the value's kind has it, and the bindings capture it on every claim of the value: the value's own, `(visibility_modifier_pub (visibility_modifier_pub_scope […]) @scope) @modifier.visibility.public.restricted`, and each owner's, `(function_item (visibility_modifier (visibility_modifier_pub (visibility_modifier_pub_scope […]) @scope))) @declaration.function.public.restricted`. So the inventory finds each route where the vocabulary declares the member, and reads a refinement's members along its value's line as well as its owner's.
  - **A claim captures only what its own fact adds.** An entry inherits the captures of every claim on its grammar kind at its path or an ancestor's, so a claim never repeats a capture that a claim above it on the same grammar kind makes. Rust's impl methods capture `receiver` on the plain `declaration.member.method` claim alone, and a level claim on the same `function_item` captures only what its level adds, `scope` for `public.restricted`. A claim on another grammar kind inherits nothing from it and captures its members itself.
  - **Owner × value refinements are authored.** The feature that owns the axis declares each owner's refinements in its folder, as it declares any kind (§4.1), and `RefinedBy` carries the value's members, so nothing generates them and there is no declaration of the axis itself: its values are kinds, and so are the owners' refinements for them.
  - **Axes are ordered, structural first.** A kind's axes have one order, the vocabulary's: what the construct's shape decides (the signature, the accessor kind) comes before a modifier's value (the visibility). A public getter's signature is `declaration.member.property.signature.getter.public`, and every node has one deepest kind. Flags have no order (below).
  - **A node's refinement changes with `$as`.** `node.$as(<refinement>)` swaps one axis value and keeps everything else. Its details belong to the edit model.
  - **An operator is always an axis value.** No member holds one, wherever it appears: rust's macro repetition is `element.macro.token_repetition.zero_or_more` (`*`), `.one_or_more` (`+`) or `.zero_or_one` (`?`), python's complex-number pattern is `pattern.complex.add` or `.subtract`, and its rest pattern is `pattern.rest`, or `pattern.rest.map` for `**`.
  - **Equality is strict.** `expression.binary.comparison.equal` and `.not_equal` compare without coercion in every language: python's and rust's `==` and `!=`, typescript's `===` and `!==`. Typescript's coercing `==` and `!=` are `.loose_equal` and `.loose_not_equal`, siblings owned by `coercive-equality` (§4.3), so a guard for `equal` never holds for a coercing comparison.
  - **A comparison chain is a form of its own.** Python's `a < b <= c` is one node holding its first operand and a list of comparators, each an operator and the operand after it, so no one value of the operator axis says what the node compares. A comparison with one comparator reads as `expression.binary.comparison.<op>` with `left` and `right`, as rust's and typescript's do. One with two or more is `expression.binary.comparison.chain`, which holds its comparators as links: each link is an `element.comparator.<axis>.<op>`, refined by its operator along the axes `expression.binary` uses (`element.comparator.comparison.less`, `.membership.not_in`, `.identity.is_not`), so the chain's operators are its links' axis values and still no member holds one.
  - **An import's or an export's form is an axis value, and type-only is a flag.** Flow's `import typeof` is `statement.import.typeof`, `export default …` is `statement.export.default`, and `export * from …` is `statement.export.all`. Each value is pinned by the keyword or the `*` that spells it, and an export that spells none is `statement.export`. A type-only import or export sets `typeOnly` whatever its form, since the form and the `type` keyword combine: `export type * from …` is `statement.export.all` with `typeOnly` set.
- **A yes/no fact is a flag unless it changes eligibility.** It is a flag only if it changes neither what the node admits, its slots and children, nor the slots that admit the node. A fact that changes either is a refinement kind. A flag reads as freely toggleable, and a consumer must never take a `try` block for a block with a bit it may clear.
  - **What the flags are.** They include `static`, `async`, `abstract`, `readonly`, `declare`, `override`, `const`, `unsafe`, `default`, `move`, `optional`, `definite`, `generator`, `big`, `imaginary`, `privateName` and `computed`, and a binding's facts (below).
    - A method's `static` is one flag in every language: python's `@staticmethod`, typescript's `static` and rust's associated function with no receiver, neither `self` nor a typed `self: Box<Self>`, set it. A python `@classmethod` is a plain `declaration.member.method`, and no fact holds a method's binding to its class.
    - `async` names every async form: a function, a closure, typescript's `for await` and `await using`, and python's `async for` and `async with`.
    - Rust's function modifiers decompose alike on a function and on a signature: the flags `async`, `const`, `unsafe` and `default`, and `extern`, a member holding the `modifier.extern` that names the ABI.
  - **A binding's facts are flags** of variables, parameters and patterns: `mutable` (typescript's `let` and `var`, rust's `mut`), `functionScoped` (typescript's `var`), `byReference` (rust's `ref`), and `disposable` (typescript's `using`), with `async` beside it for `await using`. A typescript `const` is a variable without `mutable`. Rust's `const` items, which are inlined, and python's upper-case names, constants by convention, are a kind of their own, `declaration.constant`. Rust's `static` item is storage with an address, a `declaration.variable`: `static mut` sets `mutable`, and lazy_static's `static ref` sets `byReference`.
    - `mutable` is the binding's mutability, everywhere. A reference's is `exclusive`: `&mut T`, `&mut x` and `&mut pat` set it on `type.reference`, `expression.reference` and `pattern.reference`, and the receiver's `.reference.exclusive` names it. `ref mut x` sets `byReference` and `exclusive` (§9). A raw pointer's is `writable`: `*mut T` sets it on `type.pointer`, and `&raw mut x` on `expression.reference`, a raw borrow, which has `raw` set. Raw pointers alias, so neither is `exclusive`.
  - **What changes eligibility is a refinement kind.**
    - A rust block's `try`, `async`, `gen`, `const` and `unsafe` are refinements of `expression.block`: each wraps a body block, fifteen slots admit only a plain block, and a const block is a pattern as well. `move` is a flag of the async and gen blocks, so `async move { }` is `expression.block.async` with `move` set.
    - Typescript's class `static` block is `declaration.member.static_block`, which only a class body admits.
    - Typescript's abstract method signature is `declaration.member.method.signature.abstract`: only a class body admits it, and it admits no `async`, `readonly` or `static`.
    - Typescript's definite variable (`let x!: T`) is `declaration.variable.definite`: its name is an identifier, its type is required, and it has no initializer. A field's `definite` is a flag, so one fact can be a flag on one kind and a refinement on another.
    - Typescript's optional tuple member is `element.tuple.member.optional`, whose name admits no rest pattern.
    - Rust's const generic parameter is `declaration.type_parameter.value`: it admits a type and a value, where a type parameter admits bounds and a default type.
    - A variadic type parameter, python's `*Ts`, is `declaration.type_parameter.variadic`, and a parameter-list parameter, python's `**P`, is `declaration.type_parameter.parameters`: each admits only a name, where a type parameter admits bounds and a default type. `variadic` is the term typescript's variadic tuples, C++ and Swift share, and pairs with the varargs parameter `declaration.parameter.variadic`; `parameters` follows typescript's `Parameters<F>`.
    - A raw string, `literal.string.raw`, admits no escape sequence, and rust's extern ABI admits only a plain string.
    - `yield*` and `yield from`, `expression.yield.delegate`, require their operand.
    - `asserts x is T`, `type.predicate.asserts`, holds a predicate where a type predicate holds a name and a type.
  - **A node's flags are a set of names.** A flag is declared on the kind that has it and holds for every kind beneath, and it has one owner, as a member does (§4.1). It is not a member: on the surface it is an is-guard and a builder step (below), and its guard passes alongside every refinement of its kind, so `is.declaration.method.static(x)` holds for a static getter.
- **Members carry data:** a name, parameters, a body, the module `pub(in path)` names. A fact with no data is a refinement or a flag, never a member, and no member restates one: nothing holds an operator, an access level or a getter's `get` beside the kind that says it. A choice of values is data: a float exponent's `sign`, `+` or `-`. A token that is only present or absent is a flag, even where it changes the value: a python complex pattern's leading minus (`sign`) and a rust receiver's `&` (`reference`).
  - **A statement's data is its own, whatever clause the grammar wraps it in.** An import's and an export's `source` are the statement's, lifted out of the from-clause that holds them. A re-export's clause is its `exportClause`, a `clause.export` (`{ a }`) or a `clause.export.namespace` (`* as ns`). What an export exports is its `declaration` (`export function f() {}`, `export default class C {}`) or its `value` (`export default x;`, and typescript's `export = x;`): one name for the value a module exports, whichever keyword exports it.
- **A spelling is a render option's or a kind's.** A distinction that says only how a construct is spelled belongs to the render option that the grammar's options block lists for it, and is no fact of the node: an integer's radix prefix (`0x` or `0X`) and a float's exponent marker (`e` or `E`) are options in typescript and python, as is the trailing comma after rust's last match arm and after python's comprehension `for` clause. A spelling no option lists stays a refinement kind: a float's `leading_point` (`.5`) and `scientific` (`1e5`), python's `literal.string.multiline`, a bare tuple (`expression.collection.tuple.bare`, `pattern.tuple.bare`) and rust's `type.generic.turbofish`. No member holds a spelling, except a number literal's facets, which the literal-facets feature declares: an integer's `radixPrefix` and a float's `marker` spell the number with its digits, and python's long `marker` (`L` or `l`) sits beside it. A number reads as its `$value` with a facet outside the number beside it (`0x1FL` reads `{ $value: 31n, marker: 'L' }`), and a build takes the `$value` or the facets that spell it, with a facet outside the number beside either. Python's long marker is `marker`, as python's float names its `e`: `Literal.Number.Integer.Big` declares it, and `Big.Hex`, `Big.Octal` and `Big.Binary` declare an optional `radixPrefix`. The options block prefers `L`, so a long decimal built from `3` is `3L` (user, 2026-11-12). Python's hex, octal and binary integers each have a long and a plain kind, as its decimal integer does (`integer_hex_long` claims `literal.number.integer.big.hex`, and `integer_hex_plain` `literal.number.integer.hex`), and the builder of each, `integer.hex`, builds the plain form, with `.long` and `.plain` naming each (user, 2026-11-12: "Split into long/plain kinds (Recommended)").
- **Builders and guards follow the path.** A refinement's builder is its path: `build.declaration.function.public.internal(…)`. A flag is a step after it, the steps in any order, each setting its bit: `build.declaration.method.public.static.async(…)`. Refinement builders and flag steps are the only form a refinement or a flag takes in a build (§8), and `is` follows the same paths (§9).
  - **A guard tests each fact its path names,** not the path as a prefix: `is.declaration.property.public(x)` holds for a public getter, `declaration.member.property.getter.public`, as `is.declaration.property.static(x)` holds for a static one. The kind-set (§3.2) still decides what a member admits.
  - **A flag's guard and step are spelled as a refinement's are,** so `is.declaration.method.static(x)` and `build.declaration.method.static(…)` would read the same if the vocabulary declared `static` a refinement. Only the types differ: a refinement has an interface of its own, and a flag has none. So a refinement never takes the name of a flag that its kind or a kind above it declares: typescript's `const T` sets the `const` flag of `declaration.type_parameter`, so rust's const generic parameter is `.value`.
  - **A step leaves out what its fact excludes.** Some facts of one node exclude each other: a typescript field's `static` with `abstract`, an optional parameter with an initializer, rust's `const` with `async`. Mostly the parser accepts such a combination and only the language's compiler refuses it, so no grammar rule shows them. Each grammar declares them in the `exclusions:` block of its `grammar.sittir.ts`, builder-only data that never reaches the parser, and the compiler stamps each kind's groups (`exclusionGroups`) ([builder exclusions](2026-10-19-builder-exclusions-design.md)).
    - Where every atom of a group is a flag or a refinement that a portable path names, the chain leaves the group out: after `.static`, a typescript accessor field has no `.abstract`. A guard's path offers what the chain does.
    - Every group is checked where a portable build reaches the grammar's builder, which refuses a structure that breaks one with the group's label (§8).
    - Two flags spelled by the arms of one slot are no group: a typescript field's `?` and `!` (`optional` and `definite`) are one slot's two values. A structure that states both is refused at that slot, naming both.
    - The exclusions are a language's, not the facts', so the portable surface declares none. A portable structure maps onto one grammar kind's config at a concrete call, and the groups apply there, so a chain generic over the map shows no group.
  - The generator takes each kind's refinements and flags from the vocabulary's declarations, through the vocabulary reader it plans with; no file lists them.
- **A language's text is a const string.** A token the language spells that a member holds is held as the language spells it, never as a sittir kind name or a grammar's kind id, typed per language as a string-literal union: rust's `i32` in an expression slot is `'i32'`. The const string is the literal's identity on the portable surface, as the kind id is on a grammar's (§9). A refinement that a token spells derives the token from the kind per language, so `expression.binary.logical.and` builds as `&&` in typescript and `and` in python. A fixed literal's meaning lives on its parent's refinement (`expression.assignment.compound.add`), never on the leaf.
- **A fact about a property is the property's.** What a property's name says of the property sits on the node that declares or reads the property, never on a kind of the name:
  - a private member (`#x`) is named by an `identifier`, and the field, method or member access that holds the name has the `privateName` flag, owned by `encapsulation` (§4.3) and named apart from the `private` level. In a brand check (`#x in obj`) the private name is the left operand of a binary `in`, which admits it in a language that composes `encapsulation`, with no kind of its own;
  - a computed key is its expression, and the property has the `computed` flag, owned by `computed-keys`;
  - a shorthand property is never a kind of its own (§6). Typescript spells it as a leaf, the property and its name at once: `{ a }` holds an `identifier` among the object's entries, a slot that names its role (§2.1). Rust's struct pattern `Foo { a }` holds one as its field's name, which is key and binding at once.

  The rule also covers a language that declares access on the member rather than in the name: a C++ member's access is its visibility refinement.
- **A grammar's shape kinds are told apart by the facts they state.** Injectivity (no two kinds of one grammar share a leaf) counts a node's refinements and flags. A fact a flag states is never a refinement kind as well: typescript's `abstract_class_declaration` claims `declaration.type.class` with `abstract` set, its `generator_function_declaration` `declaration.function` with `generator` set, and its `optional_parameter` `declaration.parameter` with `optional` set, so the flag tells each from its plain kind. A refinement may also name a shape of the node's own data that is a category of its own, as `special` names a method's: `.signature`, a declaration with no implementation; `clause.case.default`, a case with no value; and `declaration.module.external`, rust's `mod a;`. A member's presence alone is no refinement: python's typed and default parameters are `declaration.parameter`, with `type` and `default` present.
- **Placement: one test.** Compare two languages' constructs member by member, leaving out members a feature the other language does not compose would make absent (§4.4):
  - the same members under a different keyword: one kind under its neutral name, each keyword a synonym of it (`type_alias`, `module`, `constructor`, `throw`, `extension`; §4.2);
  - everything the other construct has, plus members of its own: a refinement under it (`interface.trait`, `field.signature`, `loop.for_each`, `loop.counted`, `enum_member.tuple`);
  - neither: sibling kinds (`class` and `struct`, `match` and `switch`, `resource` and `scope`);
  - a wrapper or a keyword: a flag, a member or a transparent container (`async`, `decorator`, `attributes`, a type annotation), or a kind of its own where the wrapper's element is only a supertype (`declaration.ambient`, `statement.labeled`).
  A rust trait has everything a typescript interface has, once typescript's index and call signatures are left out as members of `structural-conformance`, which rust does not compose; it adds default method bodies and associated items. So it is `declaration.type.interface.trait`, and a Swift protocol is `declaration.type.interface.protocol`. That keeps the distinction SCIP keeps between interface, trait and protocol, while cross-language reading sees each of them as an interface.
- **A merged kind has one set of members.** Where the placement test gives two grammars' constructs one kind, their slots merge too. The kind's interface names each member once, and each grammar's `bindings.scm` captures its own fields onto those names, reaching through any node the kind hoists. Python's except clause and typescript's catch clause are both `clause.catch`, with `name`, `type` and `body`. Python captures its `alias`, `exception` and `suite`; typescript captures its catch group's `parameter` and `type`, and its `body`, so the group is no member. The synonyms probe lists each merged kind's members.
- **A read classifies to the deepest kind.** Classification is by match, never by construction route. `build.declaration.method({ name: '__init__', … })` builds the same tree as `build.declaration.method.special({ stem: 'init', … })`, both read back as `declaration.member.method.special`, and `is.declaration.method.special(x)` holds for both. A refinement holds where its claim's tests hold, and a flag is set by the token or kind its route reaches: a rust method declared `pub(crate)` reads as `declaration.member.method.public.internal`, whose claim pins `pub(crate)`'s node.

### 3.4 How the interfaces are written

- **One file per top-level namespace,** holding the level's synonyms as well as its kinds (§4.2), plus `context.ts`, `index.ts`, the feature folders under `features/` (§4.1), the languages' compositions in `compositions.ts` (§4.1), and the generated `augment.ts` and `features/index.ts` (§4.4).
- **Every level is an interface merged with a namespace:** the interface carries the level's members, the namespace its children. A leaf is an interface alone.
- **Every interface is generic over the grammar map:** `Name<G extends GrammarMap>`, with `G` passed through every cross-reference. Cross-references go through one import alias (`V.Expression.Call<G>`), so a local interface never shadows a namespace.
- **Each namespace exports `Any<G>`,** its kind-set (§3.2, §4.5): every kind beneath it, the prefix itself included when it is a kind, and every alias beneath it. So `V.Expression.Any<G>` admits `x` and `42`, and `V.Statement.Any<G>` admits `fn f() {}` and an expression statement. The kinds beneath and the base's aliases are ungated, and a feature's alias is gated on its owner (§4.4). Nothing is aliased beneath `declaration.member.enum_member`, so `V.Declaration.Member.EnumMember.Any<G>` is the kinds beneath it. A namespace is the vocabulary's: it holds every kind beneath it, whichever feature adds it, and a language's map holds the paths its composition has (§5). Features add kinds and aliases beneath a namespace, so the unions are generated, into `augment.ts` (§4.4).
- **An alias is a type alias in its namespace's stub,** in the base or in the folder of the feature that owns it, naming its target: `export namespace Expression { export type If<G extends GrammarMap> = V.Statement.If<G>; }` in `features/rust-expressions/expression.ts`. The generator reads it as the alias path `expression.if` to `statement.if`. An alias has no interface and no `$path` of its own, so a node it admits keeps its target's. No names are written beneath an alias (`V.Expression.Loop.While<G>`): the namespace's `Any` takes the target's `Any`, which holds them. The vocabulary path list holds each alias with its target and owner (`vocabularyAliases`), and each grammar's portable module stamps the aliases its composition holds. The portable trees give an alias a node, and `is.expression.if` and `ofType(kinds.expression.if)` hold for what `statement.if`'s hold for in a language that holds the alias, and for nothing elsewhere.
- **A namespace exports an `AnyWith…` type,** such as `V.Expression.AnyWithLet<G>`, where two or more slots share a union of its `Any` and other arms (§4.5).
- **`GrammarMap` is what a language's map holds** (`map.ts`, §5): its composition's features (`features`); the slots it narrows, by path and member (`overrides`), with a kind's forms (`$forms`) and its text (`$text`); the input each text-valued path takes (`inputs`); the grammar kinds each path reads from (`nodes`); the flags each path has (`flags`); the texts that set a flag (`facts`: python's `@staticmethod` sets `static`); and the kind a slot holds where the grammar decides it (`decided`: python's `except` body is a block).
  - **A slot is typed through the map.** `Slot<G, P, M, D>` is the map's override for member `M` of path `P` where there is one, and otherwise `D`, the vocabulary's type for the slot, read as the map's nodes, flags and text inputs. A consumer generic over the map reads a slot through the constraint `G extends GrammarMap`, as the vocabulary types it.
  - **A role holds kinds, never text,** in the vocabulary and in every map. A keyword a grammar admits as a name, rust's `union`, `gen` and `default`, is an identifier whose text the grammar's reserved-word list allows in that position: the node is an `identifier`, and nothing about it is a kind of its own. A construct spelled by a keyword alone (`return`, `break`, `pass`) is a kind with no data, spelled by its kind per language (§3.3). A bare string is builder input only: it fills a slot's single or default leaf (§8), and it never stands in a role. Where a bare string would choose between arms that render differently, the slot takes no string (the user, 2026-11-22): regex's `countQuantifier({ content: '3' })` is a type error naming `{3}` and `{,3}`, written `countQuantifierArm('3')` or `decimalDigits('3')`.
  - A language's map is generated with its grammar package (§5). It extends `GrammarMap` (`PythonMap`), sets each key to what its grammar realizes, and `Fits` checks each override against the type it narrows: an override outside it is a type error (TS2344).
  - **A contract is the map of a feature set alone,** `Contract<F>`: no overrides and no nodes, so each slot takes the vocabulary's type, and a slot's node arm is `Unmapped`. Code written for no one language is checked against a contract, and a node built for several languages is built over one composing the features it uses (§8).
  - There is no permissive map: portable code is generic over the map (§4.4).
- **Interfaces are narrow at the top and expand toward the leaves.** A level carries the members every kind beneath it carries, required only where required in all of them; a leaf carries its full shape; a refinement extends its parent and adds or narrows. `Declaration<G>` holds little beyond its discriminant, `Declaration.Member.Method<G>` holds a method's full shape, `Method.Dunder<G>` narrows `name` to `` `__${string}__` `` and adds `stem`. A shared member admits the union of what the kinds beneath admit, so a leaf narrows it; `T | T[]` where the kinds beneath disagree on multiplicity.
- **Every interface carries `$path`,** the dotted path as a string literal type: a leaf's own path, a level's the union of every path beneath it. It is the discriminant that makes `Declaration.Any<G>` usable as "any declaration" in the types. The `$` marks it as sittir's own member, as on `$type` and `$value`, so it never collides with a grammar slot named `path` (rust's `scoped_identifier`). A flag is no part of `$path`, since a flag is not a kind (§3.3); a structure states its flags in `$flags` (§8). On a structure (§8) `$path` is optional data, required only where the context does not decide the kind:
  - a builder call names its kind, so the object passed to it needs no `$path`;
  - a nested plain structure needs `$path` only when its slot admits more than one kind; a slot with one admitted kind decides, as it does for a bare string;
  - the root of a generic build entry needs `$path`.

  On a node `$path` is type-only: a portable node's type carries it to select the node's interface, and no value exists at run time. The runtime tag is `$type`, and `is` decides a node's kind from `$type`, the node's own predicates and its flags (§9). Low-level configs name their kind the same way with `$type`, through a generic `build` keyed by it; a portable structure uses `$path` because `$type` is per grammar.
- **A refinement extends its parent with `$path` narrowed to its own path:** `extends SubKindOf<Parent<G>>`, where `SubKindOf` (in `utils.ts`) maps the parent's members over unchanged except `$path`, which becomes the template `` `${parent}.${string}` ``, and the refinement declares its literal. The checker then reports a refinement that widens a shared member as an incorrect `extends`. Because every slot is typed through the map (`Slot`), that check reaches slot-typed members too: a refinement's fill must fit within its parent's. `SubKindOf` is applied to interfaces only, never to a union.
- **Each fact is declared with its form.** A refinement is a kind, and an axis has no declaration of its own: its values are the refinements of the kind that has them, nested in the axis order, and a shared axis has its values beneath a root of its own, each owner's refinement for one of them being `RefinedBy` the owner and the value (§3.3). A flag is declared on the kind that has it, and holds for every kind beneath. Each has one owner, the base or a feature, as a member does (§4.1). A flag is declared with the marker type `Flag`, never `boolean`: `readonly static?: Flag`. A `boolean` member is data, as a boolean literal's `$value` is (§3.3).
- **A flag is its name.** Flags are not numbered: a node's flags read as the names that hold on it (`$flags: ['static', 'async']`), a build takes the names it sets, and `is.<path>.<flag>` tests one. The vocabulary path list in `@sittir/common`'s `portable/vocabulary-paths.ts` lists each path's flags (`vocabularyFlags`: the path, the segment and the flag), written from the vocabulary's `Flag` declarations, so a name is the same flag wherever it is declared and the vocabulary may declare any number of them. Each bound grammar's portable module tests a flag on a node with one plan per kind and flag (`queryFlags`). A kind's flags are the members it declares with `Flag`, each gated by its owner as a member is (§4.4), and the kind's guards and steps are typed by those names.

## 4. Features and synonyms

Nothing in the vocabulary is language-specific; it is feature-specific. A language that is not object-oriented has no classes, and that is a fact about a feature it does not compose, not a fact about the language. The portable API aligns the mechanics; features and synonyms align the terminology: **features** decide which kinds, members and flags a language has, and **synonyms** let any language's word for one of them be written.

### 4.1 Features

- **A feature is a marker and the kinds, members and flags it adds.** The marker is an interface with one key, the feature's name: `interface AsyncAwait { readonly 'async-await': true }`. What the feature adds is written in its folder, `features/<feature>/`, the way the base is written: an `index.ts` holding the marker, and one stub file per vocabulary namespace the feature touches. A stub interface with a `$path` is a kind the feature adds (`Statement.Labeled<G> extends SubKindOf<V.Statement<G>>`). One without a `$path` adds members to the kind of that name (`Statement.Loop<G> { readonly label?: V.Identifier.Label<G> }`), and a flag the feature adds is declared on the kind of that name in the same stub (§3.4). Nothing else marks which is which, so writing a feature is writing vocabulary.
- **Every kind, member and flag has one owner:** the base, or the most general feature that introduces it. The `async` flag of a function belongs to `async-await`, and `declaration.member.method` to `methods`. Two features that share something both extend the feature that owns it: `classes` extends `methods`, and so would `interfaces`. A second declaration of one member on one kind fails to compile (TS2717). So a member or a flag cannot belong to two features until the shared part is factored into a feature both extend.
- **Features extend features, and their folders nest the same way.** `async-blocks` extends `async-await` and sits in `features/async-await/async-blocks/`. A feature with two parents sits under one of them and extends both. Features nest and compose without limit: a feature extends any number of features at any depth, and its folder doesn't limit what it extends (the user, 2026-11-05: "Features should be 'infinitely' nestable/composable").
- **Features are atomic.** A feature is the smallest slice some real language composes or omits as a unit: no language takes half of `async-await`, but languages take type parameters without bounds, so `parametric-polymorphism` and `bounded-quantification` are two.
- **Only an atom has a marker.** A superset such as `oop` is a composition: an interface with no marker that extends its atoms, never a second source of kinds or members. An interface with no key of its own is satisfied by every context, which is why every atom keeps its marker.
- **A language composes features by extending them.** Its composition is an interface named for it: `PythonFeatures extends AsyncAwait, Generators, MultipleInheritance, …`. A composition may extend another: `TypeScriptFeatures extends JavaScriptFeatures, TypeAnnotations, ParametricPolymorphism, InterfaceConformance`. The type system computes the closure, so rust names `AsyncBlocks` and has `async-await` through it.
- **Python's composition** (the user's answers V and A on the features proposal, 2026-11-05). Python composes Encapsulation, not Visibility: it states no access level, since `_x` is a convention only, and its `__x` (not a dunder) is Encapsulation's name-spelled privacy, claimed as `privateName`, as typescript's `#x` is. It doesn't compose AbstractClasses: its abstract method has a body that `super()` can call, and a class deriving from `ABC` is abstract only through its body. ManifestTyping, "a field's or constant's type has to be written", extends StaticTypes and AnnotatedConstants; Python and TypeScript don't compose it, since their annotations are optional, and rust does (the user, 2026-11-06). Python states Accessors through `@property` and `@x.setter`, ExplicitOverrides through `@override` and `@typing.override`, and NullableTypes through `Optional[X]`, while `X | None` stays a union, as typescript's `X | null` does (the user, 2026-11-06, approving all four claims).
- **A member no grammar holds stays declared** (the user's answer N, 2026-11-05): `bounds` on the three type-parameter refinements, and `declaration.member.property`'s `definite` and `optionality`. The feature guard exempts them and lists them.
- **The feature tree is cut by holder set** (the user, 2026-11-05: "too fine-grained", then the targeted family cut). A sub-feature is the content of one feature that one holder set holds, and core content a grammar lacks moves into a feature the same way. A cell one set of the three grammars holds is cut again along family lines (C-family object-oriented, C-procedural, Swift) only where that saves a fourth grammar at least two splits per feature it adds. On the decided claims the cut gives 106 features, 67 sub-features and 39 core features. The tree and each grammar's held set are in `docs/superpowers/notes/2026-11-05-portable-features-proposal.md`, section 1.
- **Python makes no field claim** (the user, 2026-11-21). A class-level assignment is a statement run when the class is created, and `executable-class-bodies` reads and builds it as a member (§4.5). Claiming `x = 1`, `x: int = 1` and `x: int` as `declaration.member.field` would take a field kind per assignment form under a field supertype, a claim narrowed by its target's kind so `a.b = 3` and `p, q = 4, 5` stay assignments, and three visible wrappers that rename the parents of every class-level statement: 7 public kinds, 34 more parser states and 2 conflicts. So `declaration.member.field` keeps its feature, `fields-and-modifiers`, held by rust and typescript, and python holds no field.
- **Members are shared by feature, never by slot.** Two languages share a member only when the feature behind it is the same. Single inheritance gives `extends?: T`, interface conformance gives `implements: T[]`, multiple inheritance gives `bases: T[]` where a base may be a class or a protocol and the syntax cannot say which; collapsing them because the slots look alike loses a distinction a consumer would have to reconstruct.
- **Features are named by type-theory terms,** never by a language's keyword: `typeclasses`, not `traits`; `interface-conformance`, not `implements`. A primitive type and its literals are a feature named for the type: `complex-numbers`, `arbitrary-precision-integers`, `characters`, `byte-strings`. So is a literal form some languages lack: `regular-expressions`, `string-interpolation`.
- **Three relations, three homes.** Grammar to vocabulary lives in `bindings.scm` and says nothing about features. Vocabulary to feature lives in the feature folders and says nothing about grammars. Language to features lives in the language's composition. A language's shape is the intersection of what its composed features admit and what its bindings claim. A claim outside the composition is a diagnostic, and so is a composed feature that no claim or route reaches.
- **The vocabulary grows by features.** A construct a grammar has and the vocabulary lacks, whether an unclaimed kind, an unmapped kind, or a member or fact no interface declares, is covered by extending the vocabulary with a feature: the feature adds the kinds, members and flags, the languages that have the construct compose it, and their bindings claim it. The unclaimed and unmapped ratchets (§2.1, §5.1) fall this way as well as by claims onto existing kinds.
- **The feature table (§4.3) has a column for each language with a grammar,** which is that language's composition, and columns for C#, Go, C++ and Swift. Those four exist to test the cuts: C# grounds the mainstream object-oriented slice, Go supplies structural conformance with no inheritance at all, C++ is the second multiple-inheritance language, and Swift the second typeclass and error-propagation language. A cut that only makes sense for one of the three built grammars is suspect; a cut two grounding languages share is not. Nothing can check a column without a grammar, so those columns stay in this document.

### 4.2 Synonyms

- **A name is the neutral term where one exists.** A kind's or a refinement's segment, and a flag, takes the term no language owns when there is one, and the term the languages share otherwise. A language's own word for it is a synonym: a method's receiver is `declaration.parameter.receiver`, with the synonyms `self` and `this`. A segment that is one language's word for a fact no other language has keeps it (`comprehension`, `turbofish`).
- **A synonym spells one segment or one flag.** It stands for the canonical name at the position it names, so a path written with synonyms has the canonical path's segments in the canonical order: `declaration.parameter.this` is `declaration.parameter.receiver`. A synonym never drops, adds or reorders a segment, which keeps it apart from a short alias: the portable surface has none, and every path is named in full.
- **One table per level, shared by every language.** Each top-level namespace's file declares its level's table, from a canonical segment to its synonyms: `declaration.ts` maps `receiver` to `self` and `this`.
  - A segment keeps one meaning within its level, so its synonyms hold at every position it has beneath the level. A segment two levels share takes its synonyms in each level's table.
  - A feature's segment is in its level's table as a base segment is. A synonym is not gated: it holds only where its canonical segment does, so a map without the feature has neither.
  - A flag's name is one bit everywhere (§3.4), so the flags' synonyms are one table, beside the `Flag` marker.
  - A level's own name takes no synonym, since a single-segment capture names it (§2.1).
  - The census behind the tables, which grammar says which word, is the synonyms probe (`docs/superpowers/probes/2026-10-12-vocabulary-synonyms/`).
- **A word two languages use for two facts is a synonym of neither.** Rust's `mut` marks a binding's mutability, `mutable`, and a reference's exclusivity, `exclusive`, so it is a synonym of neither flag. The collision rule (below) cannot see such a word, since it is a fact about meaning, so the table's author keeps it out.
- **A word for one position of a segment is a synonym of none.** A synonym holds at every position its segment has in the level, so a word that names only one of them would name the others too. Python's TypeVarTuple names the variadic type parameter, not the varargs parameter, so `variadic` takes no synonym from it; python's ParamSpec is `param_spec`, a synonym of `parameters`, the segment's one position in the declaration level.
- **Accepted wherever a path or a flag is written.** In `bindings.scm`, a claim's path and its flag captures (§2.1); on the portable surface, every `is`, `kinds` and `build` path, refinement builders and flag steps included (§3.3).
- **Canonicalized where it is read, canonical wherever it is kept.** The bindings reader resolves each segment against the vocabulary as it reads, the canonical names at that position first and then the level's synonyms of the segments the position has, and hands on canonical paths and flags only (§5.3). The inventory, the map and everything generated never see a synonym. `$path`, `$type` and `$flags`, a language's context and portable interfaces, and every name stored or generated are canonical: a structure's `$path` is the canonical path (§8), and a synonym reaches a build through its builder's path.
- **The collision rule.** `sittir tool vocabulary-features --check` rejects a synonym equal to:
  - at any position its canonical segment has: a sibling segment or a sibling's synonym, or a flag that the parent kind or a kind above it declares, or that flag's synonym. A refinement never takes the name of such a flag (§3.3), and neither does a synonym;
  - for a flag's synonym: another flag or another flag's synonym, and at each kind that has the flag, a member of the kind, since a single-segment capture names a member or a flag (§2.1), or a segment or synonym beneath the kind.

  A synonym is spelled as a segment is: lower case, its words joined by `_`.
- **The types carry each synonym.** The portable namespaces gain a key per synonym, typed as the canonical key is, so an editor offers `is.declaration.parameter.this`. A mapped type in the vocabulary adds the keys from each level's table, and the generator emits each runtime key as the canonical key's own entry, so nothing canonicalizes at run time. A synonym has no interface and no `$path` of its own.
- **Synonyms and qualifiers are different tools.** A qualifier is a refinement, a different kind under the semantic one: `expression.call.macro`. A synonym is the same kind under another language's word. Which one applies is §3.3's placement test.

Decisions the table records: `enumerations` and `algebraic-data-types` are separate features, since a C# enum and a rust enum share a keyword and nothing else; `decorators` and `attributes` are separate, since Swift's `@` forms are never evaluated applications; `exceptions` and `error-propagation` are separate, since Swift has both and rust has only the second. `oop` as a superset reads as `classes`, one of the inheritance features, `interface-conformance`, `accessors` and `visibility`; that composition names typescript, C# and Swift exactly, and python and C++ with the other inheritance feature. `open-type-extension` is kept apart from `typeclasses` because C# and Go have the former without the latter. `explicit-receivers` is kept apart from `methods`: typescript declares a receiver on a function or a function type as well as on a method, and python's `self` is a parameter only by convention, so the `receiver` member and `declaration.parameter.receiver` are the feature's own, and a map without it has neither. `visibility` and `encapsulation` are separate: typescript's `private` is a level the compiler checks, `#x` a name the runtime hides, and the two never mark the same member, so the flag is `privateName`, apart from the level `private`. A key that is always an expression, as in python's, Go's and Swift's dictionary literals, has nothing for `computed-keys` to flag. `comprehensions` and `jsx` are real features shaped by one language each and compose as leaves under `expression` without a row here, as does `async-blocks`, rust's `async { }` under `async-await`.

Gradual typing is `type-annotations` without `manifest-typing`, not a feature of its own. Typescript's typing kinds sit in the features that own their concepts: interfaces and their property signatures in `interfaces`, type aliases in `type-aliases`, enums in `enumerations`, call, construct and index signatures in `structural-conformance`, abstract classes and methods in `abstract-classes`, the casts in `type-annotations` and namespaces in `module-declarations`. Its modifiers are flags owned by features of their own (`optional`, `readonly`, `declare`, and `x!` with `definite`), since under `type-annotations` they would reach rust's and python's fields, which compose annotations and none of the modifiers. A JavaScript context over typescript's claims therefore has no typing kind. `clause.case` is split by the features that own its members: `match-expressions` owns the match case, `clause.case.match`, with its pattern and guard, and `multiway-branch` owns the switch case, `clause.case.switch`, with its value.

What stays in the base: operators and keyword leaves, since a language never claims an operator it lacks, so its map already leaves it out (`coercive-equality`'s comparisons are the exception, being different comparisons). A statement that holds nothing is `statement.empty` wherever it is spelled, python's `pass` (a synonym, §4.2) as much as typescript's and rust's `;`. Four features own nothing in the three grammars and are markers a composition names: `overloading`, `operator-overloading`, `concurrency-syntax` and `deferred-execution`. `nullable-types` owns `type.nullable`, typescript's `?T`; python writes a nullable type as a union. A feature composed by content (†) reaches nothing until a reader derives it: python composes `visibility`, `accessors`, `abstract-classes`, `explicit-overrides` and `operator-overloading` by naming conventions, decorators and dunders, keeps composing them, and the inventory reports each one unreached.

A level the language assumes when nothing is spelled (rust's private, Swift's `internal`, typescript's `public`) is a fact about the language, not about the node, which reads as its unrefined kind.
- **A level spelled by its name is read from the name.** A build of a level's refinement whose name says another level is refused, rather than renaming the declaration.
- **Rust's paths reduce to the levels they mean.** `pub(crate)`, `pub(in crate)` and `crate` are `public.internal`; `pub(self)` and `pub(in self)` are `private`; `pub(super)` is `public.restricted`, with `super` as its `scope`. Only `public.restricted` carries a scope the level lacks, so only its refinements have `scope` (§3.3).
- **A level is not a seal.** Swift orders `open` above `public` because it lets other modules subclass; elsewhere that permission is the absence of a seal (C#'s `sealed`), which is not an access level.

### 4.4 Presence is gated, requiredness is restated

A language's map narrows slots one at a time, and that alone cannot make a member absent for one language: a member that references a specific interface (`whereClause: V.Clause.Where<G>`) keeps that type wherever the map does not override it. So the vocabulary carries every feature's kinds, members and flags for every language and gates each member and flag on the map's features, while a language's map holds only the paths its composition has. A kind keeps one name, `V.Statement.Labeled<G>`, and code written over the vocabulary does not change with the language.

- **The augmentation is generated from the base and the feature folders.** `augment.ts` holds one `declare module` block per namespace file, which adds back everything the features own:
  - a kind a feature adds, as an interface extending its stub: `interface Labeled<G> extends labeledControlFlow.Statement.Labeled<G> {}`;
  - each gated member, declared on its own, its type indexed from the stub that owns it: `readonly label?: In<G, LabeledControlFlow, labeledControlFlow.Statement.Loop<G>['label']>`;
  - each gated flag, declared on its kind as the base declares a flag (§3.4);
  - each alias a feature owns, gated on its owner: `type If<G extends GrammarMap> = gate.In<G, features.RustExpressions, V.Statement.If<G>>;`;
  - each namespace's `Any`: the kinds beneath it, the base's and every feature's, ungated, the base's aliases beneath it, ungated, and every feature's aliases beneath it, gated (§3.4, §4.5);
  - each `AnyWith…` type (§4.5).

  `features/index.ts`, which exports every feature's marker, is generated with it.

  The base files hold everything no feature owns, and nothing else. Each member is declared on its own rather than through a mapped `extends`. Otherwise a refinement that restates a gated member would inherit two disagreeing declarations of it (TS2320). The generated code reaches its own helpers through lowercase namespaces (`gate.In`, `features.Generators`). Inside a `declare module` block the vocabulary's names are in scope, and kinds named `In` and `F` exist to shadow them.
- **Levels are whole; a feature's alias is gated.** The vocabulary types each slot by kind-sets over any map (§3.4), so every refinement is checked against its parent for every `G`.
  - The kinds beneath a namespace are ungated in its `Any`, whichever feature adds them. A kind arm gated on a feature cannot be shown to hold the feature's kind for an arbitrary `G`, so a refinement that narrows a slot to a kind a feature adds would fail to compile: `expression.call.template` narrows `arguments` to the template string `string-interpolation` adds. A language's map holds only the paths its composition has: python's has no range expression (`expression.range`).
  - A feature's alias is gated on its owner, since a kind from elsewhere lies beneath a namespace only in a language that composes the owner. A refinement that narrows a slot to a feature's alias is gated on that alias's owner exactly, as a gated member is gated along its inheritance line (below). Gated on the owner, it compiles for every `G`; ungated, or gated on a feature the owner extends, it is an incorrect `extends` (TS2430). The type test is `docs/superpowers/probes/2026-11-21-any-aliases/any.test-d.mts`.
- **The gate is a conditional on the map's features:** `In<G, F, T>` is `T` where `G['features']` extends `F`, and `Missing<F>` where it does not (`utils.ts`). A language's map holds its composition, so the condition holds exactly for the features in the composition's closure. `Missing<F>` is an interface no value has, and its `$missing` names the feature: where the gate fails, the language has no such member, and a value set on it, a Rust function's `decorators` for one, is a type error that names the feature. `Missing<F>` is not `never`, so a gated alias stays in its namespace's `Any` as an arm no value fits where the language lacks its owner: over typescript's map, `V.Expression.Any<G>` admits no `if`. Its `$path` is a string no real path matches (`` `$missing:${string}` ``), so reading `$path` on an `Any<G>` stays a string with no `undefined`, and an `Extract` by `$path` leaves the arm out (the user, 2026-11-21). That is why the kinds beneath a namespace are generated ungated, and why a narrowing to a feature's alias is gated with it (above). A flag is gated on the same condition: where the composition lacks the flag's feature, its step and its guard are `never`, so `build.declaration.method.generator` is a type error for rust. Over a union of maps the gate distributes, so the union is a supertype of each map, member by member.
- **Portable code is generic over the map.**
  - **Bounded by the features it reads.** `<G extends GrammarMap & { readonly features: Decorators }>(fn: V.Declaration.Function<G>)` reads `fn.decorators` as `V.Attribute.Decorator<G>[] | undefined`. A language without the feature fails at the call, which names the feature. A bounded type parameter reads but does not build: the gate on a type parameter stays unresolved, so a value written to a member it gates fails even through the bound. A node is built over a contract instead (§8).
  - **Unbounded, it takes every language.** A gated member reads as its type or `undefined` there, since a language without the feature has no such member.
  - **It reads slots through the map** (`Slot`, §3.4). A slot that admits text is narrowed before its kind is read.
  - **Code over several languages names the union of their maps:** `asyncOf<PythonMap | RustMap>(fn)`. Inferred from a mixed value, the type argument is one language's map, and the other's value fails.
  - **There is no permissive map.** The compiler compares `X<Lang>` with `X<All>` by their maps, and a language's map lacks the markers of the features it does not compose, so a map with every feature is no supertype of the vocabulary over each language's map.
- **A gated member is gated along its inheritance line.** `type-annotations`, which owns `returnType` on `declaration.function`, also declares it on `.signature`, which restates it. An ungated declaration cannot override a gated one, nor a gated one an ungated one. For the same reason, a kind that inherits from a feature's kind belongs to a feature too. And a feature gates a member or adds the refinements that restate it, never both: a refinement is written as the base is, ungated, so it stays with its parent's owner or another feature, and the gating feature owns the member there as well. So `.signature` stays in the base, and `type-annotations` owns its `returnType`.
- **Requiredness has two sources.** An augmentation cannot change a member's optionality: a second declaration of a member must agree with the first. A member is required:
  - where a feature the language composes declares it required, gated on that feature: python-type-forms declares a typed parameter's `type` as `readonly type: gate.In<G, features.PythonTypeForms, …>`. A feature that declares required a member another owner declares optional, with the same type, restates it, and it must extend that owner; `sittir tool vocabulary-features` reports one that does not;
  - where every claim of the kind in the language's bindings requires it, as rust requires a function's body and name: the map's `$forms` override for the path names the member required (`V.Form<'body' | 'name'>` at rust's `declaration.function`), and `Formed` applies it to the read (`Read<G, P>`) and to the build input (`BuildInput<G, P>`, §8).
- **A slot is declared through `Slot`.** A member typed by a direct reference to an interface would not see a language's override for it, so a slot is declared as `Slot<G, K, M, D>`, which takes the map's override for `M` at `K` where there is one (§3.4): `declaration.type.union`'s `body` is `Slot<G, K, 'body', V.Declaration.Member.Field<G> | …>[]`.
- **Route gaps stay out of the types.** A member or flag a composed feature gives a kind is present even where the language's bindings give it no route. Python composes `generators` and marks a generator by its body, so a Python method still has the `generator` guard and step. Building one through the step is refused at run time, and the inventory reports the gap.
- **A portable node drops what its language lacks.** A language's portable interface spells out only the members its language has (§1), so a JavaScript function's `returnType()` does not exist.
- **One copy serves polyglot programs.** An augmentation applies to the whole program, so the feature folders and `augment.ts` live once, in the vocabulary package, which loads them through its index. A program that imports several languages sees every feature, each gated per map, and no feature comes from outside the package.
- **Cost, measured and reported.** The binding prototype's vocabulary was folded, gated and measured like for like (`docs/superpowers/probes/2026-10-09-vocabulary-features/`). Type-check time informs; it does not decide a type design.
  - Over the folded vocabulary, every row of §4.3 the probe realized, 75 features with its three proposals, costs 16.1% more instantiations and 19.2% more memory. Gating every member and kind particular to some grammars by grammar costs about the same, 15.0% and 15.6%.
  - Reading each level off an augmentable kind registry costs 1.8 times the generated unions' instantiations. Cost is the only measured difference between them. The registry's one other merit is that a package outside the vocabulary could add kinds to a level by augmentation, which a type alias cannot take. That merit does not arise while every feature lives in the vocabulary package; a user's own features would reopen the choice (§11).

### 4.5 Slots are typed by kind-sets

The maintainer, 2026-11-21: "The vocabulary should be content based by default", and "We still take the language-level overrides approach". What the maintainer calls a content type is a kind-set (§3.2). A slot is typed by the kind-set it admits, by name; features add kinds to a kind-set, and a language's map narrows it. On the names (2026-11-21): "The content-based slot types should get grammar level names, no? (If there is a meaningful way to do this) also it can be a type-only path under Expression, just like Expression.Any", and then: "Just Any - it seems duplicative with Supertype".

- **A slot names its kind-set.** `expression.binary`'s `left` admits the expression kind-set, a function's `returnType` the type kind-set, and a class's `members` the member kind-set, what a class, interface, trait, impl or enum body declares. Each is typed by the kind-set's name, not by its arms written out: `readonly left?: Slot<G, K, 'left', V.Expression.Any<G>>`. A slot that admits one sub-namespace's kinds is typed by its `Any` (`V.Declaration.Parameter.Any<G>`), which already names a kind-set. A slot that admits its kind-set and more takes an `AnyWith…` type where two or more slots share the union (below). A slot spells its kinds only where its set is particular to its construct: a name that may be a string literal where a module names it that way (`export { "a b" as c }`), a property that may be a tuple index (`t.0`), a macro's token stream.
- **What the census finds.** On master on 2026-11-21, 401 of the vocabulary's 631 slot declarations spell a union of two or more arms, 131 distinct ones; the other 230 name one level, one kind or text. Of the 401, 283 spell one of four kind-sets, most with arms added: the expression kind-set (158 slots, 49 distinct unions), the type kind-set (84, 16), the statement kind-set (26, 6) and the pattern kind-set (15, 8). 50 spell one level's kinds, and 68 a set particular to their construct, 36 of them an identifier with other arms. Most added arms are a feature's kinds: the macro call in 34 type slots, a removed bound (`?Sized`) in 34. The census, its scripts and its lists per group are `docs/superpowers/probes/2026-11-21-slot-kind-sets/`. With the aliases, on the body branch after the member and type nesting, 430 of the 497 slots some language's map reads take one namespace's `Any`, and 67 need more, most of them the shared unions the `AnyWith…` types below name (`docs/superpowers/probes/2026-11-21-any-aliases/`).
- **A namespace's kind-set is its `Any`.** A kind-set is the vocabulary's supertype for the slots that admit it (§2.3): a union type with a name, whose arms are the kinds beneath its path and the aliases beneath it (§3.2), and a node still carries one claim. The expression, type, pattern and statement kind-sets are their levels' `Any`, and the member kind-set is `declaration.member`'s (§3.4). `Any` is not a kind and has no `$path` of its own. `declaration.member` is the namespace of the member kinds (the user, 2026-11-21: "Declaration.Member should be a namespace for all member type declarations"): a method with its signatures and special methods, a field, a constructor, an accessor (`declaration.member.property`), a call, construct or index signature (`declaration.member.signature`), an enum member, and a static block (`static_block_declaration`). The path itself is no kind, and the member kind-set is its `Any`, `V.Declaration.Member.Any<G>`: the kinds beneath it, and through aliases the kinds a type body holds that live elsewhere, a nested type, an associated type, a constant, and rust's macro calls and inner attributes (the table below). A kind whose meaning its position decides is claimed there (§9, "A claim a grammar site decides is a kind of its own"): rust's `fn` in an impl is a method beneath `declaration.member`. Kinds that group as naturally nest the same way (the user: "Likewise for naturally groupable kinds"; the groups, 2026-11-21): `declaration.type` holds the type declarations (class, interface and trait, struct, enum, union, type alias), and the binary operator families `expression.binary.{arithmetic,bitwise,comparison,shift}`, `expression.collection` and python's `element.comparator.{comparison,identity,membership}` are namespaces, so `expression.binary.arithmetic.add` binds as `add_binary_expression` and `expression.collection.list` as `list_expression`. The shift family keeps its `shift`, `left_shift_binary_expression` and `right_unsigned_shift_binary_expression`, since `left` and `right` are slots of `expression.binary` (below). A namespace is a node of the portable trees like a kind's path, with no `$path` of its own, and its guard asks what every guard asks, whether a node reads as the path or one under it, or as the target of an alias beneath it that the language holds (the user, 2026-11-21): `is.declaration.member(node)` holds for a method, a field or a constructor, and `ofType` takes a namespace as `is` does (the user, 2026-11-22), so `ofType(kinds.declaration.member)` selects the same nodes. What a member kind-set holds are a type body's declarations, and grammars name their rule for it as one (java's `_class_body_declaration`).

  | kind-set | type | the base's aliases | rule today: rust / typescript / python | converged rule |
  | --- | --- | --- | --- | --- |
  | expression | `V.Expression.Any<G>` | `expression.identifier`, `expression.literal` | `_expression` / `expression` / `expression` | `_expression` |
  | type | `V.Type.Any<G>` | `type.identifier` | `_type` / `type` / none | `_type` |
  | pattern | `V.Pattern.Any<G>` | `pattern.identifier`, `pattern.literal`, `pattern.member`, `pattern.subscript` | `_pattern` / `pattern` / `pattern` | `_pattern` |

  The base's aliases follow each grammar's rule for the kind-set. A statement position admits an expression because an expression statement reads as its expression (§6, Names, rule 6). A pattern position admits a member and a subscript because typescript's and python's assignment targets hold them, and rust's map narrows both, since rust parses an assignment target as an expression. Rust's patterns and python's case patterns hold a literal, and typescript's and python's target slots narrow it. A base alias a language lacks is narrowed by its map, below; it needs no feature. The maintainer ruled the name `V.Declaration.Member.Any<G>` (2026-11-21), and the aliases (2026-11-22).

  The aliases features add:

  Rust's block-like statements lie beneath `expression` through `rust-expressions`' aliases, never as the statement kind-set, which would admit a declaration as an operand (§3.2). Rust's async, const, generator, try and unsafe blocks are blocks with a modifier, so they lie beneath `statement.block` (`statement.block.async`, …), and `expression.block` is rust's alias of `statement.block`, no kind. The statement kind-set has the macro call through `statement.expression`, so it needs no alias of its own.
- **The rule's name and the type's come from one path.** `boundKindName` gives a kind's name from its path, its segments reversed and joined, hidden with a leading `_`: `statement.loop.counted` is `counted_loop_statement`. A kind-set's converged rule is the hidden bound name of the path whose `Any` it is: `_expression` is `boundKindName('expression', hidden)`, and `_member_declaration` is `boundKindName('declaration.member', hidden)`. So the vocabulary's name and the grammar's rule are one source, the path, as a kind's are. A segment whose path is no kind, a namespace that only groups kinds, is left out of a bound name beneath it when every name beneath it is unique within the parent namespace, among the parent's members and the kinds directly beneath it; a namespace with one child that is not unique keeps its segment for all its children, so a family reads alike (the user, 2026-11-21 and 2026-11-22): `declaration.member.method` binds as `method_declaration`, and `declaration.member.method.signature` as `signature_method_declaration`. A segment whose path is a kind stays, since what lies beneath refines it: `statement.loop.counted` binds as `counted_loop_statement`. A name that is not unique within the parent namespace keeps the segment too: `left` is a member of `expression.binary`, so the shift family keeps `shift`, `left_shift_binary_expression` and `right_unsigned_shift_binary_expression`, while `expression.binary.arithmetic.add` binds as `add_binary_expression`. A name the shortening gives must be no other kind's across the whole vocabulary, so a kind's name never depends on a language's composition; a kind whose shortened name another kind already has is a generator diagnostic on that kind, never a rename of the other. `Any` names a role under the path and is never a segment of a bound name: `declaration.member.any` would bind as `_any_member_declaration`, which no grammar names its rule. Rust's grammar already names its supertypes this way: `_expression`, `_type`, `_pattern`, `_statement` and `_literal` from their levels, and `_declaration_statement` from `statement.declaration`.
- **A feature adds aliases beneath a namespace.** The base declares the aliases every language with the namespace has, and a feature declares the aliases it adds in its own folder, as it declares the kinds and members it adds (§3.4, §4.1). `sittir tool vocabulary-features --write` generates each namespace's `Any` into `augment.ts` (§4.4): the kinds beneath its path, ungated, the base's aliases, ungated, and each feature's aliases, gated on their owner. Each alias has one owner, the base or the feature that adds it, as a member has, and the feature guard checks it. An alias adds no member to a kind, so the second declaration that fails a member's one-owner rule (TS2717) does not arise. A refinement that narrows a slot to a feature's alias is gated on the alias's owner ("Levels are whole; a feature's alias is gated", §4.4).
- **A union two or more slots share is an `AnyWith…` type,** `V.<Namespace>.AnyWith<Extra>`: the namespace's `Any` and the extra arms, declared by the owner of its extra arm and ungated, as a kind-set is. A union one slot uses is spelled at that slot (above). The types:

  | `V.Expression.AnyWithSpread<G>` | `Expression.Any`, `Element.Spread.Any`, `Element.Attributed` | the elements of a list, a set and a tuple |

  | `V.Type.AnyWithTypeArgument<G>` | `Type.Any`, `Element.TypeArgument`, and rust's const arguments | the type argument lists |

  Python's class body runs statements, and it takes an `AnyWith…` type rather than an alias beneath `declaration.member`, named though one slot uses it (the user, 2026-11-22). An alias goes by kind, not by position: an alias of `statement` beneath `declaration.member` would make `is.declaration.member` hold for a module-level `print(1)`. With the `AnyWith…` type, `is.declaration.member` holds for a method and not for `print(1)`, and python's class-level `if`, `print()` and `pass` still read and build in `members`.
- **A language narrows, never adds.** A language's map holds each kind-set as the language has it: the claims of the members of its grammar's rule for the kind-set (§3.2), within the kinds and aliases of its composition. A slot typed by a kind-set takes the map's, so the map writes a kind-set once, not at every slot that admits it. Where one slot admits less than the language's kind-set, the map's override narrows that slot (§5.1). An override only narrows: `Fits` refuses one outside its slot's type (TS2344), and a kind a language places that its kind-set lacks is a feature's alias to add, never the language's. The inventory lists each place a grammar's rule and the aliases its language holds disagree (§3.2).
- **Each kind-set has one rule name in every grammar.** A grammar's rule for a kind-set takes the converged name in its parser, as a claimed kind takes its converged name (rule library spec, "Kind renames reach the parser"), so a library rule that references a kind-set resolves in every grammar, and an adoption that references a rule a grammar doesn't converge is refused (rule library spec, "Adopting"). A grammar names its rule for each kind-set it has in its bindings; how is the plan's.
  - A narrower supertype a grammar keeps keeps its name: typescript's and python's `primary_expression`, typescript's `primary_type` and `declaration`, python's `_simple_statement` and `_compound_statement`, rust's `_declaration_statement` and `_literal`.
  - A supertype is hidden in the tree whatever its name, so the rename changes no parsed node. Any low-level name generated from typescript's `expression`, `type`, `pattern` and `statement` or python's `expression` and `pattern` changes with it (not checked), and is listed with the library's kind renames.
  - Python has no rule for the type kind-set: a type position holds a visible `type` node, which reads as its arm (§6, Kinds, rule 2). Whether python takes a `_type` rule is the rule library's.
  - No grammar has a rule for the member kind-set: rust's trait and impl lists reuse the module's `_declaration_statement`, typescript's class body spells its members in place, and python's class body is a block. A grammar gains `_member_declaration` where its layer writes the rule, which is where rust's trait and impl lists are narrowed to what rustc accepts.
  - How a slot's own rule references its kind-set's rule is the rule library's.

## 5. The map

The map is what the generator makes of a grammar's bindings and its slot model. It is generated with the grammar package, like its factories, and never hand-edited.

### 5.1 What it holds

For one grammar:

- **Read entries,** per grammar kind: the vocabulary kinds it can be, most specific first, each with what selects it: field literals the node must have (`operator: "+"`), predicates on captured nodes (`#eq?`, `#match?`), the template's holes.
- **Build entries,** per vocabulary kind: the factories that build it, each with the literals that spell it, and a step per flag of the kind.
- **Member routes,** per entry: for each member capture, the slot it lands in, as a path from the claimed node through any transparent wrapper to the slot (`class_heritage` → `extends_clause` → value).
- **Fact routes,** per entry: for each flag, the token or the kind in a slot whose presence sets it, and for an envelope, the facts it sets on the element it unwraps (§9).
- **Container assignments:** for a container pattern, which captures it assigns to the element it wraps, and the route to each.
- **The language's `GrammarMap`** (§3.4): its composition (§4.1) as its features, each slot its grammar narrows as an override, the grammar kinds each path reads from, and its text inputs, flags, facts and decided slots, with `Fits` over it. This is the `G` the language's interfaces are instantiated with.
- **Kind-sets:** each kind-set the language has, as its grammar's rule for it admits (§3.2, §4.5), within its composition. A slot typed by a kind-set takes the language's, and an override narrows one slot further.
- **Token classes:** the keyword and punctuation classes of §2.1, for highlighting.
- **Unmapped kinds:** each grammar kind a routed slot admits that no claim covers. Its count is a ratchet that only falls.

### 5.2 How it is typed

- **Against the low-level API.** Each route names the grammar's own slots, so the map type-checks against the grammar's generated types: a route to a slot that does not exist is a compile error in the grammar package, not a runtime surprise.
- **Against the vocabulary.** The inventory checks that every name a claim gives resolves against the vocabulary's declarations (§2.1): a claimed path to a kind or one of its flags, a single-segment capture to a member or a flag of its kind. It checks that every required member of a claimed kind has a route, or is absent under the language's composition. A claim that maps onto no declared fact is a diagnostic, and the generator emits nothing for it. Neither the inventory nor the generator infers a fact's form from the grammar's shape: a choice, a keyword or a slot's arity decides nothing (§3.3).

### 5.3 Where it is made

- **By the generator,** as part of the grammar package's generated output, regenerated when the grammar or its `bindings.scm` changes and covered by the generated-output check.
- **`bindings.scm` is read with `@sittir/scm`,** into its typed tree, by the generator's query module: the same module that reads the upstream `tags.scm` and `highlights.scm` for the seed (§2.2) and the grammar's roles. The reader canonicalizes every synonym as it reads (§4.2), so nothing after it sees one. The generator also generates `@sittir/scm`, so it reads through a build of `@sittir/scm` pinned to a known commit, never through the workspace copy: a change that breaks `@sittir/scm` cannot break the generator's ability to regenerate the fix.
- **A file that does not parse is refused.** The reader names the lines that failed; the compile of each `bindings.scm` against its grammar's parser (§10) is the gate that catches what the parse absorbs.
- **The inventory** (`sittir tool bindings-inventory`) reads the bindings through the same module and reports what the generator would refuse, plus the diagnostics of §10.

### 5.4 Who reads it

- **The portable engine's `build`** finds the build entries for a structure's `$path`, routes each member to its slot and calls the low-level loose builder (§8).
- **A portable node** takes its low-level node's read entries in order, tests each entry's literals and predicates on that node, reads each member along its route when the member is called, and reads its flags along their routes (§9).
- **`is.<role path>`** compiles the read entries under the path into the query facet's plan form, and tests each of the path's flags on the node with its plan (§9).
- **`attach`** reads a node coming to the portable surface through its read entries, and rebuilds a built node through the build entries of the surface it goes to (§9).
- **The highlighting projection** reads the token classes.

## 6. Convergence rules

Names converge before kinds. The rules govern the names the vocabulary uses and the names captures give. The convergence record for the first vocabulary is `2026-09-13-base-vocabulary-draft.md`.

**Names.** The seed's model expansion applies rules (1) and (2) to every slot it turns into a capture, and an authored capture follows them too. A capture names a slot only in the claims it sits in, never grammar-wide.

0. Two languages share a member only when the feature behind it is the same, never because the slots look alike (§4.1).
1. A flag takes the keyword that marks it where the keyword says the fact (`async`, `static`), and otherwise names what it means: `mutable` for `let`, `var` and `mut`, `functionScoped` for `var`, `byReference` for `ref`, `disposable` for `using`, `exclusive` for a reference's `mut`, `writable` for a raw pointer's `mut`, `async` for typescript's `await` in `for await` and `await using`, `privateName` for `#`.
2. An axis takes the noun (`visibility`), and its values say what they mean, not how a language spells it (`public.internal` for `pub(crate)`). A segment takes the neutral term where one exists, and a language's own word for it is a synonym (§4.2).
3. Layout is not a member.
4. Containers keep the shared name (`parameters`, `arguments`, `body`, `statements`, `typeParameters`, `typeArguments`).
5. Otherwise the majority upstream name over the claiming grammars wins; a tie is a recorded choice.
6. A member's name says what it holds and never repeats the last segment of its kind's path. No member is named `content`. The vocabulary check fails on a kind's own member that breaks either rule. A slot the model leaves unnamed is one of these:
   - **Transparent** (Kinds, rule 2). A wrapper whose one slot would take its kind's own name is flattened in the portable API, through a container pattern in its grammar's bindings, not renamed (the user, 2026-11-15: "the portable api and bindings.scm should flatten scenarios like expression.expression"):
     - an expression statement is its expression, so a statement list holds the expression itself, and the statement read on its own reads as its expression (the user, 2026-11-16: "Approve all listed"). A statement position (a statement list, and a one-statement `body` or `consequence`) admits `Expression | Identifier | Literal`, and a block's and a file's statements also admit `Pattern.Rest`. An item position admits none of them (the user, 2026-11-16);
     - rust's `for<'a>` is its lifetimes (`forLifetimes: ["'a"]`);
     - a bounds clause is its bounds, read at its holder (`declaration.type_parameter`'s `bounds`), so `clause.bounds` has no member and is only the parent of the bound forms. Typescript has no bound forms, so its composition leaves `BoundClauses` out;
     - python's comprehension clauses are the `for` and `if` clauses (`clauses: [for, if]`).
   - **A member a capture names for what it holds.** A generic name (`value`, `elements`, `content`) fits only a kind's one slot (the user, 2026-11-15: "if there are multiple slots, calling one content or even value is probably not a good idea"). Beside other slots a member takes a real name, from the languages' own references where they agree. Where a real name would repeat the path, the path is renamed instead (the user, 2026-11-15):
     - `names` for an import's imported names (python's `from` and `__future__` imports);
     - `specifiers` for typescript's import clause, beside its `default`;
     - `rename` for an import alias (`import a as b`, `use a as b`: `{ name: 'a', rename: 'b' }`);
     - `name` for a struct field initializer's field, beside its `value`;
     - `argument` for a rust type argument, beside its `bounds` (`Iterator<Item: Copy>`: `{ argument: 'Item', bounds: ['Copy'] }`);
     - `operand` and `count` for a shift (`a << b`), while other binaries keep `left` and `right`. Both are optional, as a binary's `left` and `right` are (the user, 2026-11-16: "Approve all listed");
     - `expression` for a yield's operand and a parenthesized spread's spread, and `body` for an ambient declaration, as for `statement.labeled`;
     - `value` for a typescript literal type, its one slot, which stays a kind of its own;
     - python's `def f(x=1)` takes the path `declaration.parameter.defaulted`, so its member stays `default`, as `declaration.parameter.typed_default` and every typescript parameter read it.

     The grammar bindings give the slot the member's name in the grammar the parser sees, so the low-level factories take it too: an import alias's `rename:` in python and rust, a rust field initializer's `name:`, and a rust attribute item's `attribute:` (the user, 2026-11-16: "Approve all listed").
   - **Text:** where the slot holds text, the kind's `$value` (§9).

   `content` is allowed only where the value's arity is ambiguous and the preferred name would repeat the kind (the user, 2026-11-15). No member qualifies today. The numeric text values (`literal.character` and the radix integers) keep `content` until their numbers read as `$value`, and the check lists them by name until then.

**Kinds.**

1. Containers unwrap to their element kind-set as a list.
2. A wrapper clause that carries one member around punctuation is transparent: typescript's type annotation makes `returnType: type`; python's suite forms make a function body `statement.block`, the encoding chosen at build time. A getter's annotation is its `type`, as a field's is (typescript's `get x(): T`, python's `@property … -> T`), and a getter has no `returnType` (the user, 2026-11-06, keeping the 2026-10-15 ruling). A logical expression's `left`, `operator` and `right` are optional, inherited from `expression.binary` as every other binary path's are (the user, 2026-11-13). A getter has no `parameters` either: "getters don't take parameters" (the user, 2026-11-13). `parameters` sits on the setter paths only, so a property signature and an abstract accessor field have none. Python's `@property` method is a getter too: its claim tests that its one parameter is `self`, so the portable surface projects no `parameters` for it and its build writes `self` (the user, 2026-11-13: "Claim tests for self"); a `@property` method with any other parameters projects as a method, keeping them, while the grammar's own surface still reads the method's parameters as they are (the user, 2026-11-13: "It will be read at the low level but not exposed at the high level"). The portable surface never reads: it projects what the grammar's surface read (the user, 2026-11-13: "Portable never reads it 'projects'"). Python's one-line body is no kind of its own: `suite_inline` merges into the block, every python block is `block_statement` in the parser (its options key `blockStatement`), and one line or indented is a layout preference. A portable rebuild takes the form from `_suite`'s declared default or its options override, never from arm order, so it may write a one-liner indented (the user, 2026-11-06: "Merge: display as block", then "block_statement everywhere (Recommended)"). Rust's attributed array and tuple elements are `element.attributed { value, attributes }`, as an attributed argument is; a plain element stays its bare value, and the collections have no `attributes` member (the user, 2026-11-09: "element.attributed path (Recommended)"). The slot model decides it: an envelope, an alias or a polymorph whose one non-layout slot holds nodes is transparent. A wrapper with structure of its own (rust's `attributed_parameter`, typescript's class body members) is transparent only through a container pattern, because reading a kind as its content drops whatever its own text says (`impl !Trait`). A wrapper that carries one member around punctuation is transparent through a container pattern in its grammar's bindings (the user, 2026-11-15):
   - A decorator (`@`) is its expression, so `decorators` holds the expressions.
   - Rust's attribute items (`#[ ]` and `#![ ]`) are their attribute. `#!` is the item's own text, so the inner item sets `inner` on the attribute it unwraps (§9).
   - Rust's expression statement is its expression. Its `;` is what tells a macro call statement (`a!();`) from an item macro (`foo! { }`), so it sets `terminated` on the macro call it unwraps, and only there (§9).
   - Python's `type` is its arm. An annotation that is a plain expression reads as that expression, as its generic, union, constrained and optional arms already do.

   Rust's turbofish is transparent at a call, as typescript's call type arguments are: `f::<T>()` is `expression.call { function: f, typeArguments: [T] }`, `x.f::<T>()` is `expression.call.member`, and `a::f::<T>()` is `expression.call.qualified`. A turbofish that isn't called is `expression.instantiation` (the user, 2026-11-12: "On the call").
3. A slot's kind is a namespace's `Any` or an `AnyWith…` type, the narrowest covering every grammar's admitted set, and a kind a grammar admits beyond the base's aliases is an alias the owning feature adds (§4.5). Only a set particular to one construct is spelled in the slot.
4. A text piece is a kind (§2.1); a token's text is a string.
5. Markers decompose: one that picks one of several values is an axis, and a yes/no one a flag, unless it changes what the node admits or where it is admitted, when it is a refinement kind (§3.3).
6. Inclusion is a DAG with full-coverage admission and flattened unions.
7. Refinements narrow, never widen.
8. A shorthand is never a kind of its own. One the grammar spells as a node is its longhand with the omitted member absent: rust's `Foo { a }` is an `element.struct.field` with no value. One the grammar spells as a leaf has no member to omit: it is an identifier, and its slot names its role (§2.1): typescript's `{ a }` holds an `identifier` among the object's entries.

Where a grammar's set is narrower than the vocabulary's (rust's `body` required and a block only), the language's context carries the narrowing, through its sets and its restatements (§4.4); the vocabulary is not re-authored.

## 7. Template regexes

A `#match?` predicate whose regex is anchored at both ends and made of literal runs and holes is a template: the literals are injected on build, the holes are inputs on build and members on read.

- Every hole is a named group, and the member takes its name. The leaf adds it beside the parent's members: `declaration.member.method.special` has `stem: 'init'` while `declaration.member.method` keeps `name: '__init__'`.
- A hole's type is the template literal type (`` `__${string}__` ``), and a hole with a character class is validated on construction.
- Outside the subset (unanchored, backreferences, lookaround, a quantified literal, alternation that is not itself a template with the choice as a member) a predicate is read-only, and the inventory says why.
- The regex is in the syntax tree-sitter's query engine and JavaScript share; named groups are written `(?<name>…)`.

## 8. The structure API

A **structure** is a plain object satisfying a vocabulary interface, its kind named by `$path` where its slot does not decide it (§3.4). A language types it by its build input for the path, `BuildInput<G, P>` (`input.ts`): the vocabulary interface at the path with the map's forms applied and its flags named, where each member takes a structure, a node the grammar reads at that path (`nodes`) or the path's text input (`inputs`), and a member whose kind the map decides (`decided`) takes a structure without `$path`. Structures are serializable and carry no language. A structure is only build input: a read returns a portable node (§9), never a structure.

- **The portable engine's `build` builds structures,** typed per kind by the language's portable interfaces (§1): a structure's kind, named or decided by its slot, selects its interface and its build entry, each member is routed to its slot, and the low-level loose builder coerces the value as its slot's contract says. It accepts the loose form: the canonical shape with each member widened to what its slot's loose coercion accepts, derived by one mapped utility, never authored. A node already on another engine comes over through `attach` (§9), not through `build`.
- **What the portable layer adds to coercion** is only what the low-level contract cannot know:
  - an object's `$path` is omitted wherever its context decides it (§3.4);
  - a boolean and `null` in a slot that admits a literal kind become that kind as the language spells it (`literal.boolean.true`, `literal.null`).
  Everything else, a bare string or number included, is the slot's loose coercion as the loose contract states it. Runtime validates what the types check, since a structure can arrive from JSON.
- **A structure states its refinement by its `$path`,** which names its path, refinements included, **and its flags by `$flags`,** typed per kind from the flags its kind declares: `{ $path: 'declaration.member.method.public', $flags: ['static', 'async'], … }`. `$path` may be omitted where a slot decides the kind, while no slot decides a node's flags, and a set of flags has no order. Both hold canonical names only: a synonym is a builder's path, never data (§4.2). A build refuses a structure that breaks one of its language's exclusion groups: it builds through the grammar's builder, whose check refuses it with the group's label (§3.3).
- **A node built for several languages is built over a contract.** Its author names a contract composing the features the node uses, `type Authored = Contract<Decorators>`, and writes the node's JSON object to satisfy its vocabulary interface over that contract: `{ $path: 'declaration.function', name, parameters: [], decorators: [logged] } satisfies V.Declaration.Function<Authored>`. The object then goes to each language's `build`, which checks the members the object sets against that language's portable interface. Python and typescript build it, and rust refuses it on `decorators`, which rust lacks: its `#[…]` is `attributes`, annotations that are not evaluated (§4.3). The object keeps its literal type. Annotated as `V.Declaration.Function<Authored>`, it would carry every member the contract admits, with the vocabulary's types for its slots, and a language that lacks one of those members or has narrower roles refuses it even where the object sets nothing of the kind.
- **Deviation is a type error where it should be.** A structure handed to a language whose map lacks its kind fails on the kind; one that omits a member that language requires fails on the requiredness its map applies (§4.4); one that carries a member or states a flag that language lacks fails because the member or flag is `never` there, so an excess member is a type error rather than a silent drop.
- **A refinement the target lacks degrades to its parent.** A refinement is assignable to its parent by construction, so a python `declaration.member.method.special` structure builds through typescript's `declaration.member.method`, and a rust `interface.trait` through typescript's `interface`, as long as it states no member or flag the target lacks: an `unsafe` trait still fails, since typescript has no `unsafe`.
- **Refinement builders and flag steps** (`build.declaration.method.public.async({ name: 'deposit', … })`) are the authoring form, and the structure form is the data interchange; both produce the same nodes (§3.3).

## 9. Reading

A portable engine's `parse` reads **portable nodes**: each node is read as its vocabulary kind through the map. Nothing reads a node out as a plain structure; a structure is only build input (§8).

- **A portable node is an object literal,** made the way the low-level builders make nodes. Its runtime tag is `$type`, the bound engine's grammar kind id, as on every node. Its `$path` is type-only: the node's type carries it, and no value exists at run time. Where `$type` alone does not decide the vocabulary kind (a refinement, or one grammar kind read as several kinds, such as python's `method_declaration` as `declaration.member.method` or, named by a dunder, `declaration.member.method.special`), the node's own literals and text decide it. Its flags are a set of names: its read sets them along the flags' routes, the envelope that unwraps it sets those it decides (below), and a build sets them by its steps. The set is client-side only, never crosses to native, and is read only by `is`. A role is tested at run time with `is` (below), which decides from `$type`, the node's own predicates and its flags. Every member of its kind's interface that its language has (§4.4), inherited members included, is a closure that is always present, so a member is a call (`fn.name()`), as a low-level reader is. Optionality is the member's return type (`body(): … | undefined`), and a member the grammar gives no route returns `undefined`, as a low-level reader does for an absent slot. A data member would be evaluated when the node is made, so everything that reads the tree is a closure.
- **The interfaces stay property-shaped;** they are what `build` takes (§8). A kind's portable node type is derived from its interface the way a grammar kind's `X.Parsed` is derived from its data interface: one mapped type turns each member into a closure and resolves member types through a flat per-grammar table keyed by `$path`.
- **A portable node has no way down.** It exposes no low-level node, and nothing crosses implicitly. A node moves to another engine through the target engine's `attach(node)`: one verb, the same on every engine whatever surface the node comes from, typed per input by overloads. A portable engine's `attach` takes a grammar's node and returns its portable node; a grammar engine's `attach` takes a portable node and returns the grammar's node. A parsed node is re-wrapped from its tree row, since trees are one table per language, with no reparse. A built node is rebuilt with the target surface's builders through the map. A node already bound to the engine is returned as is; one bound to another engine of the same surface is re-wrapped from its row (parsed) or rebuilt (built), exactly as a crossing is.
- **Low→high crossing runs only where the node decides it.** A low-level node crosses to the portable surface on its own only when every fact of its kind is decided by the node itself: its kind, its field literals, its own text and tokens. The generator emits those kinds as a type map, and `attach` accepts only them. A kind with a fact its envelope may set (below) is reached through the envelope; nothing queries a node's ancestors.
- **A claim a grammar site decides is a kind of its own.** Where the context a claim depends on is a site in the grammar, the grammar bindings put a parser alias there: the node is parsed with a kind of its own, and `$type` decides the claim. In rust, `function_item` in an `impl` or trait body is parsed as `method_declaration` (`declaration.member.method`, with `static` set where it has no receiver), `function_signature_item` in a trait body as `signature_method_declaration`, and `crate` as a visibility, `visibility_modifier`'s own `crate` arm, as `internal_public_visibility_modifier` (the value `modifier.visibility.public.internal`), and `self` at a path's root, where it names the current module, as a kind of its own that claims `identifier`, so every other `self` is the receiver. In python, `function_definition` in a class body is parsed as `method_declaration`, both as a statement of the body and as the `definition` of a decorated definition there. In typescript, a `required_parameter` whose pattern is `this` is parsed as `this_parameter` (`declaration.parameter.receiver`), typescript's own name for it. A site must be context-unique, so the grammar bindings clone the shared rules on the way to it and keeps one body for the aliased rule: rust's methods clone `declaration_list` and `_declaration_statement`, the `crate` arm and the path root's `self` need no clone, and python's method clones the rules from the class's `_suite` down to `_compound_statement`, and the decorated definition that statement holds. A clone of a visible rule is a kind of its own, as python's class-body block and decorated definition are, and the claims on its base reach it. A base's claim stops at a clone whose own unconditional claim sits at an unrelated path, so python's constructor, a clone of `function_definition` claimed as `declaration.member.constructor`, does not read as `declaration.function`; a claim at an ancestor or a refinement of the clone's path still reaches it. A clone of a supertype the path enters stays hidden: it is a supertype in the parser's node types, over its source's forms, and has no builder. A slot that holds it keeps its source's name, so typescript's class body member still holds `method_definition`. An alias kind has its own kind id and its own low-level builder, which builds the aliased rule's node under the alias's kind id, so a built method's `$type` is a parsed one's.
- **A clone is named by its place.** A clone of a hidden rule stays hidden. A clone of a visible rule is a kind of its own, named after its owner, the kind whose field the clone's path starts in, by the owner's bound name: a clone that is that field's whole content takes `<owner>_<field>` (rust's `trait_interface_declaration_body`, the clone of `declaration_list` in a trait's `body`), and every other one takes `<kind>_<context>` with the owner as context (python's `suite_block_class_declaration`, `block_class_declaration` and `decorated_definition_class_declaration`, all under a class's `body`). The grammar bindings write `(kind as name)` for each. A visible clone never aliases back to its source's name: that would make the source's display a union over two nonterminals, which alias identity forbids.
- **A claim on a word's text is a kind of its own.** A kind claim that names its kind by a fixed text on the claimed node's own leaf (`#eq?`, `#any-of?`), where that leaf is the grammar's `word` token or an alias of it, is a parser split: typescript's `constructor`, `((method_definition name: (property_identifier) @name) @declaration.member.constructor (#eq? @name "constructor"))`, and python's `__init__`.
  - The claimed rule is copied with the leaf replaced by the literal, aliased back to the leaf's kind (`alias('constructor', $.property_identifier)`), so the leaf node does not change. Tree-sitter's keyword extraction then lexes the literal as a keyword wherever the copy's arm or one of its relaxed arms (below) is valid, and as the identifier everywhere else.
  - The copy is named from the claim's path, as an alias is (`declaration.member.constructor` is `constructor_declaration`), and sits beside its source at each site the pattern names. Ancestors the pattern names as context are copied, and a visible one is named as any clone is (above). `$type` then decides the claim: typescript's constructor claim names the class body as its context, so an object literal's method named `constructor` stays a method.
  - The literal is relaxed at every site of its word family. The family is the keywords the leaf's own site already relaxes back to the leaf's kind: typescript's reserved identifiers, `alias('get', $.property_identifier)` and its siblings in `_property_name`. Every choice that relaxes the whole family to a word display gains the literal aliased back to that display. The literal is then lexed as the keyword there too, but it reads as the word wherever its family does, as it did before the split. Without that, a word path that shares the copy's states would lose the text: a class field or an overload signature named `constructor`, or an object's shorthand `{ constructor }` once `_property_name` holds the keyword. The copy's arm takes dynamic precedence, so `constructor(…) {}` in a class body is the constructor. A leaf whose site relaxes no keyword, as python's function name, has no family and relaxes nothing. Typescript's family spans eleven sites, and the split costs 8 parser states.
  - The copy's leaf is fixed text. A field whose whole content is the literal's alias is no input: the copy's builder stamps the literal, and the parsed node keeps the field, read as the leaf's kind. Its spacing is the leaf kind's, not a keyword's, so a built constructor renders `constructor() {}`, as a built method named so does.
  - A literal that is not word-shaped, or a leaf that is a string, a number or a token other than the word, refuses the split (`literal-split-not-keyword`); the claim is dropped or rewritten on a kind the grammar has.
  - A fixed-text claim on a keyword token needs no split: the token is already a kind of its own, so the claim reads its kind id and adds no builder, as typescript's `never` and rust's `true` and `false` do. A regex predicate (`#match?`) stays a read test.
- **A receiver is no parameter.** A parameter list's leading receiver is a field of its own, `receiver`, and `parameters` holds the rest, in the grammar the parser sees. The grammar bindings derive the field from a claim that anchors the list's first element as `@receiver` and the rest as `@parameters`: rust's `self_parameter` and typescript's `this_parameter` are both `declaration.parameter.receiver`. A function with no receiver keeps its whole list as `parameters`, so a portable `parameters` never holds a receiver.
- **A claim on a supertype owner reaches its forms.** A kind with forms is a supertype in the parser, over its forms: rust's `match_arm` is over `match_arm_with_comma` and `match_arm_block_ending`. A claim on it, such as `(match_arm pattern: _ @match)`, reads each form's fields, so the field rename the grammar bindings derive from it applies at every form that holds the field. Here `pattern` becomes `match` on both forms.
  - The forms may hold the member under different field names when each holds the same shape, and each field takes the member's name. Python's `with_clause_bare` (`item`) and `with_clause_paren` (`with_items`) both hold a `with_item` list, so both fields become `items`.
  - A form that holds the member in another shape (one item where another form holds a list) refuses the rename.
- **A rule the grammar bindings create passes through enrich.** The grammar bindings edit the grammar after enrich and after the patches, so a rule an edit newly creates, such as a split's clone or the receiver's form and variants, would reach the model as the edit wrote it. Each such rule passes through the whole of enrich again, as an authored rule does: the receiver form's `,` and the list after it become enrich's group, which records a lone `,` by its presence. An edit stamps each rule it creates with its origin, and the stamp, never a comparison of rule names, says which rules pass again. A rename creates no rule, so a renamed rule does not pass again.
- **No claim is placed.** A claim that would depend on where its node sits takes one of three forms, and none reads a parent chain:
  - a grammar site decides it: it is an alias there (above);
  - the node's position decides it: it is its parent's member, not a kind. Python's docstring is the `doc` member of the function or class whose body it opens (§2.1), and the string is a `literal.string`;
  - its envelope's own text decides it: the envelope sets the fact on the element it unwraps, one level down, as it hands the element its captures, and the element keeps it with its flags. Python's `decorated_definition` sets `static` on the method it unwraps from its own `@staticmethod`. The method's kind is its alias's, `declaration.member.method`, decorated or not (above), and a `@classmethod` sets nothing. Rust's inner attribute item (`#![…]`) sets `inner` on the attribute it unwraps. An envelope line that names its element's kind sets its facts on that kind only, where its slot holds other kinds too, and the envelope's other elements sit there with none (the user, 2026-11-16: "Scope container flags by element kind"). A line whose kind is all its slot holds, or whose element is `(_)`, sets them on every element. Rust's expression statement sets `terminated` on the macro call it unwraps: `a!();` reads `{ $path: 'expression.call.macro', $flags: ['terminated'], … }`, an item macro (`foo! { }`) is a statement of its own and unflagged, and `a + b;` sets nothing (the user, 2026-11-16: "Flag `terminated` on the macro call"). Its line for every other expression stays declared, because an envelope whose lines all name kinds unwraps only to those kinds. An envelope sets a fact from a token only where every form of the envelope spells the token, outside its slots or in a required one, and the bindings refuse a line whose token some form neither spells nor holds in a slot. A flag captured on an optional token of a container is not stamped as container-set, because the container's kind does not decide it; it reads and builds as a member of the element's path. Rust's `ref` and `mut` patterns are envelopes too: `ref x` sets `byReference` on the pattern it wraps, `mut x` sets `mutable`, and `ref mut x`, a `ref` pattern around a `mut` one, sets `byReference` and `exclusive` (§3.3). An envelope may name its element's kinds. Typescript's `labeled_statement` is an envelope when its body is a loop or a block: it hands `label` to that loop or block, which holds it as rust's loops and blocks do. Around any other statement it is `statement.labeled { label, body }` (the user, 2026-11-12: "On the loop"). Its `body` still admits a loop or a block in its type, because a second label reads that way: `a: b: for (;;) {}` is `statement.labeled { label: a }` around the loop labeled `b`. A read never puts an unlabeled loop or block there, and a build that does is refused at run time (the user, 2026-11-12: "Keep the five paths").

  So a node's facts come from its `$type`, its own literals, text and tokens, its envelope or its build, and never from a parent chain.
- **A leaf is its kind or its text.** A leaf whose text varies exposes it as `$value`. So does a node whose one slot holds a text-built kind: the node is built from that text, and the build makes the child from it (the user, 2026-11-15):
  - a comment's `$value` is its text between its delimiters;
  - an escape's is its text after the backslash;
  - a raw string's is its text between its quotes, in every grammar and for its bytes and C forms too, with any fragments joined. A raw delimiter (python's `r`/`R`, alone or with `b`) makes python's scanner take a backslash together with the character after it as string content, so it never stops at `\`. The escape tokens are reached only where it stops, and it stops at `{`/`}` only for a format delimiter (`f`/`t`). So a raw string that isn't a format string holds only text. A triple-quoted one can split that text into fragments at an embedded quote, and they are joined. The format raw paths (`literal.string.interpolated(.deferred).raw*`) hold interpolations and keep `elements` (the user, 2026-11-15: "record the scanner argument in the spec").

  Rust's `literal.character` and the radix integers take theirs through forms, because their text sits beside other arms or spells a number. A fixed literal is its kind id, which is its identity, so it compares directly and has no `$value`: on a grammar's surface the grammar's id (`x === kinds.Plus`), on the portable surface the vocabulary's const string for it (§3.3), so rust's `i32` in an expression slot reads as `'i32'`. A fixed literal's meaning lives on its parent's refinement (`is.expression.assignment.compound.add(x)`), never on the leaf, and no member restates it.
  - **A number's `$value` is its meaning in the language.** Python's and typescript's `0377` are legacy octal (Python 2, ECMAScript Annex B): each grammar splits the form off decimal, so `0377` reads 255 at `literal.number.integer.octal` and python's `0377L` reads 255n at `literal.number.integer.big.octal`, while `08`, `0389` and forms of only zeros stay decimal (user, 2026-11-12: "Read them as octal"). A rebuild writes the standard spelling, `0o377` and `0o377L`, keeping the marker's (`0377l` rebuilds `0o377l`), and no member or flag records the legacy spelling (user, 2026-11-12).
- **A role test reads the node.** `is.<role path>(x)`, such as `is.expression.assignment.compound.add(x)`, decides from `$type`, the node's own predicates and its flags. It tests each fact its path names, not the path as a prefix: it checks `$type` against the kind set of the path's kind, tests on the node the field literals and predicates that decide each refinement the path names, and tests each of the path's flags on the node with its plan. So a guard holds alongside every refinement its path does not name: `is.declaration.method.public(x)` holds for a public getter, and `is.declaration.method.static(x)` for a static one (§3.3). It runs no query over the tree: the bindings rows' kind set, slot constraints such as `operator: "+="`, text predicates and kind tests compile client-side into the same plan form as the query facet, one derivation and no separate kind table, and the plan tests only the node and its captured children. A kind test is the plan's `is` op, which holds where a slot holds a node of one of its kinds, and a step toward a captured child may take the slot's `first` or `last` value: rust's method sets `static` where its `first` parameter is neither a `self_parameter` nor a `parameter` whose pattern is `self`. It takes portable and grammar nodes alike and is typed by overloads, as `attach` is: a grammar node narrows to the grammar type or types the row maps to, a portable node to the vocabulary interface. A fact an envelope sets holds on the portable node read through the envelope, not on the grammar node alone. It is not purely structural: roles that differ only by grammar kind (`identifier` and `type_identifier`) are told apart by the kind set.
- **Render dispatches on `$type`.** `$render` runs only at the root, never on the nodes within, so rendering needs no vocabulary kind.
- **No identity is promised.** A portable node follows the rule every node follows: two reads give two objects, and equality is a comparison.
- **The type maps from low-level kinds to portable nodes live with the low-level definitions:** the language's context, each kind's portable node type and the kinds that cross on their own are emitted into the grammar package's types module, beside `ParsedByKindId` and `BoundByKindId`.

A portable node reads through the grammar's typed surface: its low-level node's kind selects its read entries, an entry's literals and predicates are tested on that node and its captured children, the first entry that holds selects the node's member routes, a member reads along its route when it is called, and its flags read along theirs. No query runs over the tree at read time, and the native layer knows nothing about roles. A malformed file reads as far as its nodes do, and its read neither loses nor adds source text, rejected input included. A node a parse error sits on, or one its read passes through, is carried as its low-level node with the reason `'error'`; an error carry is an input fault, not an API gap, so the carried-pairs ratchet leaves it out (the user, 2026-11-08: "Add 'error' (Recommended)"). A token the parser inserted (`MISSING`) and an error region are each carried by their holder, the nearest node with a record of its own, which the native error-region walk names with its span and kind, so an inserted `;` never renders as source text (the user, 2026-11-08: "Add the holder (Recommended)").

## 10. Verification

1. **Totality and injectivity,** computed from `grammar.json` and the bindings by the inventory: every meaningful visible kind claimed or unclaimed with a reason; no two kinds of one grammar share a leaf unless, in every slot that admits both, a holder's flag or a member's absence tells them apart (a private name and a public one; a shorthand struct field and a struct field); the unclaimed count only falls.
2. **The bindings compile:** each `bindings.scm` compiles as a query against its grammar's parser, and a bad node or field name is reported with tree-sitter's own error and the line; the set of compiling grammars is a ratchet.
3. **The bindings read:** each `bindings.scm` reads through `@sittir/scm` with no error node and renders back byte-identical.
4. **The map type-checks** against the low-level API (§5.2), and the inventory's checks of the map against the vocabulary pass.
5. **Inclusion is a DAG:** there are no cycles.
6. **Unmapped only falls.**
7. **Portable round trip:** parse with the portable engine, build every node again from its members, render, parse-equal, over the corpus, as the validator lane that measures the portable surface's coverage.
8. **Template regexes:** a special method built from a stem re-parses to the claim; a bare hole is rejected.
9. **Cross-language errors:** `Python.Declaration.Type.Interface` handed to python fails at compile time because python composes no `interfaces` feature, and rust's `generator` step on a method fails because rust composes no `generators` (§4.4). A rust `whereClause` handed to python is refused at build and reported as a route gap: python composes `bounded-quantification` but claims no where-clause kind. A consumer generic over the map and bounded by `async-await` takes python's and rust's functions. Bounded by `generators`, it rejects rust's method at the call, naming the feature. Unbounded, it reads a function's name through the map (`Slot`).
10. **Feature ownership:** every kind and member has one owner; a gated member is gated along its inheritance line; a feature restates only what the base or a feature it extends declares; no base kind inherits from a feature's kind; no marker key is a namespace's name or `slots`, `texts` or `unmapped`. A claim outside the language's composition, and a composed feature no claim or route reaches, are inventory diagnostics.
11. **Synonyms are input spellings:** a claim written with a synonym gives the map the canonical claim gives; `is`, `kinds` and `build` under a synonym's path are the canonical path's entries; `$path`, `$type` and `$flags` never hold a synonym; and the vocabulary's tables pass the collision rule (§4.2).
12. **Consumer-seat checks,** compile-time, in `packages/types/tests/vocabulary-consumers.test-d.ts`: an ordinary function, method, call and binary satisfy their interfaces; a getter and `Add` are refinements, and no member restates them; an increment cannot omit its operand; a Rust method's `generator` step, a JavaScript function's `returnType` and a rust function without a body are the negative cases.
13. **Type-check time is measured and reported:** the whole workspace's type-check, before and after a change to the vocabulary, its features or the map's types, with the same command. The map's and the gating's own costs are measured against the same vocabulary without them, like for like, the way the features probe measures them (§4.4). The figures inform; they do not gate the change.
14. **Crossing:** a parsed node attached to its language's other engine is re-wrapped from its tree row with no reparse and renders the same text; a built node attached to the other surface is rebuilt through the map and renders the same text; attaching a low-level node of a kind that does not cross on its own is a type error; attaching a node to the engine it is bound to returns it.
15. **Role tests:** `is.<role path>` holds for exactly the nodes whose read entries classify them under the path, on both surfaces, and passes `is.identifier` for a grammar kind that only names a role (`type_identifier`, `property_identifier`), whose slot names the role; a guard holds alongside every refinement its path does not name, a public getter passing `is.declaration.method.public` and a static one `is.declaration.method.static`, and a fact an envelope sets holds on the portable node read through it; a grammar node narrows to the row's grammar types and a portable node to the vocabulary interface, checked at compile time.
16. **Refinements fit their parents:** the vocabulary types every slot through the map (`Slot`, §3.4), so a refinement whose fill falls outside its parent's fails to compile; so does a language's map that does not fit (`Fits`).
17. **Facts resolve against the vocabulary:** every name a claim gives resolves to a declared kind, flag or member, and a claim that maps onto no declared fact is reported. A fixture vocabulary that declares one fact as a flag, and then as a refinement, gives the same bindings the same guards and steps, and only their types differ.
18. **The generated vocabulary is current:** `sittir tool vocabulary-features --check` reports no planning issue and no drift. The planning issues are item 10's ownership rules, feature folders nested by inheritance, a refinement named as a flag its kind or a kind above it declares, a member typed by a direct reference to a restated kind (§4.4), a refinement whose `RefinedBy` value is not a kind, and a synonym the collision rule rejects (§4.2). No drift means `augment.ts` and `features/index.ts` are what the base and the folders generate. The tool's test holds the check at a ceiling of none.
19. **Exclusions:** for each exclusion group a language declares whose atoms are all flags or refinements a portable path names, the language's chain after one of its steps has no step for another, and no guard path holds two of them, checked at compile time. A portable build from a structure that breaks any group is refused with the group's label, as the grammar's builder refuses it, and one that states two flags of one slot is refused, naming both.
20. **Slots name their kind-sets:** `sittir tool vocabulary-features --check` reports a slot that spells a kind-set's union instead of naming it, an alias with two owners, and an alias path that is already a kind or a namespace. A language's map fits the vocabulary at every slot typed by a kind-set (`Fits`), so a kind a language places that no feature adds is a type error, never a widening.

## 11. Open questions

- **The read-side surface's name.** The `options` block's address-to-label key is `_labels`, so "bindings" names only `bindings.scm` and its overlay. Whether the read-side consumer surface (`roles.as/is/find`) takes its name from the bindings is open.
- **Trivia and provenance through `build`.** A parsed node that crosses keeps its tree row, and with it its coordinates, but `build` builds from members alone, and a structure has no coordinates. `doc` survives as a member; free trivia needs a `trivia` member or is declared lost.
- **A user's own bindings.** Whether a user's bindings file compiles to a map composed after the package's, by the seed's per-kind override rule, and whether that happens at generation or at load. Also whether a user's own features can add kinds to the vocabulary's levels and kind-sets: generated unions take kinds only from features inside the vocabulary package (§4.4, §4.5).
