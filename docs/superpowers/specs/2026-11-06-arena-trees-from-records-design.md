# Arena trees from records: design

**Status:** approved by the maintainer, 2026-11-06. Tree lifetime settled 2026-11-12 (see Decided).
**Scope:** arena storage's parse, read, render, query and edit paths in `sittir-core`, the engine's tree functions, and the arena tree holder. Object storage keeps its representation.
**Evidence:** prototype's spike (single cursor pass, token spans, hydrate at parse, tree dropped) and its render profile, both on master 2948b9f1c, release build, local. The spike's machine was loaded, so its timings compare with each other, not as absolutes.

## Rulings since that change this design

Each is the maintainer's, and where it disagrees with a sentence below, it wins until that sentence is rewritten.

- **Trivia placement is not lazy** (2026-11-15). A parse places comments and nothing else, whitespace placement for parsed trees is deleted, and a parsed node's sides are read as a built node's are. The design is [2026-11-15-parsed-comments-at-parse-design.md](2026-11-15-parsed-comments-at-parse-design.md); it supersedes every sentence here that keeps placement lazy, the baseline measure, layout runs and "placement scratch" made per call.
- **A fixed token has no row** (2026-11-17). Its text comes from its kind, and where it sits comes from its holder's template (the maintainer, 2026-11-22: "It's in the template"). The design is [2026-11-17-read-without-fixed-token-rows-design.md](2026-11-17-read-without-fixed-token-rows-design.md); it supersedes every sentence here that keeps a fixed token's row or span.
- **Release is one behaviour** (2026-11-16): "parsed node release vs. built node release really ought to be no different". This reverses "Releasing a parsed root is a no-op: its records stay until the engine's dispose" and the cap paragraph's "no parsed record is released before the engine's dispose". Those two stand as what the code does until the release design is approved; it is proposed before any code, and it replaces them here.
- **A render infers nothing from the source** (2026-11-16): "options from the source shouldn't be inferred at render time... it should be inferred adhoc (pre-render) or at parse time". The layer a source sets apart from the engine's options is inferred once, at parse, and kept with the source; an explicit style inference is a call the caller makes before rendering. What a render may do is resolve that stored layer over the options of its call. On this design's branch that resolution ran twice per render, once at the render entry and once when the per-call tree was made; it runs once, and where a call passes no options of its own it can be resolved at parse and kept.
- **A source sets no options by itself** (2026-11-16, replacing the sentence above about a stored layer): asked why arena storage keeps the layer at all, the user ruled "in tooling/tests, let's just call styleFrom". A parse infers no options and keeps none with its source; a render reads the engine's options and the options of its call, nothing else. A caller that wants a source's indentation unit and root edges calls `engine.styleFrom(...sources)` before rendering, in the shape the layout-table design's Detection section rules (a tree or a file path; the result becomes the engine's options); the validators, tools and tests that relied on the automatic layer do that. That design already drops the tree layer from the native resolution, so this ruling agrees with it. `styleFrom` is not built and its design is parked, so the layer can't go until at least the part of it that detects the indentation unit and the root's two edges exists; when that part is built is the user's to say. The engine-less `styleFrom(language, ...)` and `styleFromSource` were retired by that design and aren't built either. The precedence loses its tree level: an occurrence's stamp, then the call's options, then the engine's. Brainstorm's reading, to be confirmed with the list of tests that move: this holds in both storages, since one edit must not render differently by storage. What it changes for a caller that passes no options: a node rebuilt in a file indented by two spaces is written at the engine's unit, and a rebuilt root takes the engine's leading and trailing edge. An untouched tree still renders as its source text.
- **A parse can adopt its source's style into the engine** (2026-11-16): `styleFrom` being unbuilt, the user ruled "a way to invoke parse that tells it to update the engine level options", spelled `adoptStyle: true` on `ParseOptions` (so `engine.read(path, options)` takes it too). This is how the layer goes without waiting for `styleFrom`.
  - **What it detects:** what the layer held, by the same derivation: the indentation unit, and the arm of the root's leading and trailing edge.
  - **Where it goes:** into the engine's options, as `styleFrom`'s design applies a detection. A key set in `createEngine` wins over an adopted one; a render call's own options win over both. A later adopting parse replaces what an earlier one adopted; a parse without the option changes nothing and infers nothing.
  - **Scope:** the engine, not the tree. Every later render of that engine uses the adopted options, whichever tree the node came from. Two files of different style parsed by one engine don't each keep their own; a caller who needs that renders each with its own call options or its own engine.
  - **Example:** `engine.parse(source, { adoptStyle: true })` on a source indented by two spaces with no trailing newline leaves the engine at indent two and no trailing newline, and a statement rebuilt in that tree is written at two. `engine.parse(source)` leaves the engine's options alone, and the rebuilt statement is written at the engine's unit.
  - **Who passes it:** the validators, tools and tests that relied on the automatic layer.
  - **A threaded batch** must not adopt: it would change engine state from inside a call.
  - **Built with this design's branch** ("Approve all six", 2026-11-16), since the stored source record and the per-render resolution it removes exist only there. What changes: `ParseOptions` gains `adoptStyle`, and the native parse entries take the options; the detector's result stays, with its resolution over a table (run once per adopting parse, never per render), and its JSON forms go; the stored source record holds its text and line-break fact only; a parsed tree keeps no inferred options and reads the engine's table; a parse reply carries no `options` key, and the three TypeScript declarations of that key go with it; the native wrapper, which knows the grammar's typed options, keeps `createEngine`'s unresolved options and the defaults privately; on an adopting parse it detects against the defaults, resolves `createEngine`'s keys over the defaults with the detection laid on them, and hands the core engine the table through a new `Engine::set_options` ("Approve both", 2026-11-16). The core engine's constructors and its parse signatures don't change, and it holds no closure. Nothing during a parse reads the engine's table, so adopting right after the native parse is the same in both storages.
- **Reads share one open words chunk,** as the cap paragraph says and the code does. "In whole chunks of its own" under "A parsed node lives in the same storage as a built node" is wrong and is read as that.

## Why

- **Memory.** Tree-sitter's tree costs about 100 bytes per node, and it lives as long as any node of its parse. All of matter.js (2.91M nodes), fully hydrated in arena storage, holds 424 MB today. With the tree dropped it holds 166 MB, 61% less.
- **Render speed.** 40–57% of a rebuilt or edited render moves tree-sitter cursors down from the root (`cursor_at`, `read::goto`) to ask about rows the records already describe. Another ~10% measures baseline gaps through the tree on every render. Templates are under 1%.
- One change answers both. Once arena storage reads everything from what its records hold, it no longer needs the tree.

## Goals

1. An arena parse hydrates the whole tree within the parse call, in one cursor pass, and drops tree-sitter's tree before it returns.
2. Every question that render, query and edit ask of a parsed arena tree is answered from its nodes (records, node rows and placed sides) and its source text.
3. Each rule is written once and runs in both storages: trivia placement, edge levels, frames, list layouts, separators, seats, depth moves, line starts and descendant walks.
4. A fact fixed at parse is stamped once, not measured per render. This covers baseline gaps.
5. Renders stay byte-identical and records stay word-identical, in both storages.

## Non-goals

- Object storage keeps reading lazily over tree-sitter's tree. Rows for object storage stay parked.
- Incremental parsing and tree-sitter queries.
- Per-call reformat and styleFrom, which are parked.
- Threading, which gets its own spec. Nothing here moves a napi or V8 call off the JavaScript thread.

## Anti-goals

- A second copy of a placement or layout rule for arena storage. Two backers of one navigation interface are fine. Two copies of one rule are not.
- Any copy of the source on the JavaScript heap, or bulk source crossing to JavaScript. A tree's bytes and strings stay native.
- A render, read or query result that differs between the storages.

## Decided

The maintainer decided these on 2026-11-06:
- Arena storage only: hydrate eagerly at parse, drop tree-sitter's tree, and keep the source buffer whole (one pooled string, read by byte offsets).
- No walk into rows for arena storage. The single cursor pass hydrates directly.
- Each anonymous token's span is kept with its record, so trivia stays lazy and is placed from records.
- The arena tree holder (tree holders, Task 4) is held for this design.
- The single cursor pass ships first, as its own change, and the untouched-render fixes ride alongside.

The maintainer settled tree lifetime on 2026-11-10 and 2026-11-12. A proposal starts from these and doesn't reopen them:
- **The tree's scope is the read call.** Tree-sitter's parser and tree are made and dropped inside the parse call and never passed elsewhere: no drop thread, no deferred-drop queue. Whatever the drop costs is paid inside the call, so make the drop cheaper.
- **"The only thing that lives after parse is the source text."** Besides the nodes themselves, nothing outlives the read call.
- **No parse side channel:** "there should be no 'parse' side channel of data not captured within the materialized nodes".
- **"The root shouldn't have a reference to the tree."** No per-tree owner, slot, table or count exists for a root, a link or a side entry to name or count.
- **"Cross node reuse is not unique to the parsed nodes."** A built node linking a parsed node is the same relation as a built node linking a built node, or a side entry naming a record from elsewhere. One node-level mechanism covers every case, and it is node work, not this design's.
- **Node memory is out of scope:** "We don't need to free our nodes - we just need to get rid of the tree." For when nodes come up, the recorded direction is that released node buffers are reused and memory returns at the engine's dispose.
- **A link to another engine's nodes is refused** in arena storage, as a cross-engine side entry is.
- **A snapshot is canonical** (2026-11-12: "Canonical: renders `ur"a"`"). A detached snapshot holds a spelled slot's canonical member and no source spelling, so a snapshot of python `UR"a"` renders `ur"a"`. Both storages read the canonical member, per the 2026-11-09 ruling that spelling is its own channel, so object storage's read of a spelled slot follows it too.

The maintainer settled how a parsed node's sides are read once no tree outlives a call, on 2026-11-14 and 2026-11-15:
- **The landing gate** is one CI paired run: render and edit, this design's arena over master's arena, at most 1; parse plus whole read, arena over object storage, at most 1; parse alone is reduced and reported; no object-storage row moves. Regex's render row is reported as measured and does not hold the landing (the maintainer, 2026-11-23: "we don't have to chase phantoms trying to get the regex #s down"); every other row still applies. A fix that lowers it stays when the gain is unambiguous (the maintainer, 2026-11-23: "it's fine to keep fixes if it improves performance... unambigiously").
- **A node's three trivia sides are one read.** `readSides(node)` answers `{ leading, trailing, inner }` from one tree over the source's records, and the JS arena keeps the answer by the node's key until one of its sides is written.
- **Unit sides are read apart** (`readUnitSides`, `ReadNodes.unitSides`), because they need the baseline measure and the three sides don't. An edit doesn't ask for them: a copy of a parsed node takes its source's unit sides when the copy is next rendered or read. A parsed node lives until its engine is disposed, so the source is there when the copy asks.
- **A render hands the three sides back.** `renderBuiltSides` answers `{ text, sides }` for a parsed record, the sides read from the tree the render already made and placed, so the first edit after a render makes no side call. `renderBuilt` is unchanged. A render measures no more for it than the root's own inner side, where that side holds layout runs.
- **Nothing is kept past the call for it.** Keeping the placement or the measure between calls stays excluded by the tree-lifetime rulings above.

## What lives after an arena parse call

- **Records** for every node, from the single cursor pass. Leaves stay coordinates inside their holder's record.
- **Node rows:** one dense row per node, records included, of 4 words: start, end, subtree end, and a packed word (grammar kind, field, and named, extra, `ERROR`, `MISSING`, holds-an-error and aliased flags). A sparse map holds each aliased node's display kind.
  - The row at a node's descendant index is its row. `NodeIndex` stays tree-sitter's descendant index, so indexes, written sides and coordinates mean the same thing in both storages.
  - Rows give every node a token span. That covers anonymous tokens, extras, named units and flags, named children a template writes (such as `constructor` or an empty `()`), and nodes inside subtrees the hydrate pass doesn't enter. The spike's check found that records plus spans locate every byte trivia placement needs: 0 uncovered bytes and 0 overlaps over all of matter.js and next.js.
  - A 3-word span per child the records don't name can't answer backer parity. A token, extra, unit or flag has no record holding its kind, field or flags, and a kind isn't read from text. So rows are dense.
- **Baseline gaps**, each measured once when its layout run is first placed, and kept with the run.
- **Placed sides**, which are node data.
- **The source text**, the one thing besides the nodes.

The spike's cost: records take about 33.8 bytes per node, and spans added 7.8 bytes per node in words (11.2 counting vector capacity). Dense rows cost 16 bytes per node instead. That puts matter.js at an estimated 190 MB, not the spike's 166 MB, still about 55% under today's 424 MB. Task 7 measures it.

## One navigation interface, two backers

The rules reach the tree through a few primitives. Trivia placement (`trivia_table/place.rs`) reads only `node`, `kid`, `kids` and `path`. Its `Kid` carries a node's index, span, descendant count, kind, and whether it is named, an entry, a leaf, or holds sides. The `SourceTable` methods use the same kinds of facts.

- **The interface** gives a node's facts (`Kid`), its children in order (named, anonymous and extras), and its parent. Naming is left to the builder.
- **The tree backer** serves object storage from tree-sitter's tree. It keeps one cursor and moves it from where it last stood, instead of descending from the root for each query. That removes the root-down `goto` that object storage pays today too.
- **The record backer** serves arena storage from records, token spans and node rows. It finds a parent from the rows' subtree ends, never with a cursor.
- **The consumers** move onto the interface with their logic unchanged:
  - the placer;
  - the `SourceTable` methods `kind_of`, `for_each_descendant`, `line_starts_inside_tokens`, `last_list_child_kind`, `for_each_edge_level`, `depth_move`, `sides`, `frames`, `slot_layouts`, `separator_before`, `framed_span` and `seat_through`;
  - the engine's tree functions: `descendants`, `siblings`, `planHolds`, `snapshot`, `text`, `coordinate`, the layout baseline and stored layout.
- In arena storage, `SourceTable::read_ctx` stops handing out a tree. `source_root` and `row_coordinate` answer from node rows, and `edited_record` stops re-hydrating, since every node already has a record.
- **Backer parity is the guard.** For every node of every fixture tree, and of the matter.js and next.js corpora, both backers give the same `Kid`, children and parent.

## Parse cost

These are the spike's numbers in ns/node (relative, loaded machine):

| | big file | matter.js |
|---|---|---|
| parse only, lazy (today) | 140 | 220 |
| parse plus deep read (today) | 308 | 400 |
| parse with hydration, tree dropped | 274 | 364 |

A caller that parses and reads deep saves 12–15% of the time and 61% of the memory. A caller that parses and only renders untouched pays about twice today's parse. Arena storage is meant for read-heavy work, so the design keeps the eager path the maintainer chose, and these numbers are here for anyone who revisits that choice.

## Tree lifetime

This replaces tree holders Task 4.
- **Inside the parse call:** the parser, the tree, the cursor, placement scratch and every read cache are made and dropped.
- **After the call:** the nodes and the source text. There's no held-parse table, slot, tree table or `Tree` object, and no count that a root, link or side entry takes on a tree. The interim `Tree` object, the live-tree table and the arena's weak tree index leave arena storage.
- **Every field of today's `ParsedTree` and `TreeArena`** is node data, source text, recomputed from those on demand, or dropped inside the read call. A field that isn't per-tree at all belongs to the engine (its grammar, its built-arena store) or to the call (its work counters, per the lock-free spec). Lazy trivia placement after the call reads only nodes and source text.
- **A coordinate or link names a node,** not a tree. The link record stays 8 words.
- **A parsed node lives in the same storage as a built node** (the maintainer, 2026-11-12: "Same storage as built nodes"). A read hydrates its records into the engine's built chunks, in whole chunks of its own, so built and parsed records share one address space. No read store, per-read block, per-read row array or per-read id exists (the maintainer, on a block id standing where the tree id stood: "Don't we have relative coordinates for this reason?").
- **A parsed record embeds no child record.** Each parsed node with a record is its own entry in the built chunks, as a built node is, since a built cell has no inline form. The root's record spans the whole source, as object storage's root coordinate does, so both storages hand out the same span; the root node's own first and last bytes are stored nowhere.
- **A node's name is `NodeId`,** a newtype over its record's address in arena storage (the maintainer, 2026-11-12: "we can make nodeId a newtype", "address is sufficient"). A built cell names a parsed record directly, as it names a built one. A named leaf has no record, and is named by its holder's `NodeId` and its site, as a built leaf is. A fixed token has no cell, so it never gets a site or a `NodeId` (the maintainer, 2026-11-22: "Fixed tokens NEVER get a site"). A comment or `ERROR` gets a record of its own. Object storage keeps its tree and index inside its own `NodeId`, since its tree outlives the read.
- **`NodeCoordinate` is object storage's, `NodeId` is the arena's, and shared code takes `NodeIdOrCoordinate`** (the maintainer, 2026-11-17: "NodeCoordinate can exist for Objects....", "what's wrong with NodeId", "NodeIdOrCoordinate? for the enum?"). Object storage keeps `NodeCoordinate` as it is, with its tree, index and end. In arena storage a node is named by its `NodeId` and nothing there builds or carries a `NodeCoordinate`. The render's writer and the source table are one implementation for both storages, so their methods take one parameter type: the enum `NodeIdOrCoordinate`, whose arms are those two. The arena arm holds the node's `NodeId` and the two facts of the site it renders at: `edges`, the seams prepare gave that site, and `changed`, the edges whose neighbour its holder replaced. A record cannot answer either, because one node can sit at two sites in a render. `SlotValue::Coord` stays object storage's, and no arena path builds one.
- **What a call reads a parsed node through** (the maintainer, 2026-11-21: no per-item tree, "needs to be fixed now"; the shape below is brainstorm's call). An arena call navigates a node and its children, and makes no `ParsedTree`. The record backer, `Records`, is made once per source per call and dropped with the call. The source table's one implementation is `ReadSources`, generic over the backer: a tree in object storage, `Records` in arena storage. `TreeId`, `SourceTrees` and `record_tree` leave arena storage, and a field that held a tree id there holds the node's `NodeId`.
  - **A render keeps no table of the nodes it visits** (the maintainer, 2026-11-22, shown that each render call still built one per source). It reads a parsed node by its record's address and follows that record's cells, so `Records` holds no row per node for a render. The walk names a node by its `NodeId`, its holder and the slot that holds it (the maintainer, 2026-11-22: "it's NodeId + Slot"). It walks from the cells, so it never has to find a row's cell. A fixed token is not a node the walk visits: the holder's template writes it. Release builds neither a tree nor a table. A `Nodes` question a render still asks (an edge chain, a delimiter, `seat_through`) may hold a table for that one answer, emptied before the next, so no entry outlives the answer and no holder's run is decoded into a list. The prepare pass's per-node overlay is a separate structure and stays parked (the maintainer, 2026-11-20: "Park it").
  - **A cell names its row by the word it starts at** (the maintainer, 2026-11-23: "Cell holds the word", over a stack of positions, a cursor per list parent and checkpoints in long runs). A run's entries vary in width, so an entry number can only be reached by scanning, and a rebuilt list reads its rows in any order and from several runs. A parsed cell, a row's site and a row's count of what lies inside it therefore count in words of the holder's run. A read goes straight to its row whatever was read before it, the walk keeps no position between reads, and a list renders in linear time in any order. A row whose word does not fit beside its cell's kind is refused as unwritable, as a row past that field is today.
  - A source-table method takes the `NodeIdOrCoordinate` it is asked about and finds the source from it, so no source id crosses the table. A method whose span is not the named node's own keeps its span parameter: a list with no node of its own, and a root's inner entries.
  - No lookup reads above the node it names. Each asks downward from that node, through its run and its stamped facts: whether an `ERROR` holds it is `held_by_error`, a list's last child is found by descending from the node and remembering the last node strictly around the list's span, and whether a write lies under it is the address bound of its subtree. A node named on its own and met again as a child answers as that child.
  - The writer holds the depth move of one slice only: its source's root, a record whose side record has no parent. That is the record's own fact, read through its id, so the arena arm carries no field for it. Any other slice moves the depth at once, because it may close what a template opened around it, as a python `block` linked from a built holder closes the indent its holder's template opened.
- **`NodeId` names any arena node, a leaf included** ("`NodeId` names any arena node, leaf included"). A record's `NodeId` is its address; a leaf, which has no record, is its holder's address packed with its slot word and item, the one number the JavaScript side already keys a node by (exact in a double). The wire `{ $node, $site }` and the side store's key are views of it. `NodeName`, a wrapper coined for "a `NodeId`, or a `NodeId` and a site", goes, with the other copies of word and item it duplicated. Span and kind are read from the record through the id, not carried beside it.
- **A leaf's `NodeId` gives its item 18 bits and its slot word 5** (the maintainer, 2026-11-18, on the costed choice between this and naming a leaf by its cell's address). The packing is holder 30 bits, item 18, word 5: 53 bits, exact in a double. An item is its index in its list, from 0, so a list slot names leaf items 0 to 262,143: a list of 262,144 leaf items. A longer one is refused in arena storage when its run is written, at parse for a parsed list and at the store for a built one, with an error that names the limit, so every arena tree that exists can name each of its nodes; object storage reads such a source. A record is at most 32 words, header included (the widest today is 27). The three widths are defined once, in the core beside the key; the codec exports them to the JavaScript side, and each generated grammar crate asserts at compile time that no kind's record is wider, naming the kind. Before this the item had 16 bits and the word 7, and a query over a 70,000-item array threw at item 65,536. Naming a leaf by its cell's address was costed and not taken: it removes the limit, but costs a holder word at the head of every run (2 to 4% of record and run words on the corpora), needs a long run to span consecutive chunk numbers, and saves no copy when a holder is rebuilt, since a built leaf's cell is already one word naming its interned text entry.
- **A side's key is the node's `NodeId` and one bit; there is no inner side natively** (the maintainer, 2026-11-17: "Place is just NodeId + bit for side, right? we can in fact drop inner, which is not an option perse, it's know from context..."). The side store keys a side by `NodeId << 1 | side`, leading or trailing, so a holder's sides and its leaves' sides are one range of keys. A node's inner side is the leading side of its inner-site slot, the empty slot where the template already writes it: `NodeId::leaf(P, the slot's word, 0)`. `$trivia.inner` stays as the public reading and writes that side. An inner write on a node whose inner-site slot holds a value is refused, since the two would share a key.
- **Natively a node has two sides, leading and trailing; the public `$trivia.inner` stays and is the leading side of the node's one inside site** (the maintainer, 2026-11-18: "I guess we can keep trivia inner - it will be mapped to leading on the native side", then, shown that a slot cannot always hold it, "One fixed inside site per node"). Only arena storage's key loses inner (the maintainer, 2026-11-18: "Arena key only"). `TriviaSide` keeps `Inner` as the name of a node's inside: placement, object storage's row key, a node's trivia (leading, trailing, inner) and the wire's `inner` still use it, and arena maps it to the leading side of the inside site when it makes the key. Arena storage keys a record's inside as the leading side of one fixed site of that record that no slot uses, the same site in every kind (the record's second word, which holds no cell), so the key is still the node's `NodeId` and one bit. It is not a slot's first site: a comment can sit inside a node that has no slot to give it (`interface I { /* c */ }`, `return /* c */;`, `debugger /* c */;`, rust `m!( /* c */ $)`), and a slot's first site is its first child's leading side once the slot holds one, so the inside of `x([/* A */ a])` and `a`'s leading comment would share a key. With a site of its own the inside needs no stamp to exist, no emptiness test and no guard. Codegen's `innerKinds` still names the kinds the public `$trivia.inner` is offered on and where the render writes an inside entry. Object storage, which keys every side by its tree row, keeps a node's inside entries on the node's row (the maintainer's standing rule: object storage is not where the investment goes). `$trivia.inner` keeps its guards: it is offered on the empty forms, and giving the slot a value while it holds inner comments is refused, in both storages, before any native write ("move them to leading/trailing on the new child"); a layout-only inside is dropped by the rebuild. A unit has no inside. A fixed-text kind of several tokens can be parsed with a comment or an ERROR between them (rust `( /* c */ )` is a `unit_expression`, since the rule is `seq('(', ')')`), but a unit has no record, renders as its kind's fixed text, and nothing reads an entry inside it (the maintainer, 2026-11-18: "Right now the template won't even accommodate it though"; confirmed by probe in both storages), so none is kept, and what the source shows between a unit's tokens survives where the holder's source span is copied and is lost when the holder is rebuilt, as it is today. A root that is an ERROR renders its own span and is placed on no side of its own. Considered the same day and withdrawn: the inner-site slot's first site as the key; removing `$trivia.inner` with nothing in its place; three public accessors for a slot's side.
- **A coordinate of a recordless node** is its holder's `NodeId` and its site, `{ $node, $site: [word, item], $span, $type }`, as a built leaf handle is (the maintainer, 2026-11-13: "Use $site").
- **Nothing outside a slot is handed out,** in either storage, so a recordless node's coordinate has the one form above. An `ERROR` is leaf-like: it has its record, its span and its text, and a query walk yields nothing from inside one, whether it meets the `ERROR` or starts on it (the maintainer, 2026-11-13: "Let's just not map errors", "Yield nothing"). A query yields only nodes a slot holds, so a named child its holder routes to no slot isn't yielded: a constructor's fixed name, typescript's `constructor` and python's `__init__` (the maintainer, 2026-11-13: "Queries yield slot nodes only"; "Rule stands, name not queryable"). A child read as a unit is still yielded, since a unit is a kind and names no node. An extra held in a side always has a record, an html comment included.
- **A source's entry holds no word naming its root record** (the maintainer, 2026-11-13: "No word; start from the record"). A native call works from a record address it carries, and finds a root by a parent walk when it needs one.
- **A parsed node belongs to the engine that parsed it** (the maintainer, 2026-11-13: "Approve all three"). Building or editing around a node another engine parsed is refused. Another live engine can render it, and after its own engine is disposed the render refuses with the released-arena message. Releasing a parsed root is a no-op: its records stay until the engine's dispose.
- **The stored-layout measure passes over `ERROR` and extra subtrees,** in both storages, since an `ERROR` renders verbatim and a slot layout inside one is never rendered (the maintainer, 2026-11-13: "Skip ERROR subtrees").
- **The source text is in the string pool** (the maintainer, 2026-11-12), as one whole string, written natively inside the read call. A record names its source by a string reference, and its spans are bytes in that string. Small sources share a string chunk; a source too large for one takes a chunk of its own (the maintainer, 2026-11-12: "Share string chunks").
- **The cap.** Built storage holds 2^16 chunks, since a built cell keeps 16 bits for its chunk, and in this design no parsed record is released before the engine's dispose: each is placed with a count of 1, and releasing a parsed root is a no-op for its records. An ordinary chunk is 2^14 words (64 KiB), word and string chunks share the numbering, and reads share one open words chunk as small sources share a string chunk, so one engine holds about 4 GiB of records and text before `engine.parse` is refused with `ArenaError::Full`. A caller that keeps parsing disposes its engine and makes another; the reference benchmark's arena worker makes an engine per source chunk and times the dispose as the release (the maintainer, 2026-11-14: "An engine per source chunk"). Reusing released node buffers, the recorded direction for node memory, lifts it.
- **A side on a node that its holder keeps as a fixed token or a flag is not kept** (brainstorm's call, 2026-11-18, from the unit ruling above). Tree-sitter names some nodes that a holder keeps as a fixed token or a presence flag: rust `mutable_specifier`, `crate` and `self`, and typescript `import`, `this`, `optional_chain` and `override_modifier` (36 holder kinds; none in python, scm or regex). Such a node has no cell, so no `NodeId`, and a comment the parse places on its side (`& /*c*/ mut x`, `static /*d*/ mut X`, `extern crate /*c*/ foo`, `override /*c*/ m()`) has no key. The parse writes no placed side for it instead of refusing the source. The comment renders from the holder's run, so a render of the parsed tree shows it, and a rebuild of the holder keeps what master keeps. The node model says which node is such a node, by the same fact that gives it no cell. Not taken: naming these nodes (a flag's word and bit, and a new site name space for a fixed token), since nothing reads the entry, and moving the side onto a neighbour at parse, since that changes placement.
  - **A comment beside a flag goes to the slot the flag qualifies** (the maintainer, 2026-11-20: "Goes to the slot", replacing, for flags, the bullet above). A built node holds no side on a flag, so the comment sits where a built node would have to hold it: the shared `owner` passes over a flag as it passes over an entry, in both storages. `let mut /*c*/ x = 1;` reads the comment on `x`'s leading side, and a rebuild with `x = 2` writes `let mut /*c*/ x = 2;`, where master drops it; `static /*d*/ mut X` rebuilds as `static mut /*d*/ X`. A fixed token (python's `:`, `let`, `static`, `crate`, `self`) stays as the bullet above says: `owner` stops at it, so `case p: # c` places as before. The fact is the stamped route that gives the node no cell, read as flag or fixed token; no classifier beside it. Since the parse then places every comment beside a flag, a `Records` tree needs no placement.
- **Anonymous and MISSING tokens stay with their record,** as Decided says of token spans: a parsed record carries the rows of the children it has no cell for, so trivia placement stays lazy. A node with no source span to measure, a built node, renders from the engine's render options, as it does today (the maintainer, 2026-11-12: "we default to engine render options").
- **Nothing in arena storage is keyed or ordered by a descendant index** (the maintainer, 2026-11-12: "Why do we need to order anything by index?"; "Navigation doesn't have to 'rekey' by node id because that's what we already use for built nodes"). A parsed node uses the built node's address-keyed paths where one exists: written sides, the render entry, cell and side-record reads, counts. What a built node never asks, because it has no source (placed sides, source-faithful list facts, spans), a parsed node answers from its own record, its run of children in document order, its parent word and its source, through the record backer, whose key is a record's address or a recordless node's row address. No count word is stored and no index is derived. Only tokens with no width can share their bytes (a dedent, a MISSING token, an automatic semicolon, a node's start or end edge), and trivia placement orders them by rank: among the nodes that touch that byte, the order a walk from the root enters and leaves them. The rank is a function of the tree alone, the same whichever walk asks, computed once per such byte inside the call and kept nowhere. A render numbers no node. Any other navigation may number the nodes it meets, for that navigation only; that number carries no order and never crosses to JavaScript. The descendant index stays with object storage's tree.
- **The parsed side record changes** (it loses the descendant index and subtree end, and gains its parent, its flags and its source chunk), so record-word goldens are retaken once. Render, query and snapshot output stays byte-identical (the maintainer, 2026-11-12: "Retake, renders stay identical").
- **A built node linking parsed nodes** renders the same after the parsed root is released as before.
- **A render takes the built store's read once.** Today `render_built_with` holds that read for the whole render and `ArenaSources::render_record_entry` takes it again on the same thread, which deadlocks once a writer queues between the two (latent while one JS thread drives the engine). With the live-tree table gone, every built render goes through `render_at`, which reads the built arena once and references no tree (the maintainer, 2026-11-12: "Yes but it can't reference the tree"). The lone-leaf render joins that path as `BuiltRender::render_built_leaf(built, kind, entry, sides, changed, options, entries)`, and `render_built_with` goes; no separate function hands core the arena (the maintainer, 2026-11-14, accepting this in place of the `entry_sources_holding` row). The fix lands with the tree drop, in the same PR, and has no failing test first, since the code is napi-only and can't be tested where it sits (the maintainer, 2026-11-12: "Fold into Task 6's PR", "Port without a test").

## Order of work

Each step lands on its own and stays green:
1. The single cursor pass (in flight).
2. The navigation interface and its tree backer, with every consumer moved onto it. The representation doesn't change, and output stays byte-identical in both storages. Object storage measures the local cursor.
3. Token spans and node rows in arena records, plus the record backer, with backer parity on the corpora. The tree is still kept.
4. Arena render, queries and edits read the record backer, and baseline gaps are stamped with their run.
5. Hydrate at parse and drop the tree inside the read call. The interim `Tree` object and the live-tree table leave arena storage.
   - Then, as its own step (plan Task 6b; the maintainer, 2026-11-12): string-pool interning moves native, so the pool has one writer and one write position. Step 5 only writes each read's source into the pool natively and leaves built text's JavaScript interning as it is. Today a repeat intern is one JavaScript map lookup with no crossing, and the bench is almost all hits, so the move ships only in a shape that crosses less than once per intern call and leaves arena no slower on any CI CPU.
6. CI measurements.

## Verification

- `validate:native` rows identical in both storages after every step.
- Records word-identical to master's deep read, checked against goldens taken from master.
- Backer parity on the fixtures and both corpora.
