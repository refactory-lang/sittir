# Known Issues

Running list of known, non-blocking gaps discovered during feature work — documented here rather than silently forgotten, but not urgent enough to have blocked the work that found them. When one gets fixed, delete its entry rather than marking it done.

## `_concatInSourceOrder` sorts text-collapsed leaves (no `$span`/`$childIndex`) to the end, losing source order

**Found during:** `isInlineSafe` separator-variability qualification follow-on (rust render-emptiness regression investigation), `packages/codegen/src/emitters/wrap.ts`, `_concatInSourceOrder` (~line 1384, emitted runtime helper).

`_concatInSourceOrder` restores cross-kind source order for a repeated heterogeneous-union slot by sorting each element's `$span.start` (byte offset) or `$childIndex` (position in parent) — text-collapsed scalar leaves have neither, so they fall back to `Number.MAX_SAFE_INTEGER` and sort to the end, stable among themselves. When a real slot mixes text-collapsed leaves WITH span/childIndex-bearing elements, this pushes the leaves after everything else regardless of their true source position — reproduced on rust's `tuple_pattern`: `(x, ..)` (a text-collapsed `..` rest-marker leaf mixed with a real `identifier` element) renders as `(.., x)` instead of `(x, ..)`, a 1-2 mismatch in `read-render-parseAstMatchPass`.

**Status: deferred, not blocking.** Small (1-2 mismatches), isolated to this specific mixed-leaf-shape ordering case, and not required to resolve the separator-variability qualification's own regression (which Bugs A and B above fully account for).

**Fix, if/when prioritized:** text-collapsed leaves need SOME source-position signal to sort correctly among span-bearing siblings — likely requires either preserving a positional marker through the text-collapse step, or falling back to declaration order relative to neighboring spans instead of a global end-of-list sort.

## Rust `generic_type_with_turbofish`'s render template injects illegal whitespace around the `::<` turbofish token — accepted regression, not a TODO

**Found during:** [enrich base-grammar un-aliasing](superpowers/specs/2026-07-14-enrich-base-grammar-unaliasing-design.md) implementation, Task 1 rework (`packages/codegen/src/dsl/enrich.ts`'s `applyUnaliasDistinct`, single-site drop branch — unchanged, already-landed behavior for rust's one un-aliasing site, `scoped_type_identifier.path`).

Dropping the alias at `scoped_type_identifier.path` (visible storage kind → drop, per the existing hidden/visible branch) makes `generic_type_with_turbofish` an ordinary, independently-addressable top-level model kind for the first time. Previously it was reachable ONLY through a special context-aware reparse wrapper (see `packages/rust/grammar.sittir.ts`'s comment right below its own `generic_type_with_turbofish: { 1: field('turbofish') }` override — ADR-0006's `drillAs` mechanism), never as a bare root kind exercised by the generic per-kind read-render-parse fixture generator. Now that it is, a pre-existing gap in the shared template-rendering walker surfaces: the generated `rust/crates/sittir-rust/templates/generic_type_with_turbofish.jinja` (source of truth: `packages/codegen/src/emitters/templates.ts` → `compiler/model/node-map.ts`'s `renderTemplate()`) renders

```
{{ type_ }} {{ turbofish }} {{ type_arguments }}
```

— a literal space around the `turbofish` field (wrapping the anonymous `::` token declared via the override above). Rust's `::<...>` turbofish syntax requires exact token adjacency to disambiguate from other uses of `::`/`<`; reproduced directly: `probe-kind --grammar rust --kind scoped_type_identifier --source 'fn f(x: a::B::<T>::C) {}'` renders `"a::B :: <T>::C"` instead of `"a::B::<T>::C"`, and reparsing the spaced form yields a DIFFERENT root kind (`generic_type` instead of `generic_type_with_turbofish`) rather than round-tripping. Confirmed via corpus: rust's `read-render-parseAstMatchPass` sits at 123/136 (down from the pre-plan baseline of 125), the 2 new mismatches being exactly `generic_type_with_turbofish` (`Scoped functions`, `Struct patterns`).

This is a general "scanner-delimited / token-adjacent slot" rendering gap in the shared template-emission walker (no per-slot notion of "this field must render with zero surrounding whitespace" exists today) — not something introduced by, or fixable within, the un-aliasing pass itself.

**Status: knowingly accepted, not deferred-as-a-TODO.** The user has explicitly decided to accept this regression rather than block the un-aliasing plan on it: rust's `read-render-parseAstMatchPass` baseline is now 123 (not 125) going forward — this is the new accepted floor for rust, not a discrepancy to chase in a future session. `compiler/model/node-map.ts`'s `renderTemplate()` is a shared chokepoint across all rules in all 3 grammars, already flagged fragile in project memory ("Walker hotspot — `walkRuleForTemplate` has 3 edge fixes, no unit tests"), and a general fix carries real risk of regressing AST-match elsewhere if rushed — explicitly judged out of scope for the un-aliasing plan.

**Fix, if/when prioritized:** give the template-emission walker a way to mark a FIELD slot (or the anonymous token it wraps) as requiring token-adjacent rendering — likely keyed off `token.immediate` or a similar existing marker already tracked for other scanner-delimited cases (see project memory "Preserve token wrappers" and "Template walker adjacency — scanner-delimited kinds need adjacent rendering"). Verify against all 3 grammars' deep-AST counts before landing, given the walker's blast radius.

**More confirmed instances (2026-07-20, PR #169):** fixing typescript's `string` rule (see the `string_double`/`string_single` entry below — unrelated bug, unrelated fix) let previously-parse-blocked corpus fixtures reach far enough to exercise `break_statement`, `continue_statement`, and `debugger_statement` for the first time; all three render their trailing `;` with a leading space (`"break ;"`, `"continue ;"`, `"debugger ;"` instead of `"break;"`/`"continue;"`/`"debugger;"`), and rust's `_delim_token_tree_paren.jinja` has the same shape (`"hi" , x` instead of `"hi", x` — see that entry above). Same root cause, same deferred status — not re-litigated here, just logged as more evidence for whoever picks up the general walker fix. `regression-checker-native`'s `format-deferred-rise` verdict flagged this as typescript's `roundtrip` failingKinds growing 7→10 on PR #169 — accepted per the same reasoning as the turbofish case above (net `roundtrip` pass count went 82→109 on the same PR; the 3 new failures are pre-existing-but-newly-reachable, not caused by the string fix itself).

## TypeScript `_export_statement_default_decl_arm`'s `default` arm is unrenderable — `emitChoice`'s unnamed-arm fallback silently drops non-first choice arms

**Found during:** PR #168 baseline-refresh investigation, same research pass as the rust `token_tree` entry above — the `gen --all` run's own FR-011 coverage warning ("parity-fixtures[typescript]: FR-011 exception kind(s) not covered: export_statement") pointed at this kind.

Confirmed via direct probe: `export default function foo() {}` renders as `' export'` — the entire `default function foo() {}` portion is dropped. `_export_statement_default_decl_arm`'s shape (see `packages/typescript/grammar.sittir.ts:233-248`) is `seq(repeat(field('decorator',…)), 'export', choice(field('declaration', declaration), seq('default', choice(field('declaration', declaration), seq(field('value', expression), _semicolon)))))`, split via `variant()` at path `2/1` into a `default_kw` arm. The transport (`ExportStatementDefaultDeclArmTransport` in `rust/crates/sittir-typescript/src/render/transport.rs`) correctly carries BOTH `_declaration` and `_export_statement_default_decl_arm_default_kw` — the data is present. The bug is in `packages/typescript/templates/_export_statement_default_decl_arm.jinja`, which only references the `declaration` arm and never references `default_kw` at all, because `emitChoice` (`packages/codegen/src/emitters/templates.ts:1643-1689`) has no registered slot for this choice itself (each arm is its own slot, no fieldName, not synthetic) and falls to fallback B: **emit only the first non-empty arm, silently drop the rest.** The nested `_export_statement_default_decl_arm_default_kw` has the identical bug one level down (drops its `value` arm — `export default <expr>;` is also unrenderable). `assertSlotPreservation` doesn't catch either because the dropped slot is `isUnnamed` and is explicitly skipped.

This is a **longstanding defect, not a new regression**: the 3 previously-"passing" fixtures for this kind were `$text`-only stubs (e.g. `{"$type":364,"$text":"export default function foo(): bar"}`, no slots) — pre-alias-catalog-split (PR #165), this node never materialized structurally at all, so the renderer's `$text` fast-path emitted the source verbatim instead of ever exercising the broken template (see project memory `project_render_text_fastpath_masks_templates` for this general failure mode). PR #165 fixed materialization; the template gap became real and visible for the first time.

**Status: confirmed, not fixed. Broader than one kind — this is a bug class, not an isolated case.** A slot-vs-template scan for the same "unnamed choice arm silently dropped" pattern found ~42 unreferenced slots in typescript, ~21 in rust, ~25 in python (some fraction may be false positives from separator machinery, but multiple confirmed same-class hits exist across all three grammars — e.g. rust `function_type`→`function_type_fn_form`, `range_pattern`→`range_pattern_prefix`, `match_block`→`last_arm`; typescript `public_field_definition`→its `_first`/`_marker` slots, semicolon slots, `member_expression`→`optional_chain`). The rust `cov` validator already reports a related NAMED-field subset (5 kinds), but this unnamed-group-arm subset is invisible to both `cov` and the slot-preservation gate today.

**Fix, if/when prioritized:** in `emitChoice`'s fallback B (`packages/codegen/src/emitters/templates.ts:1684-1688`), when 2+ choice members resolve to registered nonterminal slot references, emit ALL arms as `{% if <slot> | isPresent %}…{% endif %}` conditionals — the same semantics the existing case-A `__synthetic_exclusive_choice__` path already uses (arms are mutually exclusive by grammar construction) — rather than picking only the first arm. Keep first-arm-only behavior for genuinely pure-literal/no-slot choices. `emitChoice` is a shared chokepoint across all rules in all 3 grammars (same category of risk as the `renderTemplate()` walker flagged elsewhere in this file), so the fix needs to be gated narrowly as described and verified via `validate counts` on all three grammars before landing — but since this is a fallback path that currently only ever loses information, a correctly-scoped fix should raise several kinds' AST-match numbers, not just this one. Worth a follow-up to also tighten `assertSlotPreservation` to check unnamed group-arm slots, so this class can't silently reappear.

## Assemble-time grammar diagnostics scan every `rules` map entry, including ones unreachable from any top-level kind

**Found during:** [union-slot choice routing PR 3](superpowers/specs/2026-07-21-union-slot-choice-design.md), typescript's nested/cascaded `polymorphs:` fix for `_export_statement_default` → `_export_statement_default_from_arm`.

`transform.ts`'s `resolvePatch` (ALIAS-rename branch) can't safely delete a rule from the base grammar's `rules` map — a rename-in-place could strand some OTHER, unrelated consumer keyed by the old name (confirmed necessary caution, not theoretical). So when a cascaded/nested `polymorphs:` config causes enrich's own clause-hoist mint to be superseded by a later, properly-split polymorph registration under a NEW name (the common case for 2+-level-deep `polymorphs:` splits), the ORIGINAL enrich-minted rule is left behind in `rules`, now provably unreferenced from any live top-level kind (confirmed via a manual reachability walk from `export_statement` for `_export_statement_group2`/`_export_statement_group5` — reachable: false, referenced only by each other) — but still present as a `rules` map entry.

Sittir's assemble-time grammar diagnostics (`storagename-collision`, `parsekind-noninjective`, and presumably others) walk every key in the evaluated `rules` map indiscriminately, with no reachability filter — so they fire on these orphaned duplicates exactly as if they were live grammar structure, even though tree-sitter itself never reaches them (nothing in the compiled parser can produce a node of that shape). Confirmed concretely: `_export_statement_group2` is a raw, un-split clone of `_export_statement_default_from_arm`'s content — its `export_clause`-seq arm collides in storage name with a sibling bare `export_clause` arm, firing a blocking `storagename-collision` — while the LIVE, properly-split `_export_statement_default_from_arm` (reached via `_export_statement_default`'s alias) has no such collision at all.

**Status: not fixed — worked around per-instance for now** (typescript's `_export_statement_group2`/`storagename-collision` pair is allow-listed via `expectDiagnostics` in `packages/typescript/grammar.sittir.ts`, matching the existing sanctioned per-kind exception mechanism `compiler/types.ts`'s `expectDiagnostics` doc comment already describes, e.g. the historical `_object_type_group1` example). Every future nested/cascaded `polymorphs:` split risks producing the same class of orphan + false-positive diagnostic pairing; each will need its own `expectDiagnostics` entry (or a rewritten override, avoiding the cascade) until this is fixed at the root.

**Fix, if/when prioritized:** compute rule reachability once from each grammar's top-level named kinds (a standard graph walk over `SYMBOL`/`ALIAS` references, mirroring the ad hoc walk used to confirm this issue) and have the assemble-time diagnostics pipeline (`compiler/diagnostics/grammar-diagnostics.ts`'s collectors, and whatever feeds `resolveParseKindCollisionsInSlot` in `compiler/model/node-map.ts`) skip unreachable kinds project-wide. This is a general, principled fix — broader blast radius than any single instance, since it changes what diagnostics fire for rust/python too, so it needs full `validate:native` re-verification across all 3 grammars before landing, not a narrowly-scoped patch.

**Update (2026-07-22, PR 3):** the general fix landed — `compiler/evaluate.ts`'s `buildRuleCatalog` now computes `computeReachableRuleNames` (a BFS from all visible top-level rule names via `RuleWalker.foldDeep`) and omits hidden+unreachable rules from its returned `.rules` map entirely, so downstream diagnostics never see the orphans described above. Typescript's `_export_statement_group2`/`storagename-collision` `expectDiagnostics` allow-list entry could likely be removed now that the orphan itself is filtered out before diagnostics run — not yet verified/removed, left as a follow-up so as not to entangle an allow-list removal with this PR's own verification pass.

## `emitSymbol`'s generalized hidden-helper inlining doesn't yet handle a fielded sequence inside the inlined target

**Found during:** indent-aware rendering for python (`rrp-ast-match-sweep`), generalizing `emitSymbol` (`packages/codegen/src/emitters/templates.ts`) so a NAMED field wrapping a hidden `inline: true` target (e.g. `function_definition.body` → `_suite`) inlines the target's `renderRule` the same way an unnamed group-lift helper already does, instead of always emitting an opaque `{{ body }}` slot reference. Confirmed via a full-grammar scan: 46 total "named field → hidden inline:true target" occurrences across the 3 grammars (python 11, all → `_suite`; rust 12 and typescript 23, all → 0-slot `pattern`/`enum` leaf wrappers like `_type_identifier`/`_semicolon`) — the fix was applied generically to all 46 since the non-`_suite` targets have no internal structure to be affected by inlining.

The generalization was verified safe for every CURRENT occurrence (`_suite`'s own 3 choice arms declare no fields of their own; the 35 pattern/enum targets have zero slots), but the inlining logic itself does not yet handle the case where the inlined target's content is a `seq` whose members are ALL themselves field-wrapped (as opposed to `_suite`'s arm-2 shape, `seq($._indent, $.block)`, where only the `$.block` member is field-addressable and `$._indent` is a bare terminal). If a future grammar or override introduces a hidden `inline: true` helper referenced from a named field where every seq member carries its own `fieldName`, the current inlining path's conditional-gating logic (keyed on a single `condKey`, preferring the outer field's own name) has not been exercised against that shape and may need additional handling — e.g. surfacing each inner field independently rather than gating the whole inlined body on one presence check.

**Status: not yet encountered, flagged proactively during design review — not blocking the current fix.**

**Fix, if/when prioritized:** when a future case exercises this shape, extend `emitSymbol`'s inlining block (`packages/codegen/src/emitters/templates.ts`, the `if (rule.type === SYMBOL && rule.inline === true)` branch) to detect "target's own top-level rule is a SEQ whose members are all field-wrapped" and route each inner field through its own presence/emission logic instead of a single shared conditional — likely mirroring render-module.ts's existing "group-lift inner field hoisting" pattern (hoisting a helper's inner named fields onto the parent struct) for the template side too.

## Comment fields aren't reconstructible through the factory API

**Found during:** the `factory-render-parse` storage-comparison redesign — the validator now compares a factory-built node's storage directly against the materialized read reference instead of rendering + re-parsing, which surfaces this precisely where the old render/reparse round-trip could not.

A real parse+read consistently carries a `_comment` field (and, in one python case, `_line_continuation`) wherever a comment is attached to a node — confirmed across all three grammars: python `module` (×7, e.g. "Raw strings", "Format strings"), `case_clause` (×2), `block` (×2); rust `source_file` (×1), `block` (×1); typescript `program` (×5, e.g. "Ambient exports"), `function_declaration` (×1). In every case, calling that kind's factory with the SAME materialized data (via `nodeToConfig`) produces a node missing the `_comment` key entirely — `factoryData` and `factoryFields` never mention a comment field for these kinds, so `nodeToConfig` has nowhere to route it.

**Status: confirmed via `factory-render-parse`'s storage comparison, not yet root-caused past this point.** Unknown whether comments are excluded from the factory Config type by design (comments-as-trivia, not modeled as first-class grammar fields) or whether this is a genuine gap in factory field derivation. ~19 instances across all 3 grammars, same shape every time (`root._comment: missing on factory output`).

**Fix, if/when prioritized:** first determine whether comment attachment is meant to be factory-constructible at all (check `packages/codegen/src/compiler/collect-slots.ts` / the node-model generation for whether `comment` is deliberately excluded from `_factoryFields`/`_factorySlots` for these kinds). If it's an oversight, the fix is wherever factory field derivation decides which grammar fields become Config properties — comments would need to be added as an optional field there and threaded through `nodeToConfig`'s named-slot-entries loop like any other `_<field>` key.

## Polymorph variant misselection when factory-reconstructing certain kinds — same display name, wrong underlying `$type`

**Found during:** same `factory-render-parse` redesign as above.

For several kinds, a real parse+read resolves to one specific polymorph variant (numeric `$type`), but reconstructing the SAME materialized data through `nodeToConfig` → the kind's factory produces a DIFFERENT variant that happens to share the same display name — confirmed via `KIND_DISPLAY_NAMES`: python `block` (kind id 160 expected, 135 produced — 17 of python's 32 remaining `factory-render-parse` failures, concentrated in `match_statement` contexts: "Matching specific values", "Matching multiple values", "Adding a wild card", "Or patterns", "As patterns", "If guards", "Literals", "Comma separated cases", "Case terminating in comma", "Multiple match patterns", "Match match, case case", "Matching objects", and more), python `lambda` (194 expected, 193 produced, "List comprehensions"); rust `token_tree` (168 expected, 241 produced — 17 instances, e.g. "Function declarations", "Key-Value Attribute Expressions", "Attribute macros"), `scoped_type_identifier` (246 expected, 245 produced); typescript `member_expression` (234 expected, 255 produced — 6 instances), `call_expression` (231 expected, 256 produced — 4 instances), `parenthesized_expression`, `unary_expression`, `required_parameter`, `optional_parameter`, `instantiation_expression` (1 each).

Both `block↔block` and `token_tree↔token_tree` are the two largest single clusters in their respective grammars' remaining failures (17 each). Not yet traced past confirming the symptom — plausibly `inferPolymorphVariant`/`inferOverrideHelperVariant` (`packages/tools/src/validate/common.ts`) picking a different variant than the real parse when the only signal available is the materialized data + CST hints, rather than tree-sitter's own dispatch.

**Status: confirmed via `factory-render-parse`'s storage comparison ($type mismatch, not missing/extra fields), not yet root-caused.** This is a bug CLASS spanning multiple unrelated kinds across all 3 grammars, not one isolated case — the two `match_statement`/`token_tree` clusters alone account for ~34 of the ~113 total remaining `factory-render-parse` failures across all 3 grammars.

**Fix, if/when prioritized:** start with python's `block` cluster (largest, single context — `match_statement`) via `probe-kind` on a minimal match-statement fixture, tracing `nodeToConfig`'s `inferOverrideHelperVariant`/`inferPolymorphVariant` path (`packages/tools/src/validate/common.ts`) to see which CST/hint signal it uses to pick 135 over 160 (or vice versa) and why that differs from what the real parse encodes. Given the shared symptom shape (materialize-then-reconstruct picks the wrong variant), rust's `token_tree` and typescript's `member_expression`/`call_expression` clusters may share the same root cause once traced — verify against all 3 grammars before considering it fixed.

## TypeScript `object_type_content`-shaped kinds reconstruct with zero children via the factory

**Found during:** same `factory-render-parse` redesign as above.

`object_type_content`'s `_content` field consistently reconstructs as an empty array (`array length 1 ≠ 0`) via its factory — 20 instances, the single largest typescript cluster in the new storage-comparison check (e.g. "Ambient declarations", "Satisfies expressions", "Ambiguity between function signature and function declaration"). This has the same *symptom* shape as the `getChildFactoryArgs` bug fixed in the same PR (a spread-shape factory silently invoked with zero args because the config lookup key didn't match the real field name) — but `getChildFactoryArgs` now correctly resolves the declared field via `factoryFields[kind][0]`, so either `object_type_content`'s `factoryShapes`/`factoryFields` metadata itself is wrong, or a different code path (not `getChildFactoryArgs`) is involved. Not yet traced further.

**Status: confirmed via `factory-render-parse`'s storage comparison, not yet root-caused.** Largest single typescript cluster (20 of 42 remaining failures) — worth prioritizing over the smaller singleton mismatches in the same run.

**Fix, if/when prioritized:** dump `factoryShapes['object_type_content']`, `factoryFields['object_type_content']`, and the `nodeToConfig` output for a real "Ambient declarations" fixture (mirrors the debug approach used to find the `getChildFactoryArgs` bug — see that fix's commit) to see whether the config key genuinely holds the content array and `getChildFactoryArgs`/the factory dispatch drops it, or whether `nodeToConfig` itself never populates the key for this kind.

## Boolean/keyword marker fields dropped when factory-reconstructing several rust kinds

**Found during:** same `factory-render-parse` redesign as above.

A cluster of rust kinds lose a boolean marker field (a keyword-presence flag, not a value) when reconstructed via their factory from the same materialized data a real parse+read produced: `self_parameter._reference` (`true` expected, `undefined` produced — 7 instances, e.g. "Functions with precise capture syntax"), `self_parameter._self` (`"self"` expected, a numeric id produced — 3 instances), `async_block._move_marker` (`true` expected, `undefined` produced, "Async move async move closure"), `reference_pattern._mutable_specifier` (`true` expected, `undefined` produced, "Reference patterns"). A related but distinct shape: `reference_pattern._pattern`, `extern_crate_declaration._crate` — VALUE mismatches (`"x"`/`"crate"` expected, `undefined`/a numeric id produced) rather than a missing key. Also in the same run: `async_block._block` and `gen_block._block` reconstruct as `undefined` entirely (expected a real, if empty, `block` node) — a required structural child dropped outright, not just a marker.

**Status: confirmed via `factory-render-parse`'s storage comparison, not yet root-caused.** Smaller volume than the other clusters above (~13 instances, all rust) but a distinct symptom shape (marker/value drop, not variant misselection or empty-array reconstruction) — likely a separate root cause from the other three entries above, not folded in with them for that reason.

**Fix, if/when prioritized:** trace `nodeToConfig`'s handling of `self_parameter`/`async_block`/`reference_pattern`/`extern_crate_declaration` — likely `promoteAnonymousTokenFields` or the boolean-keyword coercion path (`coerceBooleanKeywordStorage`, referenced in the generated factories) not being exercised the same way when fed materialized wrapped-tree data as when fed the validator's old shallow native-read data.
